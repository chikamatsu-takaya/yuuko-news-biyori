# ブランチ保護設定手順（develop / main）

この手順は GitHub の Branch Protection Rules を使って、未検証コードのマージを防ぐための設定手順です。

## 1. 対象ブランチ

- `develop`
- `main`

## 2. 必須設定

GitHub Repository Settings > Branches > Add rule で以下を有効化する。

- `Require a pull request before merging`
- `Require status checks to pass before merging`
- `Require branches to be up to date before merging`
- `Require conversation resolution before merging`
- `Do not allow bypassing the above settings`（管理方針に応じて）

推奨:
- `Include administrators`（管理者も同じゲートを通す）
- `Require linear history`
- `Restrict force pushes`
- `Restrict deletions`

## 3. Required status checks（推奨）

以下のジョブを required checks に追加する。

- `CI / Frontend (lint/typecheck/build)`
- `CI / Rust (check/fmt/clippy)`
- `Test CI / Frontend Tests`
- `Test CI / Rust Tests`
- `Security CI / RustSec Audit`
- `Security CI / Node Audit (High)`
- `Secret Scan / Gitleaks`

## 4. 運用ルール

- PRは原則 `develop` 宛に作成する
- `main` への反映は `develop` からの統合PRで行う
- Required checks が1つでも失敗している場合はマージしない
- 設計変更・依存追加・CI変更は必ずレビューコメントで理由を残す

## 5. CI の高速化・安定化（D149）

必須チェックのジョブ名（上記 3 章）は変えずに、次の 3 点で待ち時間と偶発失敗を減らしている。外部 Action は追加せず、GitHub 公式の `actions/cache` だけを使う。

### 5.1 Rust のキャッシュ（`CI / Rust (check/fmt/clippy)`・`Test CI / Rust Tests`）

- `actions/cache/restore@v6` / `actions/cache/save@v6` で `~/.cargo/registry/index`・`~/.cargo/registry/cache`・`~/.cargo/git/db`・`src-tauri/target` を保存・復元する。
- キーは `rust-<OS>-<ツールチェーン 1.88.0>-<用途>-<src-tauri/Cargo.lock のハッシュ>`。用途は `check-clippy` と `test` で分ける（ビルド成果物の種類が違うため）。完全一致がなければ同じ OS・ツールチェーン・用途の最新キャッシュへフォールバックする。ツールチェーンを上げるときはキー内の `1.88.0` も合わせて変える。
- **保存は develop / main への push で、キーが完全一致しなかったときだけ**。PR は復元のみ（PR ごとのキャッシュが共有キャッシュを追い出さないため。fork からの PR はそもそもキャッシュへ書き込めない）。
- 保存前に `target/debug/incremental` とワークスペース自身（`app` / `app_lib`）の成果物を削除し、依存クレート中心の小さいキャッシュにする。CI では `CARGO_INCREMENTAL=0` とし、`Rust Tests` は PDB 肥大を避けるため `CARGO_PROFILE_DEV_DEBUG=line-tables-only`（panic 時の行番号は残る）にしている。
- キャッシュが壊れた疑いがあるときは、GitHub の Actions > Caches から `rust-` で始まるキャッシュを削除すれば、次の develop への push で作り直される。

### 5.2 Rust 変更のない PR での省略

- Rust の 2 ジョブは、最初の手順で PR のマージコミットと base 側（第 1 親）の差分を見て、`src-tauri/`・`Cargo.toml` / `Cargo.lock`・`rust-toolchain(.toml)`・`.cargo/`・そのワークフロー自身のいずれも変わっていなければ、以降の手順を `if:` でスキップする。
- ジョブ自体は常に起動して成功を報告するので、必須チェックが Pending のまま残らない（`on.paths` は使わない。`security-ci.yml` と同じ方針）。
- push（develop / main）では常に全手順を実行する。差分が取れないなど判定に失敗したときも実行側に倒す。

### 5.3 フロントのビルド再試行（`CI / Frontend (lint/typecheck/build)`）

- `next/font/google` はビルド時に Google Fonts を取得するため、通信の一時失敗で `pnpm build` が落ちることがある（Turbopack では `next/font/google queries have exactly one entry` や `Can't resolve '@vercel/turbopack-next/internal/font/google/font'` として出る）。
- 失敗ログがフォント取得失敗の文言に一致したときだけ、短い待ち時間をはさんで最大 3 回まで試す。それ以外の失敗は 1 回目で即失敗にする。
- Playwright UI E2E は `pnpm dev` で起動し `pnpm build` を使わないため対象外。
