# レビューゲート運用手順（pnpm / Next.js / Tauri）

この手順は、レビュー依頼前と `git push` 前に不具合をできるだけ手元で止めるための運用です。

## 1. 一度だけ行う初期設定

```bash
pnpm run hooks:install
```

この設定で、ローカルリポジトリの Git hook が `.githooks/` を参照するようになります。

## 2. レビュー依頼前に実行するコマンド

```bash
pnpm run review
```

`review` は `review:strict` のエイリアスです。以下を順番に実行します。

- Frontend: `eslint` + `tsc --noEmit` + `pnpm test`
- Frontend build: `next build`
- Rust: `cargo check`
- Rust test: `cargo test`
- Rust format: `cargo fmt --check`
- Rust lint: `cargo clippy -D warnings`

Playwright UI E2E（`pnpm run test:ui`）は `review` / `review:quick` / `review:strict` には含めません（判断と根拠は「6.1」）。画面の導線を変えたPRなどで E2E まで通したいときは、次を使います。

```bash
pnpm run review:ui
```

`review:ui` は `review:strict` のあとに `pnpm run test:ui`（全件）を実行します。全件で約18分かかります。実行前にポート3000が空いていることを確認してください（Playwright は既存の `localhost:3000` のサーバーを再利用するため、別のツリーの `next dev` が動いているとそちらをテストしてしまいます）。

## 3. push 時の自動実行

`hooks:install` 済みであれば、`git push` 時に `pre-push` hook が `review:strict` を自動実行します。

- 成功: push 継続
- 失敗: push 中断（修正して再実行）

## 4. 緊急時の一時スキップ（非推奨）

やむを得ない場合のみ、次の環境変数で hook を一時スキップできます。

```bash
SKIP_REVIEW_HOOK=1 git push
```

PowerShell の場合:

```powershell
$env:SKIP_REVIEW_HOOK = "1"
git push
Remove-Item Env:SKIP_REVIEW_HOOK
```

## 5. CI との関係

ローカルで止めきれなかったものは CI で最終検証されます。  
基本運用は「ローカルで `review` を通してから push」です。

現在のCIジョブ:
- `CI`: lint / typecheck / build / cargo check / cargo fmt / cargo clippy
- `Test CI`: `pnpm test` / `cargo test`
- `Security CI`: `cargo audit` / `pnpm audit --audit-level=high`
- `Secret Scan`: gitleaks

## 6. Playwright UI E2Eの任意実行

Playwright UI E2Eは、通常のPR作成だけでは自動実行しません。必要なPRだけ、次のいずれかで起動します。

### PRコメントから起動する

PRの通常コメント欄で、コメント本文を次のコマンドだけにして投稿します。

```text
/e2e
```

- `OWNER` / `MEMBER` / `COLLABORATOR` のコメントだけを受け付けます。
- 説明文に `/e2e` を含めただけでは起動しません。起動コメントには他の文章を含めないでください。
- PRの最新head commitをcheckoutし、Chromiumの準備後に `pnpm run test:ui` を実行します。
- 完了後、結果とGitHub Actions runへのリンクをPRへコメントします。
- 失敗時のHTMLレポート、スクリーンショット、traceは `playwright-report-*` artifactから確認できます。
- PRコードを実行するE2Eジョブは読み取り権限のみとし、結果投稿ジョブだけにPRコメントの書き込み権限を付与しています。

> `issue_comment` は既定ブランチ上のworkflow定義を使います。そのため、このworkflowを初めて追加するPR自身では `/e2e` を起動できません。マージ後、次のPRで動作確認してください。

### Actions画面から手動起動する

1. GitHubの `Actions` を開く。
2. `Playwright UI E2E` を選ぶ。
3. `Run workflow` を開く。
4. 対象ブランチを選び、必要なら `pr_number` にPR番号を入力して実行する。

`pr_number` を指定した場合はPRのhead commitをテストし、結果をPRへコメントします。省略した場合は、Actions画面で選択したブランチだけをテストします。

このworkflowは任意チェックです。`review:quick` / `review:strict` や既存の必須CIには組み込んでいません。必須CIにするかどうかは、ここでは決めていません（別途判断します）。

### 6.1 `review:quick` / `review:strict` に入れない判断（2026-10-30）

ローカルで実行時間と安定性を測り、次のように決めました。

| スクリプト | `test:ui` | 理由 |
|---|---|---|
| `review:quick` | 入れない | 素早く確認するためのもの。E2E の約18分は合わない |
| `review:strict` | 入れない | `pre-push` hook が push のたびに実行するため、push ごとに約18分増えるのは重すぎる（入れる目安は15分以内とした） |
| `review:ui`（追加） | 入れる | E2E まで通したいときに明示的に実行する |

計測値（Windows 11 のローカル、Chromium、`workers: 1`、`retries: 0`、develop `f54968e` 時点）:

| 回 | 結果 | 時間 |
|---|---|---|
| 1回目 | 468 passed / 1 skipped / 0 failed / 0 flaky | 18.0分 |
| 2回目 | 468 passed / 1 skipped / 0 failed / 0 flaky | 17.5分 |

- 全469件のうち `tests/ui/app.spec.ts` が約11.5分を占めます。
- 2回とも失敗・フレークはありませんでした。安定性の面では入れても問題ありませんが、時間の面で `review:strict` からは外しています。
- 並列化（`workers` を増やす・遅いファイルを分ける）などで全件が15分以内に収まるようになったら、`review:strict` に入れるかを改めて判断します。
