# 軽量常駐性能確認手順

最終更新: 2026-10-19（§5 取得頻度・§9 メインウィンドウ解放〔D133〕を追記）
対象: Windows / Tauri版
根拠: 要件定義書 §8.2、§14

## 1. 目的

常駐アプリとしての変更前後を比較できるよう、次の基準値を同じ方法で記録する。

- ウィンドウが応答可能になるまでの起動時間
- 待機中・画面表示中のCPU使用率
- Working Set / Private Memory
- スレッド数・ハンドル数
- プロセスが保持するTCP接続
- `news_refresh_state.json` の更新と保存記事数の変化

現時点の要件は「業務利用に支障を与えにくい」「過剰にならない」であり、合否の固定値はまだ定めない。まず同一PC・同一条件の基準値を残し、機能追加前後の悪化を検出する。

## 2. 測定スクリプト

`scripts/measure-app-performance.ps1` はアプリ本体を変更せず、Windowsのプロセス情報を一定間隔で読み取る。Tauri本体のプロセスだけでなく、そこから起動されたWebView2等の子孫プロセスも合算する。

出力先は既定で `performance-results/`。このディレクトリはGit管理対象外である。

出力:

- `*.json`: 環境情報、起動時間、CPU・メモリ等のmin/average/p95/max、通信・ニュース更新の観測結果
- `*.csv`: サンプルごとの生データ

TCP接続数はサンプリング時点の観測値であり、HTTPリクエスト回数ではない。ニュース取得頻度は状態ファイルの変化と、§5のコード上の制御を併せて判断する。

Working Setは子孫プロセス間の共有ページを重複して含む場合がある。実メモリ圧迫の判断ではPrivate Memoryも併記し、同じPC・同じbuildとの比較を優先する。

## 3. 事前準備

本番に近い条件では、static exportを含むdebug buildを使用する。

```powershell
$env:COREPACK_ENABLE_AUTO_PIN = "0"
pnpm install --frozen-lockfile
pnpm exec tauri build --debug --no-bundle
Remove-Item Env:COREPACK_ENABLE_AUTO_PIN
```

生成される実行ファイルは通常 `src-tauri/target/debug/app.exe` である。ファイル名が変わった場合は、実際の生成先を `-ExecutablePath` に指定する。

ニュース取得を含めて確認する場合は、先に検証用ニュースソースを設定する。

```powershell
$env:COREPACK_ENABLE_AUTO_PIN = "0"
pnpm run setup:dev-news-source
Remove-Item Env:COREPACK_ENABLE_AUTO_PIN
```

## 4. 測定シナリオ

### 4.1 起動直後

スクリプトからアプリを起動し、ウィンドウ応答までの時間と起動後60秒を測定する。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ExecutablePath src-tauri/target/debug/app.exe `
  -DurationSeconds 60 `
  -SampleIntervalSeconds 2 `
  -Label startup
```

`startupReadySeconds` はプロセス生成から、メインウィンドウが作成され応答可能になるまでの時間である。ニュース取得完了時間ではない。

### 4.2 待機状態

アプリを通常どおり起動し、待機状態にしてから別のPowerShellで実行する。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ProcessName app `
  -DurationSeconds 300 `
  -SampleIntervalSeconds 5 `
  -Label waiting
```

同名の`app.exe`が複数起動している場合、誤測定を防ぐためスクリプトは停止する。タスクマネージャー等で対象PIDを確認し、`-TargetProcessId`を使用する。

### 4.3 メイン画面表示中

メイン画面を表示した状態で同じ時間・間隔を使う。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ProcessName app `
  -DurationSeconds 300 `
  -SampleIntervalSeconds 5 `
  -Label main-window
```

待機状態と画面表示中のJSONを比較し、CPU・メモリ・スレッド数が継続的に増加していないか確認する。

プロセス名で特定できない場合はPIDを指定できる。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -TargetProcessId 12345 `
  -DurationSeconds 300 `
  -Label waiting
```

## 5. ニュース通信頻度の確認

`NewsScheduler` は次の制御になっている（判断台帳 D16 で「1日1回」から変更）。

1. 起動時に1回判定する（日付変更または周期到来のときに取得）。
2. 以降は30分ごとに、状態ファイルと時刻だけを確認する。
3. 通知の時間帯（`notification.workTimeRanges`）内で、前回の取得成功から3時間以上たっていれば取得する。
4. 日付が変わった後は、時間帯外（深夜）でも1回取得する。
5. 取得成功時だけ状態ファイルの日付・時刻（`last_news_refresh_date` / `last_news_refresh_at`）を更新する。
6. 取得失敗時は次回の30分チェックで再試行する。

したがって通常の成功状態では、ニュース取得は起動時・日付変更後・時間帯内の3時間おきに抑えられる。30分ごとの処理は外部通信ではなく、設定・状態ファイルと時刻の確認である。

測定JSONでは次を確認する。

- `newsRefreshObservation.stateFileChangeCount`
- `initialState` / `finalState` の `lastNewsRefreshDate`
- `markdownCountDelta`
- `networkObservation.remoteEndpoints`

短時間の待機測定で状態ファイルや記事数が繰り返し増える場合は、日付判定または失敗時再試行を調査する。

## 6. 初回評価の見方

数値はPC性能やWebView2の状態に左右されるため、異なるPCの絶対値をそのまま合否にしない。

優先して見る項目:

1. 同じPC・同じbuildで再測定したときに大きくぶれないか
2. 待機中のCPU平均・p95が継続的に高止まりしていないか
3. Working Set / Private Memoryが時間とともに増え続けていないか
4. 待機状態とメイン画面表示中の差を説明できるか
5. ユーザー操作なしでTCP接続やニュース保存が繰り返されていないか

初期の暫定アラートとして、変更前比でCPU平均・p95またはメモリ平均が明確に増えた場合は、PRで理由を説明する。固定の製品目標値は、複数PCで基準値を集めてから別途決定する。

## 7. 結果共有

測定結果にはPC名などの環境情報が含まれるため、JSON/CSVをそのままコミットしない。PRには次の要約だけを記載する。

- build種別とコミットID
- 測定シナリオ、時間、サンプル間隔
- `startupReadySeconds`
- CPU average / p95 / max（ルート＋子孫プロセス合計）
- Working Set average / p95 / max（ルート＋子孫プロセス合計）
- ニュース状態ファイルの変更回数と記事数差分
- 前回測定との差と判断

測定条件:

- commit: `6f594b5`（PR #76反映後の`develop`）
- build: `pnpm exec tauri build --debug --no-bundle`
- シナリオ: build直後の起動応答後60秒を5秒間隔で測定し、続けて起動時間を3回再測定
- 対象: `app`と子孫プロセス（`msedgewebview2` / `conhost`、平均8プロセス）
- PC: Windows 11、論理プロセッサ14

結果:

| 項目 | 結果 |
|---|---:|
| 起動応答 | build直後 3.392秒 / 再測定3回 0.627, 0.667, 0.671秒（中央値0.667秒） |
| CPU | average 0.000% / p95 0.000% / max 0.000% |
| Working Set | average 588.754MB / p95 592.852MB / max 592.852MB |
| Private Memory | average 330.243MB / p95 332.875MB |
| TCP接続 | average 0.083 / max 1 |
| ニュース状態ファイル更新 | 0回 |
| 記事Markdown増分 | 0件 |

補足:

- 起動応答前のCPUバーストはCPU集計対象外。`startupReadySeconds`で起動体験を分けて記録している。build直後と直後の再起動で差があるため、起動性能は単発値ではなく複数回値で比較する。
- 日付未更新状態で行った事前スモークでは、起動時に状態ファイルが1回更新され記事が1件増えた。その後の同日再起動では、上記60秒測定を含め状態更新・記事増加は0回であり、不要なニュース再取得は確認されなかった。
- TCP接続は12サンプル中1サンプルだけ、WebView2を含むプロセスツリーで1接続を観測した。接続先の観測だけではアプリのHTTP要求かWebView2内部通信かを断定できないため、ニュース状態の変化と分けて扱う。
- debug buildのため、この値をリリース版の製品目標にはしない。今後の変更前後比較に使い、配布候補版ではrelease buildを再測定する。

## 9. 現在の常駐状態

2026-06-15時点で、単一のメインウィンドウを閉じるとプロセスを終了せず`hide`し、トレイの「画面を開く」から`unminimize` / `show` / `focus`するMVP方式を採用した。トレイの「常駐を終了する」からのみ明示終了できる。

その後、メインウィンドウ非表示中（最小化を含む）の通知用に、小型ゆうこ専用ウィンドウ（ラベル `yuuko`）を実装した（判断台帳 D01。ゆうこ登場・通知挙動 詳細設計書 §7.3）。このウィンドウは起動時には作らず、非表示中に初めてゆうこを出すときに Rust から遅延生成するため、非表示待機中の測定値は「ゆうこウィンドウがまだ無い状態」と「一度ゆうこが出た後の状態」で WebView の数が変わる。§4.2 の測定ではどちらの状態かを記録する。実機確認では、次を同じアプリプロセスで比較する。

1. メインウィンドウ表示中に§4.3を測定する。
2. 閉じるボタンでウィンドウを非表示にし、タスクマネージャーでプロセス継続を確認する。
3. 非表示のまま§4.2を測定する。
4. トレイから再表示でき、ニュース取得・日次アーカイブの低頻度処理が停止していないことを確認する。
5. トレイから明示終了し、プロセスが残らないことを確認する。

### 9.1 非表示が続いたときのメインウィンドウ解放（判断台帳 D133）

非表示待機（閉じる操作・自動起動時の非表示開始）が5分（`app_lifecycle::MAIN_WINDOW_RELEASE_DELAY`。2026-11-09 に10分から短縮）続くと、メインウィンドウを破棄して WebView のメモリを返す。ゆうこ用ウィンドウ・スケジューラ・自動要約・ローカルLLMは動き続ける。設定画面に未保存の変更があるあいだは破棄しない。再表示（トレイ「画面を開く」・2つ目の起動・ゆうこの「詳しく見る」）でメインウィンドウを作り直す（詳細設計書 §10.1.1）。

このため非表示中の測定値は、解放の前後で大きく変わる。§4.2 の測定では次を分けて記録する。

1. 非表示にしてから5分未満（解放前）に§4.2を測定する。
2. 非表示のまま5分以上待ち（解放後）、再度§4.2を測定する。解放前と比べて Working Set / Private Memory が減っていること、WebView2 の子孫プロセスが減っていることを確認する。
3. 解放後にトレイの「画面を開く」で再表示し、白画面にならず、ニュース・設定などが永続状態から読み直されることを確認する。
4. 解放後にゆうこの「詳しく見る」で開き、対象の記事が表示されることを確認する。
5. 設定画面に未保存の変更を残したまま閉じ、5分以上たっても解放されない（再表示で入力が残っている）ことを確認する。

### 11.1 ローカルLLMのスレッド数の比較（2026-11-09・release）

同じ記事で要約を 2 回ずつ（1 回目は新規作成、2 回目は作り直し）、2 秒間隔で測った。スレッド数だけを変えた手元のビルドで比べた。

| スレッド数 | 1 回目 | 2 回目 | 生成中の CPU 平均 | Working Set 最大 |
|---|---:|---:|---:|---:|
| 4（変更前） | 60 秒 | 62 秒 | 27〜28% | 約 2.7GB |
| 2（変更後） | 82 秒 | 63 秒 | 14〜15% | 約 2.7GB |

- 2 にすると CPU は半分になった。時間は 2 回目でほぼ同じ（62→63 秒）、1 回目は 60→82 秒（+22 秒、約 +37%）。1 回目の差の原因（入力の読み込み〔prefill〕がスレッド数に比例して遅くなる・ばらつき など）は切り分けていない。
- この結果を受けて、llama-server のスレッドの上限を 4 → 2 にした（`local_llm_runtime::MAX_THREADS`。論理コア数の半分・下限 1 は同じ）。論理 4 コア以下の PC はもともと 2 以下なので変わらない。
- 回数は 2 回ずつ・この PC だけの結果。

### 11.2 WebView2 の GPU を使わない設定（--disable-gpu）の比較（2026-11-09・release）

測定条件: release・メイン画面を最大化・起動後 60 秒放置（待機）→ 約 90 秒の画面移動・スクロール（操作中）。`--disable-gpu` の有無だけを変えた手元のビルドで比べた（値は Working Set（Private））。

| 状態 | GPU あり（変更前） | GPU なし（変更後） |
|---|---:|---:|
| 待機 | 606MB（342MB） | 448MB（168MB） |
| 操作中の最大 | 745MB（473MB） | 474MB（177MB） |
| うち GPU プロセス | 202MB（177MB） | 64MB（19MB） |
| CPU | ほぼ 0% | ほぼ 0% |
| レンダラーの CPU 時間（計測全体） | 1.5 秒 | 2.0 秒 |

- GPU なしで待機中の Private は約半分（342→168MB）、操作中の最大は 473→177MB。GPU プロセスの Private は 177→19MB。描画は CPU 側に移るため、レンダラーの CPU 時間は 1.5→2.0 秒に増えたが、CPU 使用率はどちらもほぼ 0%。
- 主な画面と、透明なゆうこウィンドウは正しく表示された。修正後の版で、藤井が画面の切り替え・スクロール・ゆうこの動きを触って、もたつきが無いことを確認した（2026-11-09）。
- この結果を受けて、メイン画面（`tauri.conf.json` の `additionalBrowserArgs`）とゆうこウィンドウ（`yuuko_window.rs`）の両方に、Tauri の既定値 `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection` と `--disable-gpu` を指定した（同じデータフォルダの WebView2 は引数が一致しないと生成に失敗するため、同じ値にそろえる）。
- 計測中、起動直後のホームに「おすすめニュースの読み込みに失敗しちゃった」が出ることがあった（GPU なしで 2 回中 2 回。いずれもその日のアーカイブ保守が済む前のデータで、起動時に保守が動いた回）。原因は GPU ではなく、起動時の日次アーカイブ保守（検証済み記事Markdownの退避＝移動）と、おすすめ一覧の読み込み（書き込みロックを取らない）の競合だった。一覧が記事ファイルを列挙した後・読む前に保守がファイルを移動すると、読み込みが「ファイルが見つからない」になり、一覧全体がエラーになっていた。GPU の有無は起動のタイミングを変えるだけと考えられ（GPU ありでは未再現。因果の切り分けはしていない）、実際には毎日最初の起動で起こりうる。一覧の読み込みで、列挙後に消えたファイル・フォルダは飛ばすように直した（`article_repository.rs` の `load_readable_article_records`・`collect_markdown_files`。回帰テスト `listing_survives_concurrent_archive_maintenance`）。修正後の release（GPU なし）で、保守が済む前のデータから 2 回起動し、2 回とも出なかった（修正前は 2 回中 2 回）。
