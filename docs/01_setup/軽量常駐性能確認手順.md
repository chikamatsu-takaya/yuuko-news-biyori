# 軽量常駐性能確認手順

最終更新: 2026-06-11
対象: Windows / Tauri版
根拠: 要件定義書 §8.2、§14

## 1. 目的

常駐アプリとしての変更前後を比較できるよう、次の基準値を同じ方法で記録する。

- ウィンドウが応答可能になるまでの起動時間
- 待機中・画面表示中のCPU使用率
- Working Set / Private Memory
- スレッド数・ハンドル数
- プロセスが保持するTCP接続
- `news_refresh_state.json` の更新と保存記事数の変化

現時点の要件は「業務利用に支障を与えにくい」「過剰にならない」であり、合否の固定値はまだ定めない。まず同一PC・同一条件の基準値を残し、機能追加前後の悪化を検出する。

## 2. 測定スクリプト

`scripts/measure-app-performance.ps1` はアプリ本体を変更せず、Windowsのプロセス情報を一定間隔で読み取る。Tauri本体のプロセスだけでなく、そこから起動されたWebView2等の子孫プロセスも合算する。

出力先は既定で `performance-results/`。このディレクトリはGit管理対象外である。

出力:

- `*.json`: 環境情報、起動時間、CPU・メモリ等のmin/average/p95/max、通信・ニュース更新の観測結果
- `*.csv`: サンプルごとの生データ

TCP接続数はサンプリング時点の観測値であり、HTTPリクエスト回数ではない。ニュース取得頻度は状態ファイルの変化と、§5のコード上の制御を併せて判断する。

Working Setは子孫プロセス間の共有ページを重複して含む場合がある。実メモリ圧迫の判断ではPrivate Memoryも併記し、同じPC・同じbuildとの比較を優先する。

## 3. 事前準備

本番に近い条件では、static exportを含むdebug buildを使用する。

```powershell
$env:COREPACK_ENABLE_AUTO_PIN = "0"
pnpm install --frozen-lockfile
pnpm exec tauri build --debug --no-bundle
Remove-Item Env:COREPACK_ENABLE_AUTO_PIN
```

生成される実行ファイルは通常 `src-tauri/target/debug/app.exe` である。ファイル名が変わった場合は、実際の生成先を `-ExecutablePath` に指定する。

ニュース取得を含めて確認する場合は、先に検証用ニュースソースを設定する。

```powershell
$env:COREPACK_ENABLE_AUTO_PIN = "0"
pnpm run setup:dev-news-source
Remove-Item Env:COREPACK_ENABLE_AUTO_PIN
```

## 4. 測定シナリオ

### 4.1 起動直後

スクリプトからアプリを起動し、ウィンドウ応答までの時間と起動後60秒を測定する。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ExecutablePath src-tauri/target/debug/app.exe `
  -DurationSeconds 60 `
  -SampleIntervalSeconds 2 `
  -Label startup
```

`startupReadySeconds` はプロセス生成から、メインウィンドウが作成され応答可能になるまでの時間である。ニュース取得完了時間ではない。

### 4.2 待機状態

アプリを通常どおり起動し、待機状態にしてから別のPowerShellで実行する。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ProcessName app `
  -DurationSeconds 300 `
  -SampleIntervalSeconds 5 `
  -Label waiting
```

同名の`app.exe`が複数起動している場合、誤測定を防ぐためスクリプトは停止する。タスクマネージャー等で対象PIDを確認し、`-TargetProcessId`を使用する。

### 4.3 メイン画面表示中

メイン画面を表示した状態で同じ時間・間隔を使う。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -ProcessName app `
  -DurationSeconds 300 `
  -SampleIntervalSeconds 5 `
  -Label main-window
```

待機状態と画面表示中のJSONを比較し、CPU・メモリ・スレッド数が継続的に増加していないか確認する。

プロセス名で特定できない場合はPIDを指定できる。

```powershell
powershell -ExecutionPolicy Bypass -File scripts/measure-app-performance.ps1 `
  -TargetProcessId 12345 `
  -DurationSeconds 300 `
  -Label waiting
```

## 5. ニュース通信頻度の確認

`NewsScheduler` は次の制御になっている。

1. 起動時に1回判定する。
2. 以降は30分ごとにローカル日付だけを確認する。
3. `last_news_refresh_date` が当日と異なる場合だけニュース取得を行う。
4. 取得成功時だけ状態ファイルの日付を更新する。
5. 取得失敗時は次回の30分チェックで再試行する。

したがって通常の成功状態では、ニュース取得は起動時または日付変更後の1回に抑えられる。30分ごとの処理は外部通信ではなく、設定・状態ファイルとローカル日付の確認である。

測定JSONでは次を確認する。

- `newsRefreshObservation.stateFileChangeCount`
- `initialState` / `finalState` の `lastNewsRefreshDate`
- `markdownCountDelta`
- `networkObservation.remoteEndpoints`

短時間の待機測定で状態ファイルや記事数が繰り返し増える場合は、日付判定または失敗時再試行を調査する。

## 6. 初回評価の見方

数値はPC性能やWebView2の状態に左右されるため、異なるPCの絶対値をそのまま合否にしない。

優先して見る項目:

1. 同じPC・同じbuildで再測定したときに大きくぶれないか
2. 待機中のCPU平均・p95が継続的に高止まりしていないか
3. Working Set / Private Memoryが時間とともに増え続けていないか
4. 待機状態とメイン画面表示中の差を説明できるか
5. ユーザー操作なしでTCP接続やニュース保存が繰り返されていないか

初期の暫定アラートとして、変更前比でCPU平均・p95またはメモリ平均が明確に増えた場合は、PRで理由を説明する。固定の製品目標値は、複数PCで基準値を集めてから別途決定する。

## 7. 結果共有

測定結果にはPC名などの環境情報が含まれるため、JSON/CSVをそのままコミットしない。PRには次の要約だけを記載する。

- build種別とコミットID
- 測定シナリオ、時間、サンプル間隔
- `startupReadySeconds`
- CPU average / p95 / max（ルート＋子孫プロセス合計）
- Working Set average / p95 / max（ルート＋子孫プロセス合計）
- ニュース状態ファイルの変更回数と記事数差分
- 前回測定との差と判断

## 8. 2026-06-11 初回基準値

測定条件:

- commit: `6f594b5`（PR #76反映後の`develop`）
- build: `pnpm exec tauri build --debug --no-bundle`
- シナリオ: build直後の起動応答後60秒を5秒間隔で測定し、続けて起動時間を3回再測定
- 対象: `app`と子孫プロセス（`msedgewebview2` / `conhost`、平均8プロセス）
- PC: Windows 11、論理プロセッサ14

結果:

| 項目 | 結果 |
|---|---:|
| 起動応答 | build直後 3.392秒 / 再測定3回 0.627, 0.667, 0.671秒（中央値0.667秒） |
| CPU | average 0.000% / p95 0.000% / max 0.000% |
| Working Set | average 588.754MB / p95 592.852MB / max 592.852MB |
| Private Memory | average 330.243MB / p95 332.875MB |
| TCP接続 | average 0.083 / max 1 |
| ニュース状態ファイル更新 | 0回 |
| 記事Markdown増分 | 0件 |

補足:

- 起動応答前のCPUバーストはCPU集計対象外。`startupReadySeconds`で起動体験を分けて記録している。build直後と直後の再起動で差があるため、起動性能は単発値ではなく複数回値で比較する。
- 日付未更新状態で行った事前スモークでは、起動時に状態ファイルが1回更新され記事が1件増えた。その後の同日再起動では、上記60秒測定を含め状態更新・記事増加は0回であり、不要なニュース再取得は確認されなかった。
- TCP接続は12サンプル中1サンプルだけ、WebView2を含むプロセスツリーで1接続を観測した。接続先の観測だけではアプリのHTTP要求かWebView2内部通信かを断定できないため、ニュース状態の変化と分けて扱う。
- debug buildのため、この値をリリース版の製品目標にはしない。今後の変更前後比較に使い、配布候補版ではrelease buildを再測定する。

## 9. 現在の常駐状態

2026-06-15時点で、単一のメインウィンドウを閉じるとプロセスを終了せず`hide`し、トレイの「画面を開く」から`unminimize` / `show` / `focus`するMVP方式を採用した。トレイの「常駐を終了する」からのみ明示終了できる。

小型ゆうこ専用ウィンドウは未実装であり、現時点の非表示待機中は画面端からゆうこを表示しない。実機確認では、次を同じアプリプロセスで比較する。

1. メインウィンドウ表示中に§4.3を測定する。
2. 閉じるボタンでウィンドウを非表示にし、タスクマネージャーでプロセス継続を確認する。
3. 非表示のまま§4.2を測定する。
4. トレイから再表示でき、ニュース取得・日次アーカイブの低頻度処理が停止していないことを確認する。
5. トレイから明示終了し、プロセスが残らないことを確認する。
