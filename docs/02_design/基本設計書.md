## 3. システム概要

本システムは、ユーザーの関心ジャンルに応じてニュースを取得し、AIによる要約・再説明・用語解説を付与するデスクトップ向けニュースコンパニオンアプリである。

アプリ内にはマスコットキャラクター「ゆうこ」が存在し、以下の体験を提供する。

- ニュースをおすすめする
- ニュース内容を分かりやすく再説明する
- 難しい用語を補足する
- 解説内容を「ゆうこ辞書」として保存する
- 利用に応じて友情ランクを上げる
- 報酬やカスタマイズ要素を解放する
- 流れ星のかけらを使ったガチャ要素で継続利用を促す

本システムは、通常時はバックグラウンド常駐を基本とし、必要時のみ画面またはゆうこの通知を表示する。

## 4. 技術構成

### 4.1 採用技術

Tauri版における採用技術は以下とする。

| 領域 | 採用技術 | 役割 |
|---|---|---|
| アプリ基盤 | Tauri v2 | デスクトップアプリ基盤、WebView表示、Rust連携、OS連携 |
| UI | React | 画面、ゆうこ表示、吹き出し、モーダル、UI部品 |
| UI言語 | TypeScript | UI実装、型安全な画面制御、Tauri command呼び出し |
| UIビルド | Next.js (App Router) | Reactアプリの開発・ビルド |
| 中核ロジック | Rust | 状態管理、通信、保存処理、AI連携、通知制御 |
| データ保存 | Markdown / JSON | ニュース、設定、辞書、状態情報の保存 |
| AI連携 | Gemini API / MockProvider | 要約、再説明、用語解説 |
| ニュース取得 | RSS | ニュース候補取得 |
| 開発エディタ | VS Code | チーム開発、AI駆動開発、拡張機能管理 |
| パッケージ管理 | pnpm | フロントエンド依存、Tauri開発コマンド |

### 4.2 技術方針

- React / TypeScriptは画面表示、ユーザー操作受付、ゆうこの演出を担当する。
- Rustは業務ロジック、状態管理、通信、保存、AI連携、通知制御を担当する。
- React側にRSS取得、AI API呼び出し、ファイル保存などの中核処理を持たせない。
- ReactとRustの接続はTauri commandを基本とする。
- Tauri commandは必要最小限とし、危険なファイル操作や任意URL取得を無制限に公開しない。
- AI連携部分は、Gemini APIとMockProviderを差し替え可能な構造にする。
- 常駐アプリであるため、軽量性と安定性を優先する。
- MVP段階ではC++ / Qt / QMLを使用しない。
- C++ / Qt版の資料は別案として残し、Tauri版とはファイル名で区別する。

## 5. 全体アーキテクチャ

### 5.1 全体構成

本システムは、以下の層で構成する。

```text
UI層（React / TypeScript）
  ↓
Tauri command呼び出し層（TypeScript services）
  ↓
Tauri command層（Rust）
  ↓
アプリケーションサービス層（Rust）
  ↓
ドメイン層（Rust）
  ↓
インフラ層（Rust）
  ↓
ローカル保存 / 外部通信
```

### 5.2 各層の責務

#### UI層

担当:
- 画面表示
- レイアウト
- ユーザー操作受付
- アニメーション
- ゆうこ表示
- 吹き出し表示
- モーダル表示
- 入力フォーム
- 表示用状態の保持

対象:
- メイン画面
- ニュース閲覧画面
- 設定画面
- ゆうこ辞書画面
- ニュース履歴画面
- カスタマイズ画面
- ガチャ画面
- 各種モーダル
- 常駐ゆうこ表示レイヤー

#### Tauri command呼び出し層

担当:
- ReactからRust側機能を呼び出す窓口
- `invoke()` の呼び出しを集約する
- React側で使いやすい関数名・型へ整える
- エラーをUI向けに扱いやすい形式へ変換する

例:
- `getRecommendedArticles()`
- `getArticleDetail(articleId)`
- `explainSelectedTerm(articleId, selectedText)`
- `saveDictionaryMemo(entryId, memo)`
- `getUserSettings()`
- `saveUserSettings(settings)`

#### Tauri command層

担当:
- Reactから呼ばれるRust側の公開インターフェース
- 入力値の検証
- サービス層への処理委譲
- UI向けDTOの返却
- エラーの整形

注意:
- 任意ファイル読み書きや任意URL取得のような危険なcommandを作らない。
- command単位で責務を明確にする。
- APIキーや秘密情報を返却しない。

#### アプリケーションサービス層

担当:
- ニュース取得制御
- 要約生成制御
- 用語解説制御
- ゆうこ辞書制御
- 友情ランク制御
- ガチャ制御
- 設定制御
- 通知制御
- 報酬制御
- AI Provider切替

#### ドメイン層

担当:
- 記事
- 辞書項目
- 友情ランク
- 報酬
- ガチャアイテム
- 設定値
- 通知状態
- 既読状態

など、アプリ固有の概念を表現する。

#### インフラ層

担当:
- RSS取得
- HTML取得
- Markdown保存
- JSON保存
- 設定ファイル保存
- ログ出力
- Gemini API通信
- MockProvider応答
- ローカルファイル読み書き
- OS連携
- 将来的なGoogle Drive連携

## 7. 主要機能設計

---

### 7.1 ニュース取得機能

#### 目的
ユーザーの関心ジャンルに応じて、RSSからニュース候補を取得する。

#### 基本処理
1. 起動時にニュース取得処理を開始する。
2. 設定されたジャンルに対応するRSSを参照する。
3. RSSから記事タイトル、URL、出典、日時、概要を取得する。
4. 重複判定を行う。
5. 必要に応じてHTML本文または本文抜粋を取得する。
6. 内部データ形式へ変換する。
7. Markdown保存対象として登録する。
8. おすすめ判定へ渡す。

#### 取得タイミング
- アプリ起動時に1回
- 長時間起動時は深夜0時に1回
- 初期版では高頻度ポーリングは行わない

#### Rust側責務
- RSS取得
- URL検証
- 重複判定
- HTML取得
- 本文抽出
- 保存対象データ生成
- エラー処理
- ログ出力

#### React側責務
- 取得中表示
- 取得結果表示
- 取得失敗時の軽い案内
- 手動更新ボタンの操作受付

#### 失敗時
- RSS取得失敗時は、既存ローカルデータを表示する。
- HTML取得失敗時は、RSSから取得可能な情報のみで記事データを作る。
- React側では画面全体をエラーにせず、前回データを表示できるようにする。

---

### 7.2 ニュース保存機能

#### 目的
取得したニュースを、再表示・アーカイブ・要約生成・辞書連携に利用できる形で保存する。

#### 保存単位
- 1記事1ファイルを基本とする。
- Markdownを主保存形式とする。
- 必要に応じて管理用JSONを併用する。

#### 保存内容
- 記事ID
- タイトル
- 出典
- URL
- 取得日時
- 公開日時
- ジャンル
- 要約
- ゆうこの再説明文
- ゆうこの一言
- タグ
- 表示状態
- アーカイブ状態
- 本文抜粋
- 解説対象候補語

#### Rust側責務
- ファイル名サニタイズ
- 保存先パス決定
- Markdown生成
- JSONメタデータ保存
- 保存失敗時のリトライまたはエラー返却

#### React側責務
- 保存状態の表示
- 保存失敗時のユーザー向け通知

#### アーカイブ
- 1か月経過したニュースを月単位で圧縮対象とする。
- お気に入り記事は圧縮対象から除外する。
- 圧縮済み記事は、ユーザー操作により展開・再閲覧できるようにする。
- MVPでは自動圧縮まで必須にせず、設計上の拡張対象とする。

---

### 7.3 おすすめ判定機能

#### 目的
取得したニュース候補から、ユーザーに提示する記事を選ぶ。

#### 判定要素
- 関心ジャンル一致
- 内容の重要度
- 驚き要素
- 鮮度
- 既読状態
- ユーザー傾向メモとの一致

#### 基本フロー
1. ニュース候補取得
2. 重複除外
3. 既読・鮮度補正
4. 重要度判定
5. 驚き要素判定
6. 関心ジャンル一致判定
7. ユーザー傾向メモ一致判定
8. 総合スコア順に並び替え
9. 上位10件前後を当日候補とする

#### 初期版方針
- ルールベースで実装する。
- AIによるおすすめ判定は初期版では必須にしない。
- スコア計算の詳細は詳細設計で定義する。
- 判定処理はRust側に置き、React側では並び替えロジックを持たない。

---

### 7.4 AI要約・再説明機能

#### 目的
記事内容をユーザーが理解しやすい形に変換する。

#### 生成対象
- 短い要約
- ゆうこの再説明文
- 要点整理
- 注目ポイント
- ゆうこの一言
- ゆうこの感想

#### 基本方針
- 原文大量表示は避ける。
- ソフト内では再説明・要点整理・注目ポイントを中心に表示する。
- 元記事確認用リンクを必ず残す。
- AI入力には必要最小限の本文または本文抜粋を使用する。
- APIキーはReact側へ渡さない。
- AI呼び出しはRust側で行う。

#### AI処理の抽象化
AI処理はRust側の `AiProviderService` または相当する抽象インターフェースを通して呼び出す。

想定Provider:
- `GeminiProvider`
- `MockProvider`

想定処理:
- 要約生成
- 再説明文生成
- 用語解説生成
- 長文要点説明生成
- ゆうこの一言生成

### 7.5 用語解説機能

#### 目的
ニュース閲覧中に分からない単語やフレーズを、ゆうこの口調で分かりやすく解説する。

#### 対象
- 単語
- 短いフレーズ
- 長文選択時の要点説明

#### 基本フロー
1. ユーザーがニュース閲覧画面上で語句を選択する。
2. 選択箇所付近に解説ボタンを表示する。
3. ユーザーが解説ボタンを押下する。
4. React側からRust側のTauri commandへ解説要求を送る。
5. Rust側で選択文字列を検証する。
6. ゆうこ辞書に完全一致項目があるか確認する。
7. 存在する場合は辞書内容を返却する。
8. 存在しない場合はAIで解説を生成する。
9. 結果をReact側へ返却する。
10. React側でポップアップ表示する。
11. 解説内容をゆうこ辞書へ保存する。

#### 表示方式
- 初回は短く表示する。
- 必要に応じて「もっと見る」で詳細表示する。
- 右側パネルまたは小型ポップアップで表示する。

### 7.6 ゆうこ辞書機能

#### 目的
一度解説した内容を保存し、再利用および見返しを可能にする。

#### 保存対象
- 単語解説
- フレーズ解説
- 長文要点説明

#### 主な機能
- 一覧表示
- 検索
- 詳細表示
- ★マーク
- 付箋メモ
- 削除
- 完全一致による再利用

#### 初期版方針
- 類似一致は実装しない。
- 完全一致を基本とする。
- 保存形式はMarkdownまたはJSON併用を検討する。
- 検索・保存・削除はRust側で行う。
- React側は一覧表示、入力、操作受付を担当する。

### 7.7 ゆうこ表示・通知機能

#### 目的
ゆうこがユーザーへ自然に話しかけ、ニュース閲覧へ誘導する。

#### 基本挙動
- 通常時はバックグラウンド待機。
- 条件を満たした場合、画面端からゆうこが出現する。
- 初回クリック時にニュース軽量プレビューを表示する。
- 再クリック時にメイン画面またはニュース閲覧画面へ遷移する。

#### 抑制条件
- スリープ状態
- 指定ソフト起動中
- マイク使用中
- フルスクリーン中
- ユーザーが通知停止中
- 通知時間帯外
- 通知クールタイム中
- 日次通知上限到達

#### Rust側責務
- 通知条件判定
- 抑制条件判定
- 通知頻度管理
- 紹介ニュース選定
- 友情ポイント加算
- ランクアップ判定
- 報酬未通知管理

#### React側責務
- ゆうこの表示
- 登場・退場アニメーション
- 吹き出し表示
- ニュース軽量プレビュー表示
- クリック操作受付
- モーダル表示

#### 初期版方針
- 抑制条件は設定構造を先に作る。
- OS連携による完全判定は段階的に実装する。
- MVPでは右下からの簡易登場を基本とする。

### 7.8 友情ランク機能

#### 目的
ユーザーの利用行動に応じて友情ポイントを付与し、継続利用を促す。

#### ポイント付与対象
- ゆうこ経由でメイン画面へ遷移
- ニュース詳細表示
- 再説明表示
- 用語解説利用

#### 基本仕様
- ポイント制
- 日次上限あり
- 初期最大ランクは20
- ランク上昇ごとに報酬を1つ解放
- 報酬解放順は固定

#### 状態管理
- 現在ランク
- 現在ポイント
- 次ランク必要ポイント
- 日次獲得ポイント
- 解放済み報酬
- 未受取報酬

#### 方針
- ポイント計算とランクアップ判定はRust側に置く。
- React側はランク、進捗、通知演出を表示する。

---

### 7.9 カスタマイズ機能

#### 目的
解放済み報酬を使い、ゆうこや画面テーマを変更できるようにする。

#### 対象
- ゆうこのデコレーション
- UIテーマ
- 吹き出しデザイン
- 話し方
- 性格
- 呼び名

#### 初期版方針
- 実際の項目数は少なくてよい。
- UIとデータ構造を先に整える。
- 解放済み / 未解放の状態を管理する。
- React側はプレビューと選択UIを担当する。
- Rust側は所持状態、適用状態、保存を担当する。

---

### 7.10 ガチャ機能

#### 目的
流れ星のかけらを使い、デコやテーマなどの収集要素を提供する。

#### 基本仕様
- 通貨名は「流れ星のかけら」
- 単発ガチャを基本とする。
- 10連ガチャは初期版ではUIのみでもよい。
- 排出対象は仮データでよい。
- 結果表示モーダルを持つ。

#### 排出対象候補
- UIテーマ
- ゆうこのデコ
- 吹き出しデザイン
- 表情差分
- 口調
- 性格
- 呼び名関連アイテム

#### 重複時
初期版では、以下のいずれかを仮実装する。

- かけらへ一部還元
- 重複として履歴のみ記録

## 12. セキュリティ設計

### 12.1 外部通信

- RSS取得先は管理対象とする。
- HTML取得先はURLスキームとホストを検証する。
- ローカルアドレスや社内アドレスへの意図しないアクセスを避ける。
- AI API通信は必要最小限のデータのみ送信する。
- 外部通信は原則Rust側で行い、React側から直接AI APIやRSS取得を行わない。

### 12.2 HTML / Markdown表示

- 取得HTMLをそのまま表示しない。
- Markdown表示時に危険なHTMLやスクリプトを許可しない。
- 外部リンクはURLを検証した上で開く。
- React側で `dangerouslySetInnerHTML` を安易に使用しない。

### 12.3 Tauri command

- 任意ファイル読み書きcommandを作らない。
- 任意URL取得commandを作らない。
- フロントから渡された値はRust側で検証する。
- APIキーや秘密情報をReact側へ返却しない。
- Tauriプラグイン追加時は権限とライセンスを確認する。

### 12.4 ログ

- 本文全文、選択文字列全文、APIキー、個人情報をログに出さない。
- ログは原因調査に必要な最小限とする。
- AIへ送信した全文をログに残さない。

### 12.5 APIキー

- コードへ直書きしない。
- React側へ渡さない。
- 初期開発では環境変数を候補とする。
- 正式な管理方法はセキュリティ詳細設計で定義する。

---

## 13. エラー処理設計

### 13.1 基本方針

- 失敗時は安全側へ倒す。
- 一部機能の失敗でアプリ全体を落とさない。
- ユーザーに過剰な不安を与えない文言にする。
- ログには原因調査に必要な範囲だけを残す。
- Rust側の技術エラーとReact側の表示文言を分ける。

### 13.2 代表的なエラーと対応

| エラー | 対応 |
|---|---|
| RSS取得失敗 | 既存ローカルニュースを表示 |
| HTML取得失敗 | RSS情報のみで記事化 |
| Markdown保存失敗 | 再試行またはエラー通知 |
| AI要約失敗 | 要約なし状態で記事表示 |
| 用語解説失敗 | 再選択を促す |
| 辞書保存失敗 | ユーザーへ軽い通知 |
| ガチャ処理失敗 | かけら消費前なら中断、消費後なら復旧対象として記録 |
| 設定保存失敗 | 保存失敗通知と再試行案内 |
| Tauri command失敗 | React側でクラッシュさせず、画面上に軽いエラー表示 |
| APIキー未設定 | MockProviderへ切替、または設定画面で案内 |

## 14. 性能・軽量性設計

### 14.1 基本方針

- 常駐時の負荷を最小限にする。
- 不要な定期処理を行わない。
- UI非表示時は描画・アニメーションを停止または軽量化する。
- RSS取得は起動時と日付変更時を基本とする。
- 大量データを一度に読み込まない。
- React再レンダリングが過剰にならないようにする。
- Rust側で重い処理を必要以上に繰り返さない。

### 14.2 UI性能

- Reactコンポーネントは責務単位で分割する。
- ゆうこの常時アニメーションは軽量なものにする。
- 一覧表示は件数が増える場合、仮想化やページングを検討する。
- 画像リソースは必要以上に大きくしない。
- 無限アニメーションや高頻度タイマーは避ける。

### 14.3 Rust側性能

- RSSやHTML取得は必要時のみ実行する。
- 保存済みニュースは必要な粒度で読み込む。
- 辞書検索は完全一致を基本とし、初期版では重い類似検索を避ける。
- AI呼び出しはキャッシュや辞書再利用で回数を抑える。

## 21. まとめ

本基本設計書では、AIニュースマスコットアプリ「ゆうこのニュース日和」をTauri構成で実装するための全体構成を定義した。

本システムは、Tauri v2をアプリ基盤とし、React / TypeScriptで画面とゆうこの見た目を構成し、Rustで業務ロジック、状態管理、通信、保存、AI連携を担当する。

初期版では、全機能を完成度高く作り込むのではなく、  
**ニュース取得 → ゆうこによる紹介 → ソフト内閲覧 → 用語解説 → 辞書保存 → 友情ランク / カスタマイズ / ガチャ**  
という体験の核を通すことを最優先とする。

次工程では、本書をもとに詳細設計書を作成し、Rustモジュール、Tauri command、Reactコンポーネント、TypeScript型、データ形式、AIプロンプト、状態遷移、テストケースを具体化する。
