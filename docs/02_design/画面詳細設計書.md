## 3. 画面共通方針

### 3.1 UI全体の基本方針
- 画面は柔らかく、親しみやすく、硬すぎない印象にする。
- 情報を詰め込みすぎず、余白を確保する。
- ゆうこはアプリ体験の中心であり、単なる装飾にしない。
- ただし、ニュース本文や設定項目の可読性を妨げない。
- 常駐アプリとして軽量に動作することを意識する。
- 過度なアニメーションや大量描画は避ける。
- React側に業務ロジックを持たせすぎない。
- 外部通信、AI呼び出し、ローカル保存はRust側で行う。
- 右列（ゆうこ・吹き出しを置く列）の幅は、ウィンドウ幅が Tailwind の `lg`（1024px）未満のとき `w-60`（240px）に狭め、中央列の幅を確保する（既定ウィンドウ 800×600 で一覧の題名や見出しが早く省略・折り返すため。判断台帳 D109）。`lg` 以上は従来幅（記事詳細・ニュース履歴・過去ニュース・ゆうこ辞書・設定は `w-72`、カスタマイズは `w-64`）。記事詳細（SCR-002）だけは `lg` 未満を `w-48`（192px）にし、ゆうこの絵も小さくする（最小幅でタイトルが5行に折り返し、右列が幅の約3分の1を取っていたため。実機テスト B8）。CSS のブレークポイントだけで切り替え、リサイズ監視の処理は持たない。ホーム（SCR-001）は別途レイアウトを見直し中のため対象外。
- 左サイドバーの「ゆうこの一言」カード（ガチャは「ゆうこのおはなし」）は、ウィンドウの高さが 740px 未満では隠し、画面ナビの8項目をスクロールせずに全部見せる（起動時の 800×600 でカスタマイズ・ガチャ・設定がスクロールしないと見えなかったため。実機テスト B8）。ニュース一覧・記事詳細・ニュース履歴・過去ニュース・ゆうこ辞書・カスタマイズ・ガチャが対象で、ホーム（SCR-001）・設定（SCR-003）は別対応。
- 画面の枠（タイトルバー・状態表示のフッター・画面ナビを含む左サイドバー）とボタン・タブの文字は、ドラッグで選択されないようにする（`app/globals.css` の `user-select: none`。実機テスト B12）。記事の本文・要約・解説・辞書の説明などの読み物と入力欄は選べるままとし、用語解説の範囲選択に影響させない。
- メインウィンドウの大きさは既定 800×600、最小サイズは幅 800・高さ 440（`src-tauri/tauri.conf.json` の `minWidth` / `minHeight`。いずれも表示領域の論理ピクセル）とする。幅: 各画面は左サイドバー（208px）と右列（240px、ホームは 256px）が固定幅のため、狭めると中央列だけが細り、幅 約 450px 未満では中央列（記事本文など）が消える。800px なら中央列は約 336〜352px を確保でき、800 は主要画面のレイアウト監査（`tests/ui/layout-audit.spec.ts`）で確認している幅でもある。高さ: 最小値はタイトルバー（約 32px）を足した外枠で画面に収まる必要がある。高 DPI の拡大表示（1366×768 の 150%、1920×1080 の 175% 等）ではタスクバーを除いた作業領域が論理 約 480px しかなく、600 では収まらず縮めることもできなくなるため、既定より低い 440 とする。中央列の見出し・本文は高さが足りない分を縦スクロールで届く（800×440 での中央列の表示・到達をレイアウト監査で確認）。設定画面（SCR-003）は、左サイドバーのヒントカードが設定メニューを押し潰さないよう、ウィンドウの高さ 560px 以下ではヒントカードを隠す（800×600 以上の見た目は変えない）。ホーム（SCR-001）は高さ約 460px 未満で記事一覧がゆうこ表示に押されて見えなくなる（ホームのレイアウト見直しで別途対応する）。解放後の作り直し（`app_lifecycle.rs` の `build_main_window`）も同じ設定から作るため、最小サイズは作り直し後も効く。常駐ゆうこウィンドウは対象外。

初期案として、以下の雰囲気を想定する。

- クリーム系
- 淡いグリーン系
- やわらかい白背景
- 角丸カード
- 強すぎない影

### 3.3 操作方針
- 主操作は大きめ・分かりやすく配置する。
- 削除やリセットなどの危険操作は、目立ちすぎない位置に置き、確認ダイアログを挟む。
- 閉じる操作はアプリ終了ではなく、原則バックグラウンド待機へ戻る。
- ウィンドウの最小化・最大化・閉じるは OS のタイトルバーだけで行う（D147）。各画面上部の `AppTitleBar` はアプリ名の表示だけとし、ウィンドウ操作ボタンを置かない（OS のタイトルバーと二重になり、押しても動かないボタンが並ぶのを避けるため）。OS の閉じるは close-to-hide でバックグラウンド待機へ戻る。
- 左サイドバーの画面ナビは、ホーム（SCR-001）と同じ項目・順序・アイコンで全画面に並べる：ホーム／ニュースを見る／ニュース履歴／過去ニュース／ゆうこ辞書／カスタマイズ／ガチャ／設定。ホーム以外の画面（ニュース一覧・記事詳細・ニュース履歴・過去ニュース・ゆうこ辞書・カスタマイズ・ガチャ）は共通部品 `AppSidebarNav`（`components/layout/AppSidebarNav.tsx`）を使い、画面ごとに項目を複製しない。その画面自身の項目を選択状態で表示し、`aria-current="page"` を付ける（記事詳細は「ニュースを見る」を選択状態とする）。ホームの項目定義は `MainScreen.tsx` 側にあるため、項目を変えるときは両方を揃える。
- 設定画面（SCR-003）の左サイドバーは設定カテゴリ一覧（§7.3）のため画面ナビは置かず、「ホームへ戻る」と「常駐を終了する」を置く。カテゴリの選択中は画面内の区分切替として `aria-current="true"` を付ける。
- サイドバーの「常駐を終了する」は、確認ダイアログ（「常駐を終了しますか？」／キャンセル・終了する）を挟んでから `quit_resident_app` で常駐ごと終了する（共通部品 `QuitResidentButton`。ニュース一覧・記事詳細・ニュース履歴・過去ニュース・ゆうこ辞書・カスタマイズ・ガチャ・設定。ホームは別対応）。失敗時は画面を保ったまま固定文言のトーストを出し、書き出し・取り込みの実行中（`MIGRATION_BUSY`）はその旨を案内する。
- ユーザーが迷わないよう、戻る導線を必ず用意する。
- 押しても処理の無いボタン（シェア・共有・ヘルプ・処理の無い「絞り込み」等）は画面に置かない。既存機能で裏付けられる場合だけ接続して出す（ニュース履歴の「過去ニュースで探す」§9.5、記事詳細の「すべての関連ワードを見る」§6.5）。各画面フッターのヘルプ「?」ボタンはヘルプ画面が無いため置かない（ホームは別対応）。
- 外部ブラウザを開く操作は、ユーザー操作を挟む。
- AI生成や保存処理は、処理中状態と失敗時表示を用意する。

### 3.4 React / TypeScript実装方針
- 画面単位で `screens/` にReactコンポーネントを分ける。
- 共通UIは `components/` に切り出す。
- モーダルやポップアップは `dialogs/` に切り出す。
- Tauri command呼び出しは `services/` に集約する。
- 型定義は `types/` に分ける。
- 画面コンポーネントにRSS取得、AI API呼び出し、ファイルI/Oを書かない。
- APIキーや秘密情報をReact側へ渡さない。
- `dangerouslySetInnerHTML` は原則使用しない。
- UI状態と永続状態を混同しない。

### 3.5 Rust / Tauri command接続方針
- 画面表示に必要なデータはTauri command経由で取得する。
- 入力値の最終検証はRust側で行う。
- ファイル保存、設定保存、辞書保存、既読更新、ポイント加算はRust側で確定する。
- React側は処理結果を表示に反映する。
- command失敗時に画面全体がクラッシュしないようにする。
- サイドバーの「自動起動：ON/OFF」表示（ホーム・ニュース一覧・記事詳細・ニュース履歴・過去ニュース・ゆうこ辞書・カスタマイズ・ガチャ）は `get_autostart_enabled` の結果（OSの登録状態）を共通部品 `AutostartStatus` で表示する。取得できない場合は表示しない。表示専用で、切替は設定画面「起動・連携」で行う。

### 3.6 記事の日時表示と「NEW」バッジ（2026-10-21 実機テスト B1・B2）
記事の日時を出す画面（ホーム・ニュース一覧・記事詳細と関連記事・ニュース履歴・過去ニュース）は、共通の純粋関数 `lib/article-date-display.mjs` で表示と判定をそろえる。

- ホーム（`MainScreen.tsx`）は担当者が差し替える予定で、2026-10-21 時点では未対応（ISO 表記と「未読なら NEW」のまま）。差し替え方は `mapTauriArticleToUi` の `timeAgo` を `formatArticleDateTime(article.publishedAtText)`、`isNew` を `isArticleNew(article)` にする。

- **日時表示**（`formatArticleDateTime`）: Rust から届く `publishedAtText` / `fetchedAt`（RFC3339・UTC保存。例 `2026-10-06T15:43:31Z`）を、端末ローカル時刻（日本の端末なら日本時間）の `YYYY/MM/DD HH:mm` で表示する（例 `2026/10/07 00:43`）。日付だけの旧データ（`2026-06-09`）は時差でずらさず `YYYY/MM/DD`。空・解釈できない値は生の文字列を出さず「日時不明」とする。
  - 「5分前」「昨日」などの相対表記にはしない。表示し続ける間に古くなり再描画用のタイマーが要る（常駐負荷を増やさない）ため。データ移行の作成日時（§7.5.1）・ゆうこ辞書の作成日時（§8.4）と同じ絶対表記にそろえる。
  - 「当日」の判定（§9b.3）と同じく端末ローカルのタイムゾーンを使う。
- **「NEW」バッジ**（`isArticleNew`）: 未読（`readState` が `unread`）で、かつ基準時刻から **24時間以内** の記事だけに付ける。基準時刻は公開日時（`publishedAtText`。日付だけの旧データは UTC 0時）、読めなければ取得日時（`fetchedAt`）。
  - 公開日時を優先するのは、取得したばかりでも数か月前に公開された記事を新着と見せないため（Rust は公開日時が無い・読めない記事の `publishedAtText` に取得日時を入れて保存する）。
  - 24時間は「新着」の目安で、おすすめの鮮度窓（72時間。おすすめ判定ポリシー）より短くする。どちらの時刻も読めない・基準時刻が24時間以上未来（時計ずれ等）のときは付けない。
  - 既読（プレビュー済み・詳細閲覧済み）は従来どおり付けない。ガチャのコレクションの「NEW」（`newItemIds`）は別の仕組みで、この規則の対象外。

# 5. SCR-001 メイン画面

## 5.1 目的
メイン画面は、本アプリのハブ画面である。  
今日のおすすめニュース、ゆうこの状態、友情ランク、各機能への導線を一画面で確認できるようにする。

## 5.2 MVPでの役割
MVPでは、以下の体験を見せる中心画面とする。

- 今日のおすすめニュースを確認する。
- ゆうこが画面内に存在する。
- ニュース閲覧画面へ遷移する。
- 辞書、履歴、設定へ移動する。
- （追加機能・実装済み）友情ランク進捗を表示する。MVP必須の通し確認には含めず、表示領域がある場合も任意とする。

## 5.3 レイアウト方針
### 基本配置
- ゆうこ本体は **画面中央下寄り** を基本位置とする。
- 左側から中央にかけてニュース一覧を配置する。
- 右側または上部に友情ランク、未読数、かけら数などの状態表示を置く。
- 下部またはサイドに主要メニュー導線を置く。

### 推奨構成
```text
上部:
  アプリ名 / 今日の日付 / 状態表示

左〜中央:
  今日のおすすめニュースカード一覧

右側:
  友情ランク
  次ランクまでの進捗
  未読数
  流れ星のかけら数
  ゆうこの一言

中央下:
  ゆうこ本体

下部:
  辞書 / 履歴 / 設定 / カスタマイズ / ガチャ導線
```

## 5.4 表示項目
| 項目 | 必須 | 備考 |
|---|---|---|
| アプリ名 | 必須 | 「ゆうこのニュース日和」 |
| 今日のおすすめニュース一覧 | 必須 | 10件前後 |
| ニュースカード | 必須 | タイトル、出典、要約、ジャンル |
| ゆうこ本体 | 必須 | 中央下寄り |
| ゆうこの一言 | 必須 | 今日のおすすめや軽い案内 |
| 友情ランク | 任意 | 追加機能（MVP必須外・実装済み。MVPでは簡易表示） |
| 次ランクまでの進捗 | 任意 | 追加機能（MVP必須外・実装済み。プログレスバー） |
| 未読数 | 任意 | MVPでは簡易 |
| 流れ星のかけら数 | 任意 | MVPではダミー可 |
| 設定導線 | 必須 | 設定画面へ |
| 辞書導線 | 必須 | ゆうこ辞書画面へ |
| 履歴導線 | 必須 | ニュース履歴画面へ |
| カスタマイズ導線 | 任意 | 後続でも可 |
| ガチャ導線 | 任意 | 後続でも可 |

## 5.5 操作項目
| 操作 | 挙動 |
|---|---|
| ニュースカードクリック | ニュース閲覧画面へ遷移 |
| 設定ボタンクリック | 設定画面へ遷移 |
| 辞書ボタンクリック | ゆうこ辞書画面へ遷移 |
| 履歴ボタンクリック | ニュース履歴画面へ遷移 |
| 閉じる | バックグラウンド待機へ戻る |
| ゆうこクリック | ゆうこの一言または簡易反応を表示 |

## 5.6 初期表示
- 起動後、ニュース取得が完了している場合はおすすめニュースを表示する。
- ニュース取得に失敗している場合は、保存済みニュースを表示する。
- ニュースが1件もない場合は、空状態メッセージを表示する。

## 5.7 状態別表示
| 状態 | 表示 |
|---|---|
| ニュースあり | おすすめニュース一覧を表示 |
| ニュースなし | 「まだニュースがないみたい」等の案内 |
| 取得中 | 読み込み表示 |

# 6. SCR-002 ニュース閲覧画面（記事詳細）

> 本画面は選択した**個別記事の詳細**を表示する画面（`NewsReaderScreen`）であり、ニュースの一覧ではない。ニュースの一覧は SCR-001 メイン画面（おすすめ）／SCR-009 ニュース一覧画面（当日取得）／SCR-005 ニュース履歴画面（全期間）が担う。

## 6.1 目的
ニュース閲覧画面は、ニュースをソフト内で読みやすく理解するための画面である。  
原文本文そのものを大量表示するのではなく、AI要約、ゆうこの再説明、要点整理、注目ポイント、用語解説を中心に表示する。

## 6.2 MVPでの役割
MVPでは、最も重要な実用画面とする。

- AI要約を読む。
- ゆうこの再説明を見る。
- 気になる用語を選択する。
- 用語解説ポップアップを表示する。
- お気に入り登録する。
- 元記事へ移動する。

  ゆうこの再説明
  要点整理
  注目ポイント

  ゆうこ本体

## 6.7 状態別表示
| 状態 | 表示 |
|---|---|
| 要約生成済み | 要約欄に表示 |
| 要約未生成（自動要約の対象外・`none`） | 「要約はまだ準備中だよ。」＋「要約を作成」ボタン（手動の `generate_article_summary`） |

## 6.8 エラー時表示
- 記事詳細の取得失敗は、エラーコードで案内を分ける（生のエラー文言・パスは出さない。Rust 側は記事IDと種別だけを WARN ログに残す）。
  - `ARTICLE_ARCHIVED`（起動時の整理などで過去ニュースのアーカイブへ移り、通常の保存先に無い）: 「この記事は過去ニュースにしまってあるよ。取り出して開く？」＋「取り出して開く」「過去ニュースを見る」「戻る」。「取り出して開く」を押したときだけ既存の `restore_archived_article`（記事IDのみ）で1記事を取り出し、記事を読み直す。取り出しに失敗したら画面に留まり、過去ニュース画面からの取り出しを案内する。
  - `NOT_FOUND_ERROR`（アーカイブ索引にも無い）: 待っても直らないため「少し待って」とは言わず、「この記事は見つからなかったよ。…」＋「ニュース一覧へ戻る」「戻る」を出す（再試行は出さない）。
  - それ以外: 従来どおり「記事詳細の取得に失敗しちゃった。少し待ってから、もう一度試してみてね。」＋「再試行」。
- AI要約失敗時は、記事自体は表示する。
- 元記事リンクが無効な場合はリンクを非活性にする。
- 元記事を開けなかった場合（保存済みURLが開けない形・ブラウザ起動失敗など）は、固定文言のトースト（「元記事を開けなかったよ」）を表示する。生のエラー文言は出さない。
- 用語解説失敗時はポップアップ内で再選択案内を表示する。

### 7.4.1 「準備中」として表示している項目（設計外・実装に合わせた扱い）
次の項目は画面に表示しているが、保存先が無い、または保存はされるが Rust 側に効果（判定処理）が無いため、誤操作防止として**非活性＋「準備中」表示**にしている。値を変更できないため、保存時に既存の保存値を上書きしない。

| 区分（画面のタブ等） | 項目 | 準備中の理由 |
|---|---|---|
| 右サイドバー「ストレージ状況」 | 使用状況の表示 | 実容量の取得には新しい command が必要なため。固定の仮値は実値と誤認されるため表示しない |

- 重複・不要な準備中項目は画面から外した（2026-10-08、判断台帳 D64 / D66 / D67）: ゆうこ表示の「常駐時のゆうこを表示する / 吹き出しの自動表示 / ゆうこの話しかけ頻度 / ゆうこのアニメーション」、解説・AI設定の「専門用語の解説レベル / AI処理の優先モード」と AI Provider の「OpenAI」、ストレージ状況の「キャッシュを削除」、抑制条件の「ゲーム実行中は通知を抑制する」（判断台帳 D70。全画面のゲームはフルスクリーン抑制の対象になる。個別判定は後で再検討しうる）。解説・AI設定の「長文要点説明の自動候補」も外した（2026-10-19、判断台帳 D144。長文の要点説明は D21 で範囲選択のフレーズ解説に統合済み）。いずれも保存DTOに対応フィールドが無い（OpenAI は Rust 側の保存値 `openai` としては引き続き読める）ため、保存形式は変わらない。

### 7.5.1 データ管理（データ移行。データ設計書 §15.6 / §15.7、判断台帳 D41）
画面は `components/settings/DataMigrationPanel.tsx`。ZIPの作成・検証・バックアップ・置き換え・フォルダの特定はすべて Rust 側で行い、画面はファイル名と結果だけを扱う（フルパスは表示しない）。

| 操作 | 挙動 |
|---|---|
| データを書き出す | `export_migration_data` を呼ぶ。実行中はボタンを「書き出し中…」にして押せなくする。成功したらファイル名と件数（ファイル数・ニュース数・アーカイブ数・合計の大きさ）を表示し、「書き出し先フォルダを開く」ボタンを出す |
| 書き出し先フォルダを開く | `open_migration_folder`（`kind: "exports"`）。Rust がアプリデータ直下の固定フォルダ `exports/` だけを開く |
| imports フォルダを開く | `open_migration_folder`（`kind: "imports"`）。移行用ZIPを置く場所を利用者に示すため常に表示する |
| 一覧を更新 | `list_migration_imports` を呼び直す。タブを開いたときにも1回読む |
| 読み込む（候補ごと） | 確認ダイアログを開く。ダイアログは「今のデータ（設定・ニュース・お気に入り・辞書・友情ランク・報酬・ガチャ・アーカイブ）がすべて置き換わる」「読み込みの前に自動でバックアップを1つ残す」「読み込みが終わったらアプリを再起動する」を示す。「置き換えて読み込む」を押したときだけ `import_migration_data` を呼ぶ（キャンセルでは何もしない） |
| 再起動する | 読み込み完了ダイアログから。`restart_app` でアプリを再起動する |
| あとで（画面だけ読み込み直す） | 読み込み完了ダイアログから。再起動はしないが、表示中の値が取り込み前のものなので画面を読み込み直す（`window.location.reload()`）。常駐処理は再起動まで前のデータに基づくことがある |

- 取り込み候補の一覧はファイル名・作成日時（manifest の `createdAt` を端末のローカル時刻で表示。読めない場合は「不明」）・大きさを出す。候補が無いときは「imports フォルダに移行用ZIPを置いてね」と、フォルダを開くボタン・一覧の更新を案内する。
- 書き出し・読み込み・一覧の読み込み・フォルダを開く・再起動は同時に1つだけ実行し、実行中はパネル内の他のボタンを押せなくする。
- 読み込み中は閉じられないダイアログ（Escape でも閉じない）で画面全体を覆い、保存・リセット・自動起動の切り替えなど他の設定操作を止める。`settings.json` の保存には書き込みロックが無いため（データ設計書 §15.7）。保存・リセット・自動起動の処理側でも読み込み中は実行しない。
- 再起動は Tauri 本体の `AppHandle::request_restart` を使う（プラグイン追加なし）。書き出し・読み込みの実行中は Rust 側が再起動を断る（`MIGRATION_BUSY`）。

### 7.5.2 アーカイブ管理（古い月のアーカイブ削除。データ設計書 §14.4 / §14.8、判断台帳 D26）
画面は `components/settings/ArchiveManagePanel.tsx`。「データ管理」タブのデータ移行の下に置く。右サイドバーの「アーカイブを管理」からも移動できる。ZIPの特定・検証・削除はすべて Rust 側で行い、画面は年月（`YYYY-MM`）だけを渡す。

| 操作 | 挙動 |
|---|---|
| 一覧表示 | タブを開いたときに `list_archive_months` を1回読む。月を新しい順に「2026年7月」「30件・3.3 MB」（容量は MB・小数1桁。0 より大きく 0.05 MB 未満のときは小数1桁だと「0.0 MB」と空に見えるため「0.1 MB未満」）と削除ボタンで表示する |
| アーカイブを読み直す | `list_archive_months` を呼び直す |
| 削除（月ごと） | `deletable: false` の月はボタンを非活性にし「最近の月はまだ削除できないよ」と添える。押せる月は `get_archive_month_delete_preview` で件数・容量を確かめ、確認ダイアログ「N件 / X MBのアーカイブが削除され、元に戻せません。」を出す（通常のニュースとして残る件数があれば併記）。「削除する」を押したときだけ `delete_archive_month` を呼ぶ（キャンセルでは何もしない） |

- 事前確認・削除・一覧の読み込みは同時に1つだけ実行し、実行中はパネル内のボタンを押せなくする。
- 削除に成功したら「2026年7月のアーカイブ（30件）を削除したよ。」と表示し、一覧を読み直す。`cleanupPending: true`（一覧からは消えたがZIPを消せなかった）も成功として扱い、表示・動作に影響しない旨を添える。
- 失敗はエラーコードだけで固定文言を出し、Rust のエラー文・パスは出さない（文言は `lib/archive-manage-display.mjs`）。`VALIDATION_ERROR`（アーカイブにしか本文が無いお気に入りを含む月など）は「この月はまだ削除できない」旨、`NOT_FOUND_ERROR` は一覧を読み直して案内する。それ以外の削除失敗は「アーカイブはそのまま残っている」と案内する（Rust 側は index 更新までの失敗で何も消さない）。
- 過去ニュース画面（SCR-011。§9c）は表示のたびに `list_archive_months` を読み直すため、削除した月は次に開いたときに一覧から消える。

## 7.6 初期表示

| 保存失敗 | エラー表示 |

## 7.8 エラー時表示
- 設定保存に失敗した場合、変更前設定を維持する。
- API接続テスト失敗時は、アプリ全体を止めずに警告を表示する。
- 設定の読み込みに失敗した場合は、固定文言のエラー表示と「再試行」を出す（生エラー文・ファイルパスは出さない）。
- 読み込み失敗が設定ファイルの破損（`get_user_settings` のエラーコード `JSON_ERROR`）の場合は、原因（設定ファイルが壊れている）と「設定を初期化する」ボタンを追加で出す。ボタンは既存のリセット確認ダイアログを開くだけで、確認後に `reset_user_settings` で初期化する。破損ファイルを自動で既定値へ置き換えることはしない（判断台帳 D28 / セキュリティ詳細設計書 §11.4）。破損時の確認ダイアログは「壊れた設定ファイルは、初期化の前に別名でコピーを1つだけ残します。」と案内し（パスは出さない）、Rust 側は初期化の前に壊れたファイルを `config/settings.corrupt.json` へ1世代だけ複製する。複製に失敗した場合は初期化せず、リセット失敗として表示する（判断台帳 D57 / データ設計書 §8.1）。通常のリセット確認の文言は変えない。初期化に成功したらエラー表示を消し、既定値で表示する。

- データ移行の失敗は固定文言だけを表示し、Rust のエラー文・パスは出さない（文言は `lib/migration-display.mjs`）。読み込みは、エラーコードだけで ZIPが検証で弾かれた（`IMPORT_ZIP_REJECTED`。現在のデータに触れる前に失敗するので「今のデータはそのまま」と案内）・選んだZIPが見つからない（`NOT_FOUND_ERROR`）・前回の読み込みが途中で止まっている（`IMPORT_INCOMPLETE_PREVIOUS`）とそれ以外を分けて案内する。フォルダを開けない場合は、Windows 以外（`OPEN_FOLDER_UNSUPPORTED`）とそれ以外を分ける。

# 8. SCR-004 ゆうこ辞書画面

## 8.1 目的
ゆうこ辞書画面は、過去に解説した単語、短いフレーズ、長文要点説明を見返すための画面である。  
AI再実行を減らし、ユーザーの知識蓄積を支援する。

## 8.2 MVPでの役割
- 解説済み項目を一覧表示する。
- 項目の詳細を見る。
- ★マークを付ける。
- 付箋メモを書く。
- 不要項目を削除する。

## 8.3 レイアウト方針
```text
上部:
  画面タイトル / 検索バー / フィルタ

左側:
  辞書項目一覧

右側:
  選択中項目の詳細
  解説本文
  メモ
  ★状態
  関連ニュース

下部:
  戻る / 削除 / 保存
```

## 8.4 表示項目
| 項目 | 必須 | 備考 |
|---|---|---|
| 検索バー | 任意 | MVPでは簡易 |
| 種別フィルタ | 任意 | term（単語）/ phrase（フレーズ）。旧「要点説明」（key_point）は D21 でフレーズに統合したため置かない（判断台帳 D144。旧データの key_point はフレーズとして表示・絞り込まれる）。絞り込みは検索バーと種別フィルタのチップで行い、別の「絞り込み」ボタンは置かない |
| 辞書項目一覧 | 必須 | 見出し語 |
| 解説内容 | 必須 | 詳細ペイン |
| 作成日時 | 重要 | 詳細ペインに表示（YYYY/MM/DD）。旧データで無い場合は「—」 |
| 参照回数 | 任意 | 詳細ペインに「N回」で表示。0・欠損（旧データ）は「—」 |

# 9b. SCR-009 ニュース一覧画面（本日取得したニュース）

## 9b.1 目的
ニュース一覧画面は、その日に**アプリが取得**したニュースを一覧で確認し、記事詳細へ進むための独立画面である（`NewsListScreen`）。ホーム（SCR-001）のおすすめ表示件数設定に縛られず、当日取得分をまとめて見られるようにする。

## 9b.2 MVPでの役割
- サイドバー「ニュースを見る」／ホーム「すべて見る」の遷移先とする。
- 当日取得したニュースを一覧表示する。
- 記事を選択して記事詳細（SCR-002）を開く。

## 9b.3 「当日取得」の判定（重要）
- 「その日にアプリが取得したニュース」を対象とし、**媒体の公開日時（`publishedAt`）では判定しない**。
- 保存時に付与される**取得日時（`fetchedAt`, RFC3339 / UTC保存）**を正として、**端末ローカル日付**の当日で抽出する。
- 端末ローカル日付を採用する理由: ニュース取得スケジューラ（`news_scheduler` の `local_today()`）および日次アーカイブ処理の日付境界が**端末ローカル日付**であり、それに合わせる（独自の日付基準を作らない）。友情ポイント・通知回数の日次リセットは UTC 日付だが、これらは上限管理用であり「取得日」の基準ではない。
- `fetchedAt` が解釈できない記事は、安全側で当日扱いにしない。

## 9b.4 レイアウト方針
- レイアウトはニュース履歴画面（SCR-005）に近い構成（左サイドバー＋中央一覧）とする。
- ただしニュース履歴画面そのものは再利用せず、目的とデータを分ける。
- 次はニュース履歴固有機能のため本画面へ持ち込まない: アーカイブ表示、履歴専用フィルタ、お気に入り絞り込み、再閲覧専用文言（「もう一度見る」等）、全期間表示。

## 9b.5 表示項目
| 項目 | 必須 | 備考 |
|---|---|---|
| 見出し | 必須 | 「本日取得したニュース」 |
| 取得基準の補足文 | 必須 | 「今日、アプリが新しく取得したニュースを表示しています。」（取得日時基準であることを明示し、公開日との誤解を避ける） |
| 当日取得件数 | 必須 | 一覧の件数を表示 |
| ニュース一覧 | 必須 | タイトル・出典・公開日・ジャンル |
| 要約状態タグ | 任意 | ニュース履歴画面（§9.4）と同じ `SummaryStateTag`（「要約待ち」/「ゆうこ要約中」/「要約失敗」） |
| 記事タグ | 任意 | ニュース履歴画面（§9.4）と同じ `ArticleTagList` で概要の下に表示のみ（絞り込みはしない）。タグの無い記事では何も出さない |
| 公開日ラベル | 必須 | カードの日付は媒体の公開日時（`publishedAtText`）を「公開日: …」と表示する。取得日時（`fetchedAt`）は当日判定に使用する。`publishedAtText` が空の場合に限り、`fetchedAt` を同じ「公開日: 」ラベルで表示する。表示形式は §3.6（`YYYY/MM/DD HH:mm`、読めなければ「日時不明」）。「NEW」も §3.6 の規則で付ける |
| 読み込み中表示 | 必須 | ローディング |
| 空状態表示 | 必須 | 「今日取得したニュースはまだないみたい」等 |
| 取得失敗表示＋再試行 | 必須 | 安全なエラー表示（本文全文・生エラー・ローカルパスを出さない） |

## 9b.6 操作項目
| 操作 | 挙動 |
|---|---|
| ニュースカード選択 | ニュース閲覧画面（記事詳細）へ。選択記事IDを渡す |
| 戻る／ホーム | メイン画面へ |
| サイドバー各項目 | 対応画面へ遷移 |

## 9b.7 表示件数・取得上限（MVP制限）
- ホームの表示件数設定（`maxDailyRecommendations`）は**適用しない**。
- データ取得は既存 `list_article_history` を `limit = 200`（`fetched_at` 降順）で呼び、当日取得分を抽出する。
- **MVP制限**: 当日取得したニュースが **200件を超える場合、超過分は表示されない**（`list_article_history` の取得上限に依存）。「当日分を必ず全件取得できる」ことは保証しない。
- 大量件数への本格対応（ページネーション・仮想スクロール・当日専用command）は今回のMVP範囲外とし、必要になった時点で検討する。既存のスクロール表示を優先する。

# 12b. SCR-010 初回起動の案内（オンボーディング）オーバーレイ

根拠: 要件定義書 §7.1.1 / §7.1.2、判断台帳 D27（初回起動時のみ・選択内容を設定として保存）/ D59（案A: 1枚のオーバーレイ）/ D60（4項目を縦に並べ「はじめる」「スキップ」、完了は設定に記録、既存の設定ファイルがあるユーザーには出さない）。

## 12b.1 表示条件
- 設定ファイルを新規作成した初回起動だけ表示する（`get_user_settings` の `onboardingCompleted === false`）。
- 既存の設定ファイルがあるユーザー（`ui.onboardingCompleted` を持たない旧形式を含む）、完了／スキップ済み、設定の読み込み失敗、ブラウザプレビュー（非Tauri）では表示しない。
- メインウィンドウ（`app/page.tsx`）にだけ重ねる。ゆうこウィンドウには出さない。

## 12b.2 レイアウト（D59 案A）
- アプリの上に重ねる1枚のダイアログ（`role="dialog"`、フォーカスはダイアログ内に閉じる）。
- 見出し「はじめまして、ゆうこだよ！」と、あとから設定画面で変えられる旨の一言。
- 次の4項目を縦に並べる。選択肢・範囲は設定画面（SCR-003）と共通（`lib/settings-options.ts` / `components/settings/TimeInput.tsx`）。
  1. 関心のあるジャンル（設定画面と同じ7種のチェックボックス）
  2. 通知を受け取る時間帯（最大2区間。午前・午後）
  3. ニックネーム（32文字以内）
  4. PC起動時の自動起動（スイッチ。初期値はオフ。ON を勧める一言を添える）
- 下部に「スキップ」「はじめる」ボタン。閉じるボタン・Esc・外側クリックでは閉じない。

## 12b.3 操作
- 「はじめる」: 読み込んだ設定に選択内容を重ね、`onboardingCompleted: true` を付けて既存の `save_user_settings` で保存する。自動起動をオンにした場合だけ、保存後に既存の `set_autostart_enabled(true)` を呼ぶ。自動起動の失敗では完了を取り消さず、設定画面から再試行できることをトーストで伝える。
- 「スキップ」: 既定値のまま `onboardingCompleted: true` だけを記録する。
- 保存される項目（「はじめる」の場合）: ジャンル（`genres` → 設定 `news.categories`）、通知の時間帯（`workTimeRanges` と、先頭区間の開始・末尾区間の終了から作る `notifyStartTime` / `notifyEndTime`）、ニックネーム（`nickname`）、完了の記録（`onboardingCompleted` → `ui.onboardingCompleted`）。自動起動は設定ファイルではなく OS の登録状態が正のため `set_autostart_enabled` で反映し、設定ファイルの `ui.autoStartOnPcBoot` はその写しとして更新される。
- 自動起動のスイッチは初期値オフのまま、すぐ下にゆうこの口調で ON を勧める一言（「ONにしておくと、PCを起動したときにゆうこがすぐ来てくれるよ」）を表示する（判断台帳 D31 / D84）。一言は `aria-describedby` でスイッチに関連付ける。
- 保存失敗時はトーストを出し、案内を閉じずに残す（もう一度「はじめる」か「スキップ」を選べる）。
- 新しい Tauri command は追加しない。

## 12b.4 見直し表示（「オンボーディングを見る」、判断台帳 D146）
- ホーム右カラムの「オンボーディングを見る」は、旧 `OnboardingScreen`（選択を保存しない別画面・Gemini 前提の文言。D146 で削除）ではなく、この案内（`components/onboarding/OnboardingOverlay.tsx`）を見直し表示（replay）で重ねる。画面遷移はせず、閉じると元の画面のまま。

- 下部ボタンは「閉じる」「保存する」。4項目は初回と同じで、見出しは「ゆうこの設定、もう一度見てみよう！」、説明文は「今の設定を表示している」旨に変える。
  - 「保存する」: 初回の「はじめる」と同じ項目を保存する。`onboardingCompleted` は常に `true` で送り、見直しによって初回扱いへ戻すことはない。自動起動は読み込み時の状態から変えたときだけ `set_autostart_enabled(ON/OFF)` で反映する。

# 13. 後続拡張画面の簡易方針

## 13.1 カスタマイズ画面
### 目的
テーマと呼び名を切り替える画面（2026-10-08 決定、判断台帳 D83）。

### 方針
- 中央にゆうこプレビューを大きく表示する。
- 左にカテゴリ、右に候補一覧を置く。
- カテゴリ（D83）:
  - テーマ: ランク報酬のテーマ2種（ランク3・ランク7。未解放はロック表示。D33 / D34）と、ガチャで獲得した色違いテーマを切り替える。適用中の値は設定 `ui.themeId`（D51）。
  - 呼び名: 解放条件なしで入力・変更できる（D37。ランク報酬ではない）。
  - 飾り・吹き出し: ゆうこの着せかえ（D155）。既定（なし・いつもの）とガチャで手に入れたものから選ぶ。
  - 口調・性格: カテゴリから外す（保留）。
- 注記: タスク qQsEaWBW の「テーマ以外は準備中」は、上記 D83 に合わせて読む（呼び名は準備中にせず使える、口調・性格は表示しない）。飾り・吹き出しは 2026-10-20 に準備中をやめた（D155）。
- 実装状況（タスク qQsEaWBW）: 実データに接続済み。
  - カテゴリの並びは「テーマ」「呼び名」「飾り」「吹き出し」。口調・性格のタブ、「現在の設定」の口調・性格の行は置かない。
  - テーマ: 既定（クリーム）→ ランク報酬テーマ（解放ランク順）→ ガチャの色違いテーマ（ガチャマスタ順）を並べる。表示に使うのは `get_reward_state`（解放状態・`activeThemeId`）と `get_gacha_state`（所持状態）。
    - 未解放の報酬テーマは「ランクNで解放」、未所持のガチャテーマは名前を「？？？」にして「ガチャで手に入るよ」と出し、どちらも押せない。
    - 選べるテーマは押した時点で `set_active_theme` で保存し、戻り値の `activeThemeId` をすぐ `<html data-theme>` に適用する（別の保存ボタンは置かない）。適用中は「使用中」表示。
    - すぐ切り替わるのはメインウィンドウだけ。常駐ゆうこウィンドウは、次の通知が届いたときに設定を読み直して新しいテーマになる（切り替えた瞬間には変わらない）。
    - 各テーマに色見本（CSS 変数の 3 色）を出す。配色が未登録のテーマ（例: 配色追加前のガチャテーマ）は点線の枠にし、選んでも配色は既定のまま「配色はじゅんび中だよ」と出す。
    - 失敗時は固定文言（「テーマを保存できなかったよ。もう一度ためしてね。」「テーマの状態を読み込めなかったよ。」「ガチャのテーマを読み込めなかったよ。」）だけを出し、生のエラー文は出さない。報酬状態を読めないときは「使用中」を出さず、切り替えもしない。
  - 模様（判断台帳 D152〜D154。カテゴリの並びは「テーマ」「模様」「呼び名」「飾り」「吹き出し」）: テーマの地にうすく敷く模様を、色テーマとは独立に選ぶ。
    - 「なし」→ 初期の模様（水玉・肉球）→ ガチャの模様（ガチャマスタ順）を3列のタイルで並べ、各タイルに今の色テーマで見本を出す（見本は小さいため濃さだけ2倍）。
    - 選べるかは `get_pattern_state` の `selectablePatternIds`（Rust で判定済み）だけで決める。未所持のガチャ模様は名前を「？？？」にして形も伏せ、押せない（「ガチャで手に入るよ」）。
    - 押した時点で `set_active_pattern` で保存し、戻り値の `activePatternId` をすぐ `<html data-pattern>` に適用する。「現在の設定」に模様の行を出す。
    - 失敗時は固定文言（「模様を保存できなかったよ。もう一度ためしてね。」「模様の状態を読み込めなかったよ。」）だけを出す。読めないときは「使用中」を出さず、切り替えもしない。
    - 模様は画面の地（サイドバー・タイトルバー・カード・吹き出しを除く部分）全体に1枚の層として敷く（列ごとに分けると境目で柄の並びがやり直しになり段差ができるため）。メインウィンドウだけで、常駐ゆうこウィンドウには敷かない。印刷・Windows ハイコントラストでは出さない。濃さ・大きさは模様ごとの推奨値で固定し、利用者が調整する UI は置かない。カードの外にある見出しや短い注記は地の上にあるため模様に薄く重なる（濃さ 19% 以下で読みやすさを保つ）。
  - 呼び名: 設定の `nickname` を読み取り専用で表示し、「設定で変える」で設定画面へ移動する（入力欄は設定画面にある）。
  - 飾り・吹き出し（判断台帳 D155）: 模様タブと同じ作りで、3列のタイルに見本を出して選ぶ。
    - 飾りは「なし」→ ガチャの飾り（ガチャマスタ順）、吹き出しは「いつもの」→ ガチャの吹き出しの順に並べる。ただし持っているもの（選べるもの）を先に、未所持（「？？？」）を後ろにまとめる（既定は先頭のまま。模様タブも同じ）。所持品が「？？？」の後ろに埋もれて探しにくかったため（実機テスト B10）。見本は、飾りなら小さなゆうこに重ねて、吹き出しなら短い文で形を見せる（いまの色テーマの色）。
    - 選べるかは `get_dressup_state` の `selectableDecoIds` / `selectableBalloonIds`（Rust で判定済み）だけで決める。未所持は名前を「？？？」にして形も伏せ、押せない（「ガチャで手に入るよ」）。
    - 押した時点で `set_active_deco` / `set_active_balloon` で保存し、戻り値をすぐ各画面のゆうこへ反映する（`components/yuuko/YuukoDressupProvider.tsx`）。中央のプレビューのゆうこに飾りが重なり、吹き出しタブでは選んだ吹き出しの見本をゆうこの頭の上に出してしっぽを頭へ向ける（ゆうこの絵を基準に置く。舞台の隅に置くとゆうこから離れて見えたため。実機テスト B10）。プレビューの舞台は左の一覧カードと高さがそろって伸び、見本の下に空白を残さない。「現在の設定」に吹き出し・飾りの行を出す。
    - 失敗時は固定文言（「飾り（吹き出し）を保存できなかったよ。もう一度ためしてね。」「飾り（吹き出し）の状態を読み込めなかったよ。」）だけを出す。読めないときは「使用中」を出さず、切り替えもしない（ゆうこは既定の見た目のまま）。
    - ゆうこの立ち絵と吹き出しは共通部品（`components/yuuko/YuukoFigure.tsx`・`YuukoBalloon.tsx`）で描く。既定（いつもの・なし）のときは各画面のもともとの形・大きさ・余白のまま。頭に乗せる飾り（王冠・シルクハット・サンタ帽）は立ち絵の上にはみ出すため、その分だけ上に余白を取る。
    - メインウィンドウ（各画面とアプリ内通知）は切り替えた時点で反映する。メイン画面（SCR-001）の差し替えは担当者が行う。
    - 吹き出しの中の閉じるボタン（×）は、形がふちを内側に描くとき（もこもこ雲の丸）はその内側へ下げ、どの形でもふちに重ねない（`app/globals.css` の `.yuuko-bb-close` と `--yuuko-bb-close-inset`。実機テスト B15）。
    - 常駐ゆうこウィンドウ（判断台帳 D156・案2）: 着せかえの command は許可せず、Rust がゆうこ通知のデータ（イベント・マウント時の状態取得）にその時点で有効な吹き出し・飾りの ID を載せて渡す。切り替えた瞬間には変わらず、次の通知から新しい着せかえで出る（テーマと同じ）。ページは既知の ID か確かめてから共通部品で描き、無い・未知なら既定（いつもの・なし）。吹き出しのしっぽは従来どおり描かない。ゲームの窓の白文字・動きを抑える設定（▼の点滅を止める）・Windows ハイコントラスト（輪郭を足す）はメインと同じ。
    - 常駐ゆうこウィンドウの大きさ: 着せかえを付けているとき（既定以外の吹き出し・飾りのどちらか）だけ、Rust が高さを吹き出し段階 +20px（196→216）・軽量プレビュー段階 +26px（298→324）にする。頭の上へはみ出す飾り（最大で立ち絵の上に約 12px）と、ふち・余白が厚い吹き出し（ゲームの窓・もこもこ雲、プレビューでは罫線に合わせて行が広がるノート）が上で切れないようにするため。既定のときは今までの大きさのまま（透明部分がクリックを奪う範囲を広げない）。全部の吹き出し×はみ出しが最大の飾り（サンタ帽）で長文でも収まることを `tests/ui/yuuko-window.spec.ts` で確認している。
    - 常駐ゆうこウィンドウの長い吹き出し文言: 大きさは上の固定値のまま、文言の行数を抑えて末尾を「…」で省略する（ニュースは3行、OK の付く報酬通知・一言は2行まで）。3行＋OK だと吹き出しの上端がウィンドウの上で切れるため。全文は DOM に残って読み上げられ、`title` でも読める。詳細は「ゆうこ登場・通知挙動 詳細設計書」§9.3。
  - 「解放済みアイテム」には、解放済みの報酬テーマと所持済みのガチャテーマを色見本と名前で並べる。
  - 報酬テーマ「そらいろ」「さくら」の配色は 2026-10-09 承認済み（判断台帳 D96）。

## 13.2 ガチャ画面
### 目的
流れ星のかけらを使って、ひとことカードやテーマなどを獲得する画面（2026-10-08 決定、判断台帳 D72〜D81）。

### 方針
- 所持かけら数を上部表示。
- 中央にガチャ実行ボタン（1回引く・1個もらえる）とゆうこを配置。
- 結果はモーダルで表示（獲得したものの名前と種類。カードは文面も見せる）。模様・飾り・吹き出しは名前だけでは分からないため見本も出す（飾りは小さなゆうこに重ね、吹き出しは短い文で形を見せる。D155）。引いただけでは適用せず、カスタマイズ画面で切り替える。
- 「コレクション」欄（D80）: 獲得済みのものを並べ、未所持は「？」で表示する。残り数（例: 残り 38 / 43）を出す。カードは選ぶと文面を読める。
- 状態別表示:
  - かけら不足: 実行ボタンを無効にする。
  - コンプリート: すべて所持したら「コンプリート」と表示し、実行ボタンを無効にする（D76）。
- まわしたときは、ゆうこが3回跳ねる短い演出（約0.9秒・CSS の transform だけ）の後に結果モーダルを出す（結果がすぐ出て「まわした」感じが無かったため。実機テスト B16）。要件（演出は控えめに）と常駐負荷に合わせ、これ以上の演出（カプセルの排出・効果音など）は置かない。動きを抑える設定（prefers-reduced-motion）では跳ねず、待たずに結果を出す。抽選そのものは Rust が行い、演出は表示を遅らせるだけ。演出中に別画面へ移った場合（かけらは消費済み）は、結果を画面モジュール内に1件だけ預け、次にガチャ画面を開いたときに「前回のガチャの結果」として同じ結果モーダルで出す（`app/page.tsx` に state を足さないため。過去ニュース画面の戻り先の記憶と同じ作り）。アプリを終了した場合は出せないが、獲得したものはコレクションに NEW 付きで残る。
- 10連・レアリティ表示は置かない（D72）。購入（課金）導線も置かない（仮の設計判断〔判断台帳外・2026-10-08〕）。重複は発生しないため、重複表示も置かない（D76）。

# 18. まとめ
本書では、Tauri版MVPで必要となる主要画面の詳細仕様を定義した。

MVPで最も重要な画面体験は以下である。

```text
メイン画面
  ↓
ニュース閲覧画面
  ↓
用語解説ポップアップ
  ↓
ゆうこ辞書
```

これに加えて、ゆうこ通知、ニュース軽量プレビュー、ランクアップ通知を組み合わせることで、  
**ゆうこがニュースを届け、AIが読みやすくし、難しい用語をその場で解説する**  
という本アプリの中心体験を実現する。

Tauri版では、React / TypeScriptが画面表示とユーザー操作を担当し、Rust側が外部通信、AI連携、保存、状態更新を担当する。  
画面実装時は、React側に業務ロジックを持たせすぎず、Tauri commandを通じて安全にRust側処理へ接続することを基本とする。
