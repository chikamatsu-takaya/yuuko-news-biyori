# ローカルLLMモデルの初回ダウンロード 設計案

作成日: 2026-11-16 ／ Firestore タスク mPGhDTi2ThHLsEWDGLIY ／ 状態: **設計案（未決定・未実装）**

- 背景: 評価資料（`docs/00_project/要約の機械点検の評価_2026-10.md` §23）で、Gemma 4 E2B（Q4_K_M・3,106,738,272 B）は要約の誤り（作り話＋取り違え）が今の Qwen3.5-2B より大きく減った（3 回の計で 49.5 件 → 9.5 件。作り話だけでは差があるとは言えない）。ただし同梱物の合計が約 3.15GB になり、MSI・NSIS のおおむね 2GB の上限（`docs/01_setup/ローカルLLM同梱配布手順.md` §4。インストーラーを作って確かめてはいない）を超える見込み。
- 藤井さんの判断（2026-11-16）: 回避策は「A. 初回起動でダウンロード」で進める。インストーラーにはアプリだけを入れ、初めて起動したときにモデルを取得してハッシュで確かめる（D101 の将来案）。
- **モデルを Gemma に替えるかどうかは、まだ決まっていない。** 本書の設計は特定のモデルに依存させず、今の 2B のままでも、将来ほかのモデルへ差し替えるときにも使える形にする。
- 本書は設計案だけ。コード・許可リスト・設定・capabilities は変えていない。

## 0. 結論と要判断の一覧

### 0.1 設計の要点（案）

1. 実行の部品（`llama-server.exe` と DLL・約 44MB）はこれまでどおりインストーラーに入れ、**モデル（GGUF）だけを初回に取得する**。実行ファイルをネットから取らないため、改ざんされた実行ファイルを起動する道を増やさない。
2. 取得先の URL・ファイルの大きさ・SHA-256 は **コードに固定する**（モデルの表 `ModelSpec`）。利用者・画面・設定ファイルから URL を受け取る command は作らない。許可リスト（`network_allowlist.json`）との関係は要判断 Q2。今は外部の相手（Gemini を含む）はすべて許可リストを通しているため、許可リストを通さない案（Q2 の A）は **外部通信で初めての例外** になり、セキュリティ詳細設計書 §6.2・§6.3 の改訂と判断台帳への記録が要る。
3. 置き場所は `%LOCALAPPDATA%\<アプリの識別子>\local_llm\models\<モデルの版>\`。途中のファイル（`.part`）に書き、大きさと SHA-256 が合ってから名前を変えて完成とする。途中で切れたら `Range` で続きから取り直す。
4. 取得は Rust の別スレッドで行い、React は進み具合を表示してボタンを押すだけ。取得中もニュースの取得・閲覧・辞書など AI 以外の機能はそのまま使える。ローカル AI の機能は、今のエラー処理の方針（黙って Mock へ切り替えない。D104・セキュリティ詳細設計書 §6.5）に合わせて「準備中」の固定の失敗を返す。
5. 実装は 5 つの PR に分ける（モデルの表と置き場所の分離 → 取得の部品 → 取得の制御と command → 画面 → 配布物の変更）。モデルを Gemma に替える作業は、本書の作業と別の PR・別の判断にする。

## 1. 今の仕組みのまとめ

確かめたファイル: `src-tauri/src/infra/local_llm_runtime.rs`・`src-tauri/src/services/local_llm_service.rs`（`verified_bundle` / `is_bundle_present`）・`src-tauri/src/lib.rs`（起動時の組み立て）・`scripts/local-llm/check-bundle.mjs`・`src-tauri/tauri.conf.json`（`bundle`）。

### 1.1 同梱

- 同梱物は `src-tauri/resources/local_llm/` に置き（git 外）、`tauri.conf.json` の `bundle.resources`（`"resources/local_llm": "local_llm"`）でインストーラーへ入る。インストール先では `resource_dir/local_llm/` にある。
- 中身は `runtime/`（`llama-server.exe`・DLL・VC++ ランタイム。表は `RUNTIME_FILES` と `VC_RUNTIME_FILES`）と `models/stario-qwen3.5-2b-q4_k_m.gguf`（`MODEL_FILE`・`MODEL_SIZE`＝1,312,164,800 B・`MODEL_SHA256`）。合計約 1.36GB。
- `pnpm tauri build` のとき、インストーラーを作る直前に `scripts/local-llm/check-bundle.mjs`（`beforeBundleCommand`）が同じ表と照合し、欠け・不一致があれば作成を止める。

### 1.2 置き場所の決め方（`resolve_bundle_dir`）

- `resolve_bundle_dir(resource_dir)` が `resource_dir/local_llm` を返す。debug ビルドだけは、そこに実行ファイルが無ければ `src-tauri/resources/local_llm` を使う。
- アプリ起動時（`lib.rs` の `setup`）に 1 度だけ呼ばれ、`LocalLlmService::new(bundle_dir)` に渡される。ここでは起動しない（遅延起動）。
- `LocalLlmBundle::in_dir(dir)` が、`<dir>/runtime/llama-server(.exe)` と `<dir>/models/<MODEL_FILE>` を **同じフォルダの下から** 組み立てる。関数の説明には「将来『初回にダウンロード』へ替える場合も、この関数の返す場所を差し替えるだけで済む（D101）」とある。ただし実際には、実行の部品（インストール先）とモデル（取得先）が別のフォルダになるため、**`LocalLlmBundle` を「実行の部品の場所」と「モデルの場所」に分ける変更が要る**（§2.3）。

### 1.3 照合

- `is_bundle_present`（自動要約の可否の安い確認）: 実行ファイルの有無と、モデルの大きさだけを見る。照合で壊れていると分かった後は false。
- `verified_bundle`（初めて生成・接続テストするとき）:
  - 実行ファイルが無い → `Missing`。モデルの大きさが違う → `Broken`、無い → `Missing`（毎回）。
  - 実行の部品の SHA-256 と、モデルの SHA-256 は、アプリ起動中に 1 度だけ。合えば `verified` を覚える。不一致は `Broken`、壊れていたことは `found_broken` で覚え、自動要約を空振りさせない。
- 大きさと SHA-256 の期待値は `LocalLlmConfig` の `model_size` / `model_sha256` / `runtime_files` から読む（定数を直接は読まない）。そのため、モデルの表を差し替えても照合の処理そのものは変えずに済む。
- 失敗は `LocalAiFailure`（`Missing` / `Broken` / `StartFailed` / `Timeout` / `RequestFailed`）で返し、設定画面は固定の文言（例「ローカルAIの部品が見つかりません」）を出す（`components/screens/SettingsScreen.tsx` の `localAiConnectionMessage`）。

### 1.4 今の外部通信の仕組み（取得に関係するところ）

- RSS・記事 HTML・Gemini は `reqwest`（`blocking`・`rustls-tls`）で取る。取得先は `url_guard::validate_url` が許可リスト（`NetworkAllowlist`。deny-by-default）と危険なスキーム・IP の拒否帯で確かめる。
- 同梱ローカルLLM への接続は例外で、許可リストに足さず、`url_guard::local_llm_url` がホスト・スキーム・経路を固定して組み立てる（D102。セキュリティ詳細設計書 §6.3）。
- 応答本文は受信の上限付きで読む（`http_body`）。
- SHA-256 は `sha2`（既存の依存）。

## 2. 初回ダウンロードの流れ

### 2.1 全体の流れ

```
アプリ起動
  └ モデルの表（ModelSpec）から、使うモデルを決める
      ├ 取得済みのファイルがある（大きさが合う） → 使える（SHA-256 は今までどおり、初めて使うときに1度）
      └ 無い
          ├ 同意済み（Q5） → 起動から少し待って（例: 60 秒）取得を始める
          └ 未同意 → メイン画面に案内を出す（Q6）。「ダウンロードする」で始める

取得
  1. 空き容量を確かめる
  2. 途中のファイル（.part）があれば、その続きから取る（Range）
  3. 受け取りながら .part に書く（大きさの上限を超えたら止める）
  4. 全部そろったら SHA-256 を確かめる
  5. 合えば名前を変えて完成 → 「使えます」
     合わなければ .part を消して 1 回だけ最初から取り直す → それでも合わなければ失敗
```

### 2.2 取得元とモデルの表

- モデルごとに次の値をコードの表（例 `ModelSpec`）に持つ。今の `MODEL_FILE` / `MODEL_SIZE` / `MODEL_SHA256` をこの表の 1 行にまとめる形。
  - `id`: 版の名前（例 `qwen3.5-2b-q4km-5405508f`。ファイル名と SHA-256 の先頭から作る）。置き場所のフォルダ名にも使う。
  - `file_name`・`size`・`sha256`。
  - `sources`: 取得元の一覧（ホスト名と経路を分けて持つ。順に試す）。
  - `display_name`（画面用。例「標準モデル」。モデルの名前を画面に出すかは画面の案で決める）。
- 使うモデルは表の 1 行（今は 1 つ）。どの行を使うかは、ビルドに入れた定数で決め、設定ファイル・画面からは選ばせない（任意のモデルを取得させない）。
- 例（Q1 で A を選び、Gemma にした場合）: 取得元は `huggingface.co` の `unsloth/gemma-4-E2B-it-GGUF` の `gemma-4-E2B-it-Q4_K_M.gguf`（3,106,738,272 B・SHA-256 `740185b2…34b8`。`docs/00_project/ローカルLLMモデル比較の試作評価_2026-10.md` の表の値）。URL の形（`/resolve/<コミット>/<ファイル名>` で版を固定できるか）、転送先のホスト、利用条件は **未確認**。
- 取得元が変わっても、SHA-256 が合わなければ使わないため、中身の正しさはハッシュで守る。

### 2.3 置き場所

| 候補 | 内容 | 判断 |
|---|---|---|
| `%LOCALAPPDATA%\<識別子>\local_llm\models\<id>\` | Tauri の `app_local_data_dir()`。そのパソコンだけのデータ | **推奨** |
| `%APPDATA%\<識別子>\...`（今の `app_data_dir`） | 利用者のデータ（設定・記事・辞書）の置き場 | 使わない。ドメイン環境では移動プロファイル（Roaming）で同期されることがあり、3GB を同期させたくない。データの移行・退避の対象とも分けておきたい |
| インストール先（`resource_dir`） | アプリのフォルダ | 使わない。更新・アンインストールで消える。全員向けにインストールした場合は書き込めない |

- `<識別子>` は `tauri.conf.json` の `identifier`（`jp.star-system.yuuko-news`）。実際のパスは実装時に `app_local_data_dir()` の値で確かめる（**未確認**）。
- 置き場所の決め方（案）:
  - `resolve_runtime_dir(resource_dir)`: 今の `resolve_bundle_dir` の役目のうち、実行の部品の場所だけを決める（debug の代わりの場所も今と同じ）。
  - `resolve_model_path(spec, local_data_dir, resource_dir)`: ①取得したファイル（`<local_data_dir>/local_llm/models/<id>/<file_name>`）、②（Q3 で B を選んだ場合や開発中）同梱のファイル、の順で探す。debug ビルドでは、今と同じく `src-tauri/resources/local_llm/models/` も見る（開発者が取得せずに使えるように）。
   - 注意（Q3 で B を選ぶ場合）: `LocalLlmConfig` は照合の期待値（`model_size` / `model_sha256`）を **1 組しか持てない**。同梱の 2B と取得したモデルを切り替えるには、「ファイルの場所とモデルの表の行（大きさ・SHA-256）を必ず組で切り替える」仕組みを足すか、「取得が終わったら、次にアプリを起動し直したときに切り替える」形にする。場所だけを替えると、別のモデルの期待値で照合して `Broken` になる。
  - `LocalLlmBundle` は `exe`（実行の部品の場所から）と `model`（上の結果）を別々に受け取る形にする。
- `LocalLlmService` が起動時に受け取るのは「実行の部品のフォルダ」と「モデルの完成ファイルのパス（まだ無くてよい）」。パスは決まっていてファイルが後からできる形にすれば、取得の後にアプリを起動し直さなくても使える（取得の完了時に `found_broken` を下ろし、`verified` をどう扱うかは §3.2）。

### 2.4 途中で切れたときの再開とやり直し

- 途中のファイル: `<id>\<file_name>.part`。横に小さな記録 `<file_name>.part.json`（`id`・期待する大きさ・取得元の `ETag` か `Last-Modified`）を置く。記録は既存の `atomic_file::write_json_atomic` で書く。
- 記録に残すのは `id`・期待する大きさ・`ETag` などだけ。**転送先の署名付き URL（問い合わせの部分に署名や期限が付く URL）は記録しない**（期限切れになるうえ、ログ・ファイルに残したくない）。再開のときは、いつも表の取得元から取り直し、転送も毎回確かめ直す。
- `.part` がすでに全体の大きさ（`size`）に達していれば、取りに行かずに SHA-256 の照合へ進む（全部そろっているのに `Range` を送ると `416` が返り、3GB を取り直すことになるため）。
- 再開: `.part` の大きさを N（N は全体より小さい）として、`Range: bytes=N-` と `If-Range: <ETag>` を付けて取る。
  - `206` で `Content-Range` の始まりが N なら、続きに書き足す。
  - `200` が返ったら（取得元が途中からを受け付けない・中身が変わった）、`.part` を空にして最初から書く。
  - `416`（範囲が合わない）・`Content-Range` の始まりが N でない・記録の `id` が今のモデルと違う → `.part` を消して最初から。
  - 別の案: `If-Range` を付けず、途中で中身が変わった場合の見つけ方を最後の SHA-256 の照合に任せる。`ETag` が転送先で変わる・付かない取得元でも続きから取れる。その代わり、中身が変わっていたときは全部取ってから不一致で分かり、丸ごと取り直しになる。どちらにするかは、取得元の `ETag` の動き（**未確認**）を見て実装時に決める。
- 大きさの確かめ方: 応答の `Content-Length` が、`200` なら全体の大きさ（`size`）、`206` なら全体から N を引いた大きさと合うことを確かめる。合わなければ始めない。受け取った合計が期待する大きさ（`size`）を 1 バイトでも超えたら、その場で止めて `.part` を消す（大きすぎる応答でディスクを埋めない）。
- 電源が落ちるなどして `.part` の末尾に書きかけのゴミが残った場合は、続きから取ってもそのまま残る。最後の SHA-256 の不一致で見つかり、丸ごと取り直しになる（下の「不一致」）。
- SHA-256: 最初から取るときは、受け取りながら計算する。再開したときは、既存の `.part` を読み直してから続きを足す（ハッシュの途中の状態は保存しない。3GB の読み直しは release で数秒の見込みだが **未計測**）。
- 不一致: 大きさが合って SHA-256 が合わない → `.part` を消し、自動で 1 回だけ最初から取り直す。2 回目も合わなければ「失敗（中身が合わない）」にして止め、利用者の「やり直す」を待つ（同じ取得元から壊れたものを取り続けない）。取得元が複数あるとき（Q1 で C）は次の取得元へ移る。
- 自動のやり直し（通信の失敗・時間切れ）: 1 分 → 5 分 → 30 分と間をあけて、アプリの起動中に最大 3 回。それでも失敗したら止め、利用者の「やり直す」を待つ。待つ間は、決まった時刻に 1 回起きるだけにし、常時の見張りはしない。
- 時間切れ: 接続は 30 秒。本文は「一定の時間（例: 60 秒）何も届かなければ切る」形にする。`reqwest` の `blocking` のクライアントには **既定で 30 秒の時間切れがある**ため、取得用のクライアントでは `timeout(None)` を明示して全体の時間切れを外す（明示しないと、3GB の取得が 30 秒で切れる）。そのうえで、読み取りごとの時間切れを付けられるかは **未確認**（§8）。付けられない場合は、読み取りのたびに経過を見て止める。
- アプリの終了: 終了の要求で読み取りの繰り返しを抜け、`.part` と記録を残す（次の起動で続きから）。

### 2.5 空き容量の確認と一時ファイル

- 始める前に、置き場所のドライブの空きが「残りの大きさ＋余裕（例: 1GB）」以上あるかを確かめる。足りなければ始めずに「空き容量が足りません（あと約 ○GB 必要です）」を出す。
- 空きの調べ方: Windows の `GetDiskFreeSpaceExW` を使う。既存の `windows-sys`（0.61）に feature を 1 つ足す見込み（feature 名は **未確認**。新しいクレートは増えない見込み）。
- 書いている途中でディスクがいっぱいになった（書き込みの失敗） → 止めて「空き容量が足りません」にする。`.part` は残し、空けた後に続きから取れるようにする。
- 一時ファイルは置き場所のフォルダの中だけに作る（`%TEMP%` は使わない。完成時の名前の変更を同じドライブの中で済ませるため）。
- 片付け: 起動時に、`local_llm\models\` の中で、今のモデルの表に無い `id` のフォルダと、記録の無い `.part` を消す（消すのは本アプリが作った名前の形に合うものだけ。§5.2）。

### 2.6 失敗やオフラインのときの代わりの動き

今のエラー処理の方針（AGENTS.md §8「失敗時は安全側へ倒す。一部機能の失敗でアプリ全体を落とさない」、D104、セキュリティ詳細設計書 §6.5「同梱ローカルLLMは黙って Mock / Gemini へ切り替えず、固定の失敗として返す」）に合わせる。

| 状況 | AI の動き（Provider が「ローカル」のとき） | 画面 |
|---|---|---|
| 取得していない・取得中・失敗 | 手動の要約・用語解説・接続テストは、新しい固定の失敗 `NotReady`（例: `LocalAiFailure::NotReady`。`error.rs` の固定コードは例 `LOCAL_AI_NOT_READY`）を返す。Mock・Gemini へ黙って切り替えない（Q9） | 「ローカルAIの準備がまだ終わっていません」＋取得の状態への案内 |
| 同上 | 自動要約は動かさない（今の `is_bundle_present` が false になる）。このとき `AutoSummaryQueue::enqueue_unsummarized` は待機列を空にする（`allowed` が偽のとき `clear_pending`）。そのため **取得が終わって使えるようになったら、取得の制御から `enqueue_unsummarized` を呼んで並べ直す**（§7.1 の PR 3） | 自動要約の状態の表示は、既存の `AutoSummaryStatusKind::LocalAiNotReady`（今は「同梱物が無い・壊れている」の意味）と取り違えないよう、取得前・取得中を分ける種類を足すか、文言を見直す（§7.1 の PR 3・4） |
| オフライン | 取得を始めても通信の失敗になり、§2.4 の間隔でやり直す。3 回で止める | 「インターネットにつながっていないため、ダウンロードできませんでした。つながってから［もう一度試す］を押してください」 |
| 取得済みのファイルが壊れていた（SHA-256 が合わない） | 今と同じく `Broken`。ただし取得したファイルなら、案内から取り直せるようにする | 「ローカルAIのモデルが壊れています。［取り直す］」 |
| Provider が Gemini / Mock | 影響なし | 設定画面のローカルの欄にだけ状態を出す |

- 失敗の種類は Rust の固定の分類で返し、画面の文言は React が決める（今の `local_ai_missing` などと同じ形）。URL・パス・HTTP の本文は画面へ返さない。
- 2B を残す案（Q3 の B）を選んだ場合だけ、「取得が終わるまで同梱の 2B で動く」が代わりの動きになる。

### 2.7 取得中もほかの機能が使えること

- 取得は Rust の専用のスレッド（1 本だけ）で行い、Tauri command の処理（`async` の実行器）を止めない。command は「始める」「止める」「状態を見る」をすぐ返す。
- ニュースの取得・閲覧・辞書・アーカイブ・ゆうこの通知など、AI 以外の機能はそのまま使える。
- 同じ回線を使う RSS 取得とは同時に走りうる。RSS 取得は小さいので、取得を止めるほどではない見込み（**未計測**）。

## 3. セキュリティ

### 3.1 許可リスト方式との関係

- 取得先は **コードに固定した専用の経路** とし、許可リスト（`network_allowlist.json`）で取得先を広げられないようにする（Q2 の A・C 共通）。Q2 で C を選んだ場合は、許可リストで「止める」ことだけを選べる。
  - 注意: D102 の例外は、パソコンの外へ出ない `127.0.0.1` だけが対象で、外部の相手は Gemini も含めてすべて許可リストを通している。許可リストを通らずに外へ出る経路を作るのは **初めての例外** で、許可リスト方式（セキュリティ詳細設計書 §6.2）の方針を緩める判断にあたる。実装の前に、同 §6.2・§6.3 の改訂と判断台帳への記録が要る。
  - 取得先の URL は `url_guard` に新しく作る組み立て関数（例 `model_download_url(source)`）だけが作る。ホスト・スキーム（`https` のみ）・経路はモデルの表の定数から組み立て、文字列の URL を外から受け取らない。
  - `UrlPurpose` には足さない。RSS・記事・外部 AI の経路で、許可リストに取得元のホストを書いても、それでモデルの取得先が広がることはない（逆も同じ）。
- **任意の URL を取得できる command は作らない。** command は「今のモデルの表の 1 行を取る」ことしかできず、引数に URL・パス・ハッシュを取らない。
- 転送（リダイレクト）: Hugging Face などは配信用の別のホストへ転送することがある（どのホストかは **未確認**）。自動では従わず（`redirect::Policy::none()`）、1 回ずつ次を確かめてから自分で次へ進む。
  - スキームが `https` であること。
  - ホストが、そのモデルの表に固定した「転送を許すホストの一覧」に入っていること（ホスト名の完全一致。親ドメインの一括許可はしない）。
  - DNS で引いた先の IP が、RSS・記事取得と同じ拒否帯（`is_disallowed_ip_addr`）に入らないこと。確かめた IP へ `resolve_to_addrs` で接続先を固定する（`html_fetcher` / `rss_client` と同じ。確かめた後に DNS の答えを変えて内側のアドレスへつながせる攻撃〔DNS rebinding〕への対策）。プロキシを通す場合は、接続するのはプロキシで、IP の確かめ方が変わる（§8 の 10）。
  - 転送は最大 5 回まで。
- 認証情報（Cookie・トークン）は送らない。取得元の利用に認証が要る（例: 利用条件への同意が要る置き場）場合は、その取得元を使わない。
- ログには、固定の分類・経過時間・受け取った大きさだけを残す。URL の問い合わせの部分（転送先に付く署名など）はログ・画面に出さない。

### 3.2 改ざんへの対策

- 大きさと SHA-256 をコードに固定し、取得の直後に照合する。合わないものは完成ファイルにしない（`.part` のまま消す）。
- 取得の後も、今と同じく「大きさは毎回、SHA-256 はアプリ起動中に 1 度」照合してから `llama-server` を起動する。
- **照合の後のすり替えへの対策が要る**: SHA-256 の照合は起動中に 1 度だけのため、照合した後に、同じ大きさの別のファイルへすり替えられると、次に `llama-server` を起動したときにそのまま読み込まれる（大きさしか見ないため）。GGUF の読み込み（解析）には、過去に脆弱性が報告されている。置き場所を利用者が書ける `%LOCALAPPDATA%` へ移すと（§3.3）、この道を使える相手が増える。
  - 対策の案（推奨）: 照合するときに、モデルのファイルを **書き込み・削除を拒む共有モード**（Windows の共有モードで読み取りだけを許す）で開き、その取っ手をアプリの終了まで持ち続ける。持っている間は、ほかのプログラムが書き換え・削除・名前の変更をできない。`llama-server` は読み取りで開くので妨げない見込み（**未確認**。mmap での読み込みが共有モードと合うかを実装時に確かめる）。
  - 持ち続けられない場合の案: `llama-server` を起動するたびに SHA-256 を照合し直す。2 分使わないと止まるため、起動のたびに 3GB を読み直す負荷がかかる（release で数秒、キャッシュに無ければさらに長い。**未計測**）。
  - 取得の直後に確かめた SHA-256 で `verified` 扱いにするかも、上の取っ手を持つ形にするなら同じ扱いにできる（取っ手を持ったまま名前を変えて完成にする）。
- 通信は TLS（`rustls`）で、証明書の確認を切らない。ハッシュを固定しているため、仮に取得元が乗っ取られても、違う中身は使われない。
- 実行の部品はネットから取らない（Q4 の推奨 A）。取るのはモデル（データのファイル）だけ。

### 3.3 置き場所の権限

- `%LOCALAPPDATA%` の下は、その利用者が書ける場所で、同じ利用者で動くどのプログラムでも書き換えられる。
- **MSI で入れた場合は、今より守りが弱くなる**。`bundle.targets` は `"all"` で MSI も配っており、MSI は既定で Program Files に入るため、今のモデルは管理者しか書き換えられない。モデルを `%LOCALAPPDATA%` へ移すと、管理者でないプログラムでも書き換えられるようになる。NSIS（既定で利用者ごとのインストール）で入れた場合は、今もインストール先を利用者が書けるため、差は小さい。
- この弱まりは、照合（§3.2）と、照合した後のすり替えへの対策（§3.2 の共有モードで開き続ける案）で補う。
- フォルダを作るときに特別な権限の変更（ACL の変更）はしない（設定・セキュリティ設定を変えない方針）。
- 取得したファイルを実行しない。`llama-server` には `-m <パス>` で渡すだけ。

### 3.4 capabilities・CSP・Tauri command

- **CSP**: 取得は Rust だけが行い、画面（WebView）は外へ通信しない。`connect-src` は変えない。
- **capabilities**: `default.json` は変えない（新しい command は `main-window-commands` の権限セットに入れるだけ）。進み具合の通知（イベント）を画面が受け取るのは `core:default` の範囲で、新しい権限は要らない見込み。常駐ゆうこウィンドウ（`yuuko-window.json`）には何も足さない。
- **新しい Tauri command（案）**: いずれも引数に URL・パス・ハッシュを取らない。

| command | 何をするか | 許可するウィンドウ | `main-window.toml` へ足す名前 |
|---|---|---|---|
| `get_local_model_status` | 状態（未取得・取得中〔受け取った大きさ・全体〕・確認中・使える・一時停止・失敗〔固定の分類〕）と、全体の大きさ、空き容量が足りるかを返す | メインだけ | `allow-get-local-model-status` |
| `start_local_model_download` | 取得を始める（同意の記録を兼ねる）。止まっていれば続きから、失敗していればやり直す。走っていれば何もしない | メインだけ | `allow-start-local-model-download` |
| `pause_local_model_download` | 一時停止する（`.part` を残す） | メインだけ | `allow-pause-local-model-download` |
| `discard_local_model` | 途中のファイル、または取得したモデルを消す（Q10 の C。消せるのは本アプリの置き場所の中で、今のモデルの表の名前に合うものだけ）。順番: 取得中なら先に取得を止める → `llama-server` が動いていれば止める → §3.2 の取っ手を閉じる → 消す → `verified` を下ろす（消した後に古い照合の結果で起動しないため） | メインだけ | `allow-discard-local-model` |

- 追加の手順はセキュリティ詳細設計書 §5.6.1 のとおり（`lib.rs` の `generate_handler!`・`command_manifest.rs` の `APP_COMMANDS`・`permissions/main-window.toml` の `main-window-commands`）。`command_permissions_tests` で漏れを検出する。
- 進み具合は Rust からメイン画面だけへイベント（例 `local-model-download-progress`）で送る（既存の `emit_to(MAIN_WINDOW_LABEL, …)` と同じ形）。送るのは状態と数（バイト数）だけで、1 秒に 1 回か 1% ごとまでに間引く。
- 同意の記録（Q5）を設定に持つなら、データ設計書の設定の項目に足す（例: `localModel.downloadConsentAt`）。

## 4. 画面の案

React は表示とボタンだけを持ち、取得・確認・保存はすべて Rust が行う。表示するのは `get_local_model_status` とイベントの値だけ。

### 4.1 メイン画面の案内（Q6 の A）

- 出す条件: Provider が「ローカル」で、モデルが「使える」になっていないとき。閉じたら、その起動中は出さない（状態は設定画面でいつでも見られる）。
- 文言の例:

| 状態 | 文言（例） | ボタン |
|---|---|---|
| 未取得（未同意） | 「ゆうこのAI（ローカルAI）を使うには、AIのモデルをダウンロードします（約 3.1GB）。ダウンロード中もニュースは読めます。」 | ［ダウンロードする］［あとで］ |
| 取得中 | 「AIのモデルをダウンロードしています… 1.2GB / 3.1GB（39%）」 | ［一時停止］ |
| 確認中 | 「ダウンロードしたモデルを確かめています…」 | なし |
| 一時停止 | 「ダウンロードを一時停止しています（1.2GB / 3.1GB）。」 | ［再開する］ |
| 使える | 「ローカルAIの準備ができました。」（数秒で消える） | なし |
| 失敗（通信） | 「インターネットにつながらないため、ダウンロードできませんでした。」 | ［もう一度試す］ |
| 失敗（空き容量） | 「ディスクの空きが足りません。あと約 2.0GB 空けてから、もう一度試してください。」 | ［もう一度試す］ |
| 失敗（中身が合わない） | 「ダウンロードしたモデルを確かめられませんでした。もう一度ダウンロードしてください。」 | ［もう一度試す］ |

- 大きさは Rust から受け取った数を画面で GB に直して出す（モデルの表の値。画面に固定で書かない）。
- 残り時間は、速さが安定しないため最初の版では出さない（出す場合は「残り約 ○分」を直近 30 秒の速さから計算し、10 秒より細かく更新しない）。

### 4.2 設定画面

- AI の設定の「ローカル」の欄に「ローカルAIのモデル」の小さな欄を足す。
  - 状態（上の表と同じ文言）と進み具合の棒、［ダウンロードする / 一時停止 / 再開する / もう一度試す］。
  - 使えるとき: 「ダウンロード済み（3.1GB）」と［モデルを削除］（Q10 の C。押すと確認の小窓「削除すると、もう一度ダウンロードするまでローカルAIは使えません」）。
- 接続テストの失敗の文言に `local_ai_not_ready` を足す: 「ローカルAIの準備がまだ終わっていません（モデルのダウンロードが必要です）」。
- 今の `local_ai_missing`（「ローカルAIの部品が見つかりません」）は、実行の部品が無いとき（インストールが壊れている）だけに使う。

### 4.3 AI を使おうとしたとき

- 要約・用語解説のボタンで `NotReady` が返ったら、今の失敗の表示と同じ場所に「ローカルAIの準備がまだ終わっていません」と、設定画面の欄への案内を出す。勝手に取得を始めない（同意の扱い〔Q5〕に合わせる）。

## 5. モデルの更新と差し替え

### 5.1 版の管理

- モデルの版は表の `id` で表す。置き場所を `models\<id>\` に分けるため、版が違うファイルが同じ名前で上書きされることはない。
- アプリを更新してモデルの表が変わった（例: 2B → Gemma）とき:
  - 新しい `id` のファイルが無いので「未取得」になり、案内を出す（同意の扱いは Q5 に合わせる。前のモデルで同意していても、大きさが変わるので改めて確かめる案を推奨）。
  - 古いモデルは使わない（照合の期待値は今の表の 1 行だけのため）。取得が終わるまでの間に古いモデルを使い続けるかは、Q3 と同じく「2 つのモデルを混ぜるか」の判断になるため、最初の版では使わない。
- 同じモデルでも、取得元だけが変わった（URL の変更）場合は、`id`（ファイル名と SHA-256 から作る）が変わらないので取り直しは起きない。

### 5.2 古いファイルの削除

- 起動時と、新しいモデルの取得が終わった直後に、`local_llm\models\` の中の「今の表に無い `id` のフォルダ」を消す。
- 消すのは、本アプリの置き場所の中で、`id` の名前の形（英数字・`.`・`-` だけ）に合うフォルダと、その中の `*.gguf` / `*.part` / `*.part.json` だけ。シンボリックリンクはたどらない。それ以外のファイルがあればフォルダごとは消さない。
- 消すのに失敗しても（使用中など）、アプリは止めず、次の起動でやり直す。

## 6. 常駐時の負荷

常駐アプリとして、取得中もパソコンの操作が重くならないことを優先する（AGENTS.md §2）。数値は見込みで、**どれも未計測**。

| 項目 | 見込みと対策 |
|---|---|
| 通信の帯域 | 回線の速さまで使う（Q8 の推奨 A）。一時停止できる。取得は 1 本の接続だけ（分割して並べて取らない） |
| CPU | TLS の復号と SHA-256 の計算。受け取りながら計算するので、回線の速さに比例して小さい。取得のスレッドは優先度を下げる（Windows の `SetThreadPriority`。既存の `windows-sys` の `Win32_System_Threading` にある見込み） |
| ディスク | 約 3.1GB（Gemma の場合）を 1 回書く。1MiB ずつまとめて書く。再開時は `.part` を 1 回読み直す。書き込みの優先度を下げる「バックグラウンドの処理モード」（`THREAD_MODE_BACKGROUND_BEGIN`）を使えるかは **未確認** |
| メモリ | 読み書きの入れ物 1MiB 程度。ファイルの全体をメモリに載せない |
| 常駐の見張り | 取得が終わったらスレッドを終える。待ちは決まった時刻に起きるだけで、常時のポーリングはしない。取得が要らないとき（使える状態）は何も動かない |
| 取得の後の照合 | 今と同じく、初めて使うときに 1 度 SHA-256 を計算する。3.1GB の照合は、今の 1.3GB（release で約 1〜2 秒・ファイルが OS のキャッシュにあるとき）より長くなる（**未計測**） |
| ローカル AI の利用中 | 取得とは別の話。モデルを替えた場合の生成中のメモリは §23.4 の値（Gemma 約 1.7〜1.8GB）。自動要約のメモリの基準（`LOCAL_LLM_RESIDENT_ESTIMATE`）の見直しは、モデルを替える PR で扱う |

- 取得を始めるのは、アプリの起動から少し後（例: 60 秒）にし、起動直後の RSS 取得などと重ねない。
- 取得中に llama-server は起動しない（モデルが無いため）。取得とローカル AI の生成が同時に重くなることはない。

### 7.2 テストの観点（自動）

- 再開: `206` で正しい `Content-Range` → 続きに書く／`200` → 最初から／`416`・始まりの違う `Content-Range`・`ETag` の違い → `.part` を消して最初から。`.part` が全体の大きさに達していれば、通信せずに照合へ進む。
- 大きさ: `200` で全体と違う・`206` で「全体−N」と違う `Content-Length`、期待より大きい本文 → 止めて `.part` を消す。
- 時間切れ: 取得用のクライアントが `timeout(None)` で作られ、30 秒を超える取得が切れないこと。何も届かない時間が上限を超えたら切れること。
- 記録: `.part.json` に転送先の URL・問い合わせの部分が入らないこと。
- すり替え: 照合の後、モデルのファイルをほかから書き換え・削除できないこと（§3.2 の取っ手）。`discard_local_model` の後は `verified` が下りていること。
- 自動要約: 取得が終わった後に待機列が並べ直されること。
- ハッシュ: 合わない → 完成ファイルを作らない・1 回だけ取り直す・2 回目は失敗で止まる。
- 転送: `http` への転送・表に無いホストへの転送・拒否帯の IP・6 回以上の転送 → 止める。
- command: 引数に URL・パスを取らないこと。戻り値・イベント・ログに URL・パス・問い合わせの部分が入らないこと。`command_permissions_tests` が通ること（常駐ゆうこウィンドウからは呼べない）。
- 状態: 同時に 2 回「始める」を押しても取得は 1 本。一時停止 → 再開で続きから。アプリの終了で `.part` と記録が残る。
- 置き場所: `resolve_model_path` が取得済み → 同梱 → debug の代わり、の順に選ぶ。
- 古いファイル: 今の表に無い `id` だけを消す。名前の形に合わないもの・リンクは消さない。
- AI の連携: 取得前は `NotReady`（Mock へ切り替えない）。自動要約は動かず、使えるようになったら動く。
- 画面（Playwright）: 各状態の文言とボタン、案内を閉じたら出ないこと、取得中もほかの画面へ移れること。

### 7.3 手で確かめる観点

- 新しい Windows（VC++ ランタイム無し・Windows サンドボックスなど）にインストールし、初回起動 → 同意 → 取得 → 照合 → 接続テストが「利用できます」になる。
- オフラインで初回起動したとき、AI 以外の機能が使え、案内とやり直しが出る。
- 取得の途中でアプリを終了 → 起動し直して続きから取れる。途中で回線を切る → やり直しで続きから。
- 取得したファイルを 1 バイト書き換える → `Broken` になり、llama-server を起動しない。取り直せる。
- 空き容量が足りないドライブで始めない。
- 取得中の CPU・ディスク・ほかのアプリの操作感（`docs/01_setup/軽量常駐性能確認手順.md` の測り方に合わせる）。
- アンインストールで何が残るか（Q10）。
- 会社のネットワーク（プロキシ）の下で取れるか（RSS 取得と同じ動きになるか）。

## 8. 未確認のこと

本書を書く時点（2026-11-16）で確かめていないこと。推測で埋めず、実装の前か途中で確かめる。

1. **Hugging Face から取る条件**: 利用条件・アプリからの自動取得の可否、回数や帯域の制限、認証が要るか（`unsloth/gemma-4-E2B-it-GGUF` が同意の要る置き場かどうか）。本書では Web を確かめていない。
2. **URL が変わらずに使えるか**: `/resolve/<コミット>/<ファイル名>` の形で版を固定できるか、置き場（リポジトリ）が消されたり名前が変わったりする可能性、転送先のホスト名（固定の一覧に入れる値）。
3. **今の 2B の取得元**: `stario-qwen3.5-2b-q4_k_m.gguf` は自前の量子化で、公開の置き場が無い。2B のまま取得に切り替えるなら、チームの配布場所（Q1 の B）が要る。配布場所の候補（例: GitHub Releases）の 1 ファイルの大きさの上限も未確認。
4. **2GB の上限**: MSI・NSIS の 2GB の上限は配布手順書 §4 の記載に基づく見込みで、インストーラーを作って確かめていない。
5. **`reqwest`（0.12・`blocking`）の時間切れ**: `timeout` が本文の読み取りまで含むか、読み取りごとの時間切れを付けられるか。
6. **空き容量・優先度の API**: `GetDiskFreeSpaceExW` は `windows-sys` の `Win32_Storage_FileSystem` の feature にある見込み（実装のときに確かめる）。`THREAD_MODE_BACKGROUND_BEGIN` はどの feature にあるか未確認。どちらも新しいクレートは要らない見込み。
7. **従量制の回線の判定**（Q7 の C）: 既存の依存で判定できるか。
8. **`app_local_data_dir()` の実際のパス**（Windows で `%LOCALAPPDATA%\jp.star-system.yuuko-news` になるか）。
9. **アンインストール時の動き**: Tauri の NSIS のアンインストーラーが `%LOCALAPPDATA%` のアプリのデータを消すか・消す選択肢があるか（Q10）。
10. **プロキシ**: 会社のネットワークで、`reqwest` が Windows のプロキシ設定を使うか（RSS 取得と同じ動きになるはずだが、大きな取得で確かめていない）。プロキシを通すときは、接続先はプロキシになり、`resolve_to_addrs` で固定した IP は使われず、取得元の IP の拒否帯の確かめもプロキシ任せになる。RSS・記事取得のプロキシ経由のときの今の扱いを確かめ、それに合わせるか、取得ではプロキシを通さないかを決める。
11. **時間・負荷**: 3.1GB の取得にかかる時間、取得中の CPU・ディスクの負荷、取得後の SHA-256 の照合の時間（キャッシュに無い初回）。どれも未計測。
12. **ライセンス表記**: 取得したモデルのライセンス本文と改変の告知（今は `local_llm/LICENSES/` に同梱）を、取得の形でどう示すか（インストーラーに入れておくか、取得と一緒に置くか）。Gemma の Apache-2.0 は評価資料の記載で、本書では確かめ直していない。
13. **モデルを替えるかどうか**: Gemma に替えるかは未決定（§23.5 の判断材料のとおり、作り話は減ったとは言えず、記事の文を長く写す傾向もある）。本書の設計は、2B のまま取得に切り替える場合にも使える。
14. **共有モードと mmap**: 書き込み・削除を拒む共有モードで開いたまま、`llama-server` がモデルを読み取り（mmap）で開けるか（§3.2）。
