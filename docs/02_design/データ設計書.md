# データ設計書_Tauri v1

## 1. 文書目的
本書は、AIニュースマスコットアプリ「ゆうこのニュース日和」におけるローカル保存データ、Markdown管理、ユーザー設定、ゆうこ辞書、友情ランク、ガチャ要素、アーカイブ、データ移行対象を、Tauri版の実装前提で整理するためのデータ設計書である。

本書は以下を目的とする。

- Rust側のdomain / repository / service設計の土台を作る
- TypeScript側で扱う型定義の土台を作る
- Markdown保存形式を明確にする
- ローカル保存データの責務を整理する
- MVP実装時に最低限必要なデータ構造を定義する
- 将来的なGoogle Driveデータ移行やアーカイブ運用に備える

---

## 2. 基本方針

### 2.1 保存方針
本アプリは、クラウドDBや専用バックエンドを前提とせず、基本的なデータをローカルに保存する。

主な保存対象は以下とする。

- ニュースデータ
- AI要約
- ゆうこの再説明文
- ゆうこ辞書
- 閲覧履歴
- お気に入り情報
- 友情ランク
- 報酬解放状況
- ガチャ関連データ
- ユーザー設定
- テーマ / デコ設定
- アーカイブデータ
- ゆうこ通知状態

### 2.2 データ形式の基本
- ニュースは **1記事1Markdown** を基本とする。
- ゆうこ辞書も、初期版ではMarkdownまたはJSONで管理する。
- アプリ設定や状態管理系データはJSONを基本候補とする。
- 大量に増えるニュースデータは月単位でアーカイブ可能な構造とする。
- 人間が確認しやすい可読性と、プログラムが扱いやすい構造の両立を目指す。
- React側から直接ローカルファイルを読み書きしない。
- 保存、読込、更新、アーカイブ処理はRust側で行う。
- React側はTauri command経由でDTOを受け取る。

### 2.3 MVPでの優先
MVPでは、以下の保存構造を優先する。

- ニュースMarkdown
- ゆうこ辞書
- ユーザー設定
- 友情ランク情報
- お気に入りフラグ
- 既読状態
- AI Provider設定
- ゆうこ通知状態

ガチャ、データ移行、詳細アーカイブは、データ構造上の余地は作るが、完全実装は後続でもよい。

## 3. 推奨ディレクトリ構成

### 3.1 ローカルデータルート
アプリのローカルデータは、Tauriのアプリケーションデータ領域配下に保存することを想定する。

概念例:

```text
YuukoAppData/
  config/
  news/
  favorites/
  dictionary/
  archive/
  user/
  rewards/
  gacha/
  cache/
  logs/
  transfer/
```

Tauri実装時は、`app_data_dir` 相当のアプリ管理ディレクトリを利用する。  
開発中は、プロジェクト直下またはユーザー配下の検証用ディレクトリを使ってもよいが、本番想定ではOS標準のアプリデータ領域へ寄せる。

### 3.2 ディレクトリ責務

| ディレクトリ | 役割 |
|---|---|
| `config/` | アプリ設定、AI設定、通知設定 |
| `news/` | 通常ニュースMarkdown |
| `favorites/` | お気に入り記事、またはお気に入り管理情報 |
| `dictionary/` | ゆうこ辞書 |
| `archive/` | 月次圧縮アーカイブ |
| `user/` | 友情ランク、ユーザー傾向、表示状態など |
| `rewards/` | 解放済み報酬、テーマ、デコ情報 |
| `gacha/` | ガチャ所持情報、結果履歴 |
| `cache/` | 一時キャッシュ |
| `logs/` | 必要最小限のログ |
| `transfer/` | データ移行用一時ファイル |

### 3.3 MVPで必須のディレクトリ
MVPでは最低限以下があればよい。

```text
YuukoAppData/
  config/
  news/
  dictionary/
  user/
  logs/
```

### 3.4 Rust側の保存担当
ローカルデータの読み書きは、以下のようなRust側repository / storageで行う。

| Rustモジュール | 役割 |
|---|---|
| `article_repository.rs` | ニュース記事の保存・読込 |
| `dictionary_repository.rs` | ゆうこ辞書の保存・読込 |
| `settings_repository.rs` | 設定保存・読込 |
| `friendship_repository.rs` | 友情ランク保存・読込 |
| `reward_repository.rs` | 報酬状態保存・読込 |
| `gacha_repository.rs` | ガチャ状態保存・読込 |
| `markdown_storage.rs` | Markdown保存共通処理 |
| `json_storage.rs` | JSON保存共通処理 |
| `archive_storage.rs` | アーカイブ処理 |
| `logger.rs` | ログ出力 |

## 4. ニュースデータ設計

## 4.1 ニュースMarkdownの基本方針
ニュースは、1記事につき1つのMarkdownファイルで保存する。

ファイル内部は、以下の2部構成を想定する。

1. YAML Front Matter
2. 本文 / 抽出テキスト / AI生成結果

### 4.2 ファイル名規則
初期案として、以下の形式を候補とする。

```text
news_YYYYMMDD_<sourceKey>_<shortId>.md
```

例:

```text
news_20260428_itmedia_a1b2c3.md
news_20260428_googleai_d9e8f7.md
```

### 4.3 ニュースID
ニュースIDは、以下を材料に生成する。

- URL
- 出典
- タイトル
- 取得日時
- ハッシュ値

初期版では、URLのハッシュを中心に生成する。

```text
articleId = sha256(url).substring(0, 12)
```

URLが取得できない場合は、出典 + タイトル + 取得日時から生成する。

### 4.4 ニュースMarkdown例

```markdown
---
version: 1
articleId: "a1b2c3d4e5f6"
title: "AIモデルの新機能が発表"
sourceName: "Example News"
sourceKey: "example_news"
url: "https://example.com/news/ai-001"
fetchedAt: "2026-04-28T09:10:00+09:00"
publishedAt: "2026-04-28T08:00:00+09:00"
category: "AI"
tags:
  - "AI"
  - "生成AI"
status:
  fetched: true
  htmlExtracted: true
  markdownGenerated: true
  summarized: true
  recommended: true
  introducedByYuuko: false
readState: "summary_viewed"
favorite: false
archiveState: "active"
recommendScore: 82
summaryGeneratedAt: "2026-04-28T09:12:00+09:00"
aiProvider: "gemini"
contentHash: "9f8e7d6c5b4a"
---

# AIモデルの新機能が発表

## 本文抜粋
ここにHTMLから抽出した本文抜粋を保存する。

## AI要約
AIモデルの新機能が発表され、開発者向けの利用範囲が広がりました。

## ゆうこの再説明
これは、AIを使った開発がもう少し便利になるかもしれないニュースだよ。

## 注目ポイント
- 新機能が公開された
- 開発者向けの利用が想定されている
- 今後のツール連携に影響する可能性がある

## ゆうこの一言
ちょっと未来の道具箱が増えた感じだね。

## 解説対象候補語
- 生成AI
- API
- モデル
```

## 5. ニュース状態設計

### 5.1 記事処理状態
記事は処理状況として以下を持つ。

| 状態 | 意味 |
|---|---|
| `fetched` | RSSまたはニュースソースから取得済み |
| `htmlExtracted` | HTML本文または本文抜粋を抽出済み |
| `markdownGenerated` | Markdown化済み |
| `summarized` | AI要約生成済み |
| `recommended` | おすすめ候補に含まれる |
| `introducedByYuuko` | ゆうこが紹介済み |
| `archived` | アーカイブ済み |

Rust型候補:

```rust
#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
pub struct ArticleProcessingStatus {
    pub fetched: bool,
    pub html_extracted: bool,
    pub markdown_generated: bool,
    pub summarized: bool,
    pub recommended: bool,
    pub introduced_by_yuuko: bool,
    pub archived: bool,
}
```

### 5.2 読了状態
読了状態は以下の文字列で管理する。

| 値 | 意味 |
|---|---|
| `unread` | 未読 |
| `summary_viewed` | 要約閲覧済み |
| `detail_viewed` | 詳細閲覧済み |
| `reexplained_viewed` | 再説明閲覧済み |
| `source_opened` | 元記事遷移済み |

Rust型候補:

```rust
#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
pub enum ArticleReadState {
    Unread,
    SummaryViewed,
    DetailViewed,
    ReexplainedViewed,
    SourceOpened,
}
```

### 5.3 アーカイブ状態
| 値 | 意味 |
|---|---|
| `active` | 通常表示対象 |
| `archive_candidate` | アーカイブ候補 |
| `archived` | アーカイブ済み |
| `restored` | アーカイブから再展開済み |

### 5.4 お気に入り
お気に入りは記事状態ではなく、独立したフラグとして扱う。

```yaml
favorite: true
```

お気に入り記事はアーカイブ対象から除外する。

## 7. ゆうこ辞書データ設計

## 7.1 基本方針
ゆうこ辞書は、ユーザーが解説した単語、短いフレーズ、長文要点説明を保存する。

用途は以下とする。

- 再利用によるAIトークン削減
- ユーザーが後から見返すための知識蓄積
- ★マークや付箋メモによる整理

### 7.2 保存形式
初期版では、以下のいずれかを候補とする。

- 1項目1Markdown
- 1ファイルJSON配列
- SQLite等の軽量DB

MVPでは、可読性重視で **1項目1Markdown** または **JSON** を候補とする。  
実装の単純さを優先する場合は、まずJSON配列で始める。

### 7.3 辞書ファイル名
```text
dict_<type>_<shortHash>.md
```

例:

```text
dict_term_aa11bb22.md
dict_phrase_cc33dd44.md
dict_summary_ee55ff66.md
```

### 7.4 ゆうこ辞書Markdown例

```markdown
---
version: 1
dictionaryId: "dict_aa11bb22"
targetText: "生成AI"
normalizedText: "生成AI"
type: "term"
createdAt: "2026-04-28T10:00:00+09:00"
lastReferencedAt: "2026-04-28T12:20:00+09:00"
referenceCount: 3
sourceArticleIds:
  - "a1b2c3d4e5f6"
favorite: true
memo: "社内発表でよく使いそう"
aiProvider: "gemini"
---

# 生成AI

## 解説
文章や画像などを新しく作れるAIのことだよ。

## 詳細
ニュースの文脈では、文章作成やコード補助、画像生成などを行うAI技術全般を指しているよ。
```

## 14. アーカイブデータ設計

## 14.1 基本方針
1か月経過したニュース群を月単位でZIP化する。

```text

  2026-03.zip
  2026-02.zip
```

### 14.2 アーカイブ対象
- 1か月以上前のニュース
- お気に入りではないニュース
- アーカイブ済みでないニュース

### 14.3 アーカイブ対象外
- お気に入り記事
- 再展開中の記事
- エラー状態の記事
- 保存整合性が確認できない記事

### 14.4 アーカイブインデックス
アーカイブ内検索を軽くするため、月別インデックスを用意する候補がある。

```text

```

例:

```json
{
  "archives": [
    {
      "month": "2026-03",
      "file": "2026-03.zip",
      "articleCount": 42,
      "createdAt": "2026-04-01T00:10:00+09:00",
      "sizeBytes": 102400
    }
  ]
}
```

### 14.5 Tauri版の注意
- ZIP化や展開はRust側で行う。
- React側から任意ファイルパスを指定させない。
- アーカイブファイル名は年月など安全な形式から生成する。

### 15.4 manifest.json例

    "news",

### 15.5 暗号化方針
- Google Driveへアップロードする場合は、ZIP化後にクライアント側で暗号化する。

- 復号鍵はDrive上に保存しない。
- ワンタイムパスコードまたはQRコードで復元情報を受け渡す。
- 暗号化・復号・ZIP作成はRust側または安全な連携層で行う。
- React側は進捗表示、QR表示、ワンタイムパスコード入力を担当する。

## 17. データバージョン管理

## 17.1 versionフィールド
JSONやMarkdown Front Matterには、可能な限り `version` またはスキーマ版数を持たせる。

```json
{
  "version": 1
}
```

### 17.2 マイグレーション
将来的に保存形式を変更する場合に備え、以下を検討する。

- 起動時にデータバージョンを確認
- 古い形式の場合は変換
- 変換前にバックアップ
- 変換失敗時は元データを維持
- 変換処理はRust側で行う

### 17.3 TypeScript側の扱い
React側では、マイグレーション済みのDTOを受け取ることを基本とする。  
React側で古い形式のデータ変換を行わない。

## 21. まとめ
本アプリは、基本データをローカルに保存し、ニュースと辞書を可読性の高い形式で管理する。

MVPでは、以下のデータ構造を優先して実装する。

- ニュースMarkdown
- ゆうこ辞書
- ユーザー設定
- 友情ランク
- ゆうこ通知状態
- お気に入り
- 既読状態
- AI要約メタ情報

Tauri版では、React / TypeScriptは表示用DTOを扱い、保存・読込・更新・アーカイブ・移行処理はRust側で担当する。  
ガチャ、Google Drive移行、詳細アーカイブは、将来的な拡張としてデータ構造の余地を残しつつ、MVP段階では過剰に作り込まない。
