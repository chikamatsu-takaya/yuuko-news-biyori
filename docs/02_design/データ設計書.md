# データ設計書 v1

## 1. 文書目的
本書は、AIニュースマスコットアプリ「ゆうこのニュース日和」におけるローカル保存データ、Markdown管理、ユーザー設定、ゆうこ辞書、友情ランク、ガチャ要素、アーカイブ、データ移行対象を、Tauri版の実装前提で整理するためのデータ設計書である。

本書は以下を目的とする。

- Rust側のdomain / repository / service設計の土台を作る
- TypeScript側で扱う型定義の土台を作る
- Markdown保存形式を明確にする
- ローカル保存データの責務を整理する
- MVP実装時に最低限必要なデータ構造を定義する
- 将来的なGoogle Driveデータ移行やアーカイブ運用に備える

---

## 2. 基本方針

### 2.1 保存方針
本アプリは、クラウドDBや専用バックエンドを前提とせず、基本的なデータをローカルに保存する。

主な保存対象は以下とする。

- ニュースデータ
- AI要約
- ゆうこの再説明文
- ゆうこ辞書
- 閲覧履歴
- お気に入り情報
- 友情ランク
- 報酬解放状況
- ガチャ関連データ
- ユーザー設定
- テーマ / デコ設定
- アーカイブデータ
- ゆうこ通知状態

### 2.2 データ形式の基本
- ニュースは **1記事1Markdown** を基本とする。
- ゆうこ辞書も、初期版ではMarkdownまたはJSONで管理する。
- アプリ設定や状態管理系データはJSONを基本候補とする。
- 大量に増えるニュースデータは月単位でアーカイブ可能な構造とする。
- 人間が確認しやすい可読性と、プログラムが扱いやすい構造の両立を目指す。
- React側から直接ローカルファイルを読み書きしない。
- 保存、読込、更新、アーカイブ処理はRust側で行う。
- React側はTauri command経由でDTOを受け取る。

### 2.3 MVPでの優先
MVPでは、以下の保存構造を優先する。

- ニュースMarkdown
- ゆうこ辞書
- ユーザー設定
- 友情ランク情報
- お気に入りフラグ
- 既読状態
- AI Provider設定
- ゆうこ通知状態

ガチャ、データ移行、詳細アーカイブは、データ構造上の余地は作るが、完全実装は後続でもよい。

```text
  news/
  favorites/
  dictionary/
  archive/
```

Tauri実装時は、`app_data_dir` 相当のアプリ管理ディレクトリを利用する。  
開発中は、プロジェクト直下またはユーザー配下の検証用ディレクトリを使ってもよいが、本番想定ではOS標準のアプリデータ領域へ寄せる。

## 4. ニュースデータ設計

## 4.1 ニュースMarkdownの基本方針
ニュースは、1記事につき1つのMarkdownファイルで保存する。

ファイル内部は、以下の2部構成を想定する。

1. YAML Front Matter
2. 本文 / 抽出テキスト / AI生成結果

### 4.2 ファイル名規則
記事Markdownは、ニュースディレクトリ（`news/`）配下の月別サブディレクトリへ、記事IDをそのままファイル名にして保存する（`article_repository.rs` の `article_path`）。

```text
news/<YYYYMM>/<articleId>.md
```

例:

```text
news/202604/news_0123456789abcdef.md
```

- `<YYYYMM>` は公開日時（`publishedAt`）の先頭の年月から決める。公開日時から年月を取れない場合は取得日時（`fetchedAt`）を使い、どちらも取れない場合は `unknown` とする（`month_bucket`）。
- 公開日時・取得日時はいずれもUTCで保存するため、月の区切りもUTC基準になる。
- 出典キー（`sourceKey`）はファイル名には含めず、Front Matterにのみ保存する。

### 4.3 ニュースID
ニュースIDは、記事URLから生成する（`news_service.rs` の `article_id_from_url`）。

```text
articleId = "news_" + fnv1a_64(正規化したURL) の16桁16進表記
```

- 正規化: URLとして解釈し、フラグメント（`#...`）を除去し、末尾の `/` を除去する（ホスト名は小文字化される）。URLとして解釈できない場合は前後の空白を除いた文字列をそのまま使う。
- ハッシュには、Rustのバージョンに依存せず値が変わらない FNV-1a 64bit を使う。
- 同じURLは常に同じIDになるため、取得済みIDとの照合で重複保存を避ける。
- 初回起動時に書き出すサンプル記事は `article-001` 形式のIDを持つ（`seed_articles`）。

### 4.4 ニュースMarkdown例

```markdown
---
version: 1
articleId: news_0123456789abcdef
title: AIモデルの新機能が発表
sourceName: Example News
sourceKey: example_news
url: https://example.com/news/ai-001
fetchedAt: 2026-04-28T00:10:00Z
publishedAt: 2026-04-27T23:00:00Z
genre: AI
tags:
- AI
- 生成AI
status:
  fetched: true
  htmlExtracted: true
  markdownGenerated: true
  summarized: true
  recommended: true
  introducedByYuuko: false
  archived: false
readState: previewed
favorite: false
archiveState: active
archived: false
recommendationScore: 0.82
summaryGeneratedAt: 2026-04-28T00:12:00Z
aiProvider: gemini
contentHash: null
---

## 本文抜粋
ここにHTMLから抽出した本文抜粋を保存する。

## AI要約
AIモデルの新機能が発表され、開発者向けの利用範囲が広がりました。

## ゆうこの用語解説
これは、AIを使った開発がもう少し便利になるかもしれないニュースだよ。

## 注目ポイント
- 新機能が公開された
- 開発者向けの利用が想定されている
- 今後のツール連携に影響する可能性がある

## ゆうこの一言
ちょっと未来の道具箱が増えた感じだね。

## 解説対象キーワード
- 生成AI
- API
- モデル
```

補足（`article_repository.rs` の `PersistedArticleFrontMatter` / `ArticleBodySection` に対応）:

- Front Matter のキーは camelCase。ジャンルは `genre` で保存する（旧キー `category` も読み込み時に受け付ける）。
- `fetchedAt` / `publishedAt` はUTCのRFC3339（`YYYY-MM-DDTHH:MM:SSZ`）。フィードの公開日時を解釈できない場合、`publishedAt` には取得日時を入れる。
- `archiveState` と `archived` はアーカイブ状態の保存用（§14）。
- 本文に記事タイトルの見出し（`#`）は書かない。値が空の節は見出しごと出力しない。
- 見出しは上記6種（`本文抜粋` / `AI要約` / `ゆうこの用語解説` / `注目ポイント` / `ゆうこの一言` / `解説対象キーワード`）で固定し、読み込み時もこの見出し名で節を判別する。
- お気に入りは Front Matter の `favorite` に加えて `favorites/article_favorites.json` でも管理し、どちらかが true ならお気に入りとして扱う（`is_effectively_favorite`）。

## 5. ニュース状態設計

### 5.1 記事処理状態
記事は処理状況として以下を持つ。

| 状態 | 意味 |
|---|---|
| `fetched` | RSSまたはニュースソースから取得済み |
| `htmlExtracted` | HTML本文または本文抜粋を抽出済み |
| `markdownGenerated` | Markdown化済み |
| `summarized` | AI要約生成済み |
| `recommended` | おすすめ候補に含まれる |
| `introducedByYuuko` | ゆうこが紹介済み |
| `archived` | アーカイブ済み |

Rust型候補:

```rust
#[derive(Debug, Clone, serde::Serialize, serde::Deserialize)]
pub struct ArticleProcessingStatus {
    pub fetched: bool,
    pub html_extracted: bool,
    pub markdown_generated: bool,
    pub summarized: bool,
    pub recommended: bool,
    pub introduced_by_yuuko: bool,
    pub archived: bool,
}
```

### 5.2 読了状態
読了状態は以下の3段階の文字列で管理する（Front Matter の `readState`）。

| 値 | 意味 |
|---|---|
| `unread` | 未読 |
| `previewed` | 一覧閲覧または軽量プレビュー表示済み |
| `detail_viewed` | 詳細閲覧済み |

- 状態は `unread` → `previewed` → `detail_viewed` の一方向にだけ進め、後退させない（`ArticleReadState::can_advance_to`）。
- `readState` が無い記事は `unread` として読み込む。

Rust型（`src-tauri/src/domain/article.rs`）:

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum ArticleReadState {
    Unread,
    Previewed,
    DetailViewed,
}
```

### 5.3 アーカイブ状態
| 値 | 意味 |
|---|---|
| `active` | 通常表示対象 |
| `archive_candidate` | アーカイブ候補 |
| `archived` | アーカイブ済み |
| `restored` | アーカイブから再展開済み |

### 5.4 お気に入り
お気に入りは記事状態ではなく、独立したフラグとして扱う。

```yaml
favorite: true
```

お気に入り記事はアーカイブ対象から除外する。

### 5.5 ニュース取得タイミング状態
常駐中の自動取得（起動時・日付変更時・通知の時間帯内の定期取得）の実行タイミングを管理する。

```text
state/news_refresh_state.json
```

```json
{
  "lastNewsRefreshDate": "2026-10-07",
  "lastNewsRefreshAt": "2026-10-07T03:00:00+00:00"
}
```

- `lastNewsRefreshDate` は最後に自動取得が成功したローカル日付（`YYYY-MM-DD`）。日付変更時の取得判定に使う。
- `lastNewsRefreshAt` は最後に自動取得が成功した時刻（UTC・RFC3339）。定期取得の周期（既定3時間）判定に使う。
- `lastNewsRefreshAt` は後から追加した項目のため省略可能とし、日付だけの旧形式も読み込める（欠落時は通知の時間帯内なら取得する）。
- 自動取得が成功したときだけ両方を更新する。失敗時・手動取得の実行中で見送った場合は更新せず、次回の低頻度チェックで再試行する。
- 欠落・破損時は未取得扱い（再取得側）とする。取得元・許可リストの検証は取得処理側で fail-close のため、ここはセキュリティ境界ではない。

## 7. ゆうこ辞書データ設計

## 7.1 基本方針
ゆうこ辞書は、ユーザーが解説した単語、短いフレーズ、長文要点説明を保存する。

用途は以下とする。

- 再利用によるAIトークン削減
- ユーザーが後から見返すための知識蓄積
- ★マークや付箋メモによる整理

### 7.2 保存形式
辞書は、全項目を1つのJSONファイルにまとめて保存する（`dictionary_repository.rs`）。

```text
dictionary/entries.json
```

- ファイル全体は `version` と `entries`（項目の配列）を持つオブジェクトとする（`PersistedDictionaryStore`）。
- 1項目1Markdown や SQLite 等の軽量DB は、現実装では採用していない。

### 7.3 辞書ファイル名
現実装では辞書を `dictionary/entries.json` の1ファイルで保存するため、項目ごとのファイル名は持たない。  
以下は1項目1Markdownとする場合の参考案であり、現実装では使用していない。

```text
dict_<type>_<shortHash>.md
```

例:

```text
dict_term_aa11bb22.md
dict_phrase_cc33dd44.md
dict_keypoint_ee55ff66.md
```

### 7.4 ゆうこ辞書Markdown例
以下は1項目1Markdownとする場合の参考案であり、現実装では使用していない（保存形式は §7.5 のJSON）。

```markdown
---
version: 1
dictionaryId: "dict_aa11bb22"
targetText: "生成AI"
normalizedText: "生成AI"
type: "term"
createdAt: "2026-04-28T10:00:00+09:00"
lastReferencedAt: "2026-04-28T12:20:00+09:00"
referenceCount: 3
sourceArticleIds:
  - "a1b2c3d4e5f6"
favorite: true
memo: "社内発表でよく使いそう"
aiProvider: "gemini"
---

# 生成AI

## 解説
文章や画像などを新しく作れるAIのことだよ。

## 詳細
ニュースの文脈では、文章作成やコード補助、画像生成などを行うAI技術全般を指しているよ。
```

### 7.5 辞書JSON例
`dictionary/entries.json` の例（`PersistedDictionaryStore` / `PersistedDictionaryEntry`）。

```json
{
  "version": 1,
  "entries": [
    {
      "version": 1,
      "dictionaryId": "entry-news_0123456789abcdef-1a2b3c4d5e6f7a8b",
      "targetText": "生成AI",
      "normalizedText": "生成ai",
      "entryType": "term",
      "shortExplanation": "文章や画像などを新しく作れるAIのことだよ。",
      "detailExplanation": "ニュースの文脈では、文章作成やコード補助、画像生成などを行うAI技術全般を指しているよ。",
      "createdAt": "1777338000",
      "lastReferencedAt": "1777346400",
      "referenceCount": 3,
      "sourceArticleIds": ["news_0123456789abcdef"],
      "favorite": true,
      "memo": "社内発表でよく使いそう",
      "relatedArticleTitle": "AIモデルの新機能が発表",
      "relatedArticleId": "news_0123456789abcdef"
    }
  ]
}
```

補足:

- 項目のキーは camelCase。種別のキーは `entryType`（値は §7.6）。
- `dictionaryId` は `entry-<記事ID>-<ハッシュ16進>` 形式で、記事IDと正規化した選択文字列から生成する（`dictionary_service.rs` の `build_entry_id`）。ハッシュ部は Rust 標準の `DefaultHasher` の値を16進で表したもの（ゼロ埋めなし）で、桁数は固定ではなく、Rust のバージョンをまたいだ安定性も保証しない（記事IDの FNV-1a とは異なる）。
- `normalizedText` は前後の空白を除いて小文字化した文字列（`normalize_text`）。
- `relatedArticleId` / `relatedArticleTitle` は最後に保存したときの関連記事、`sourceArticleIds` はこれまでに関連した記事IDの一覧。
- AIプロバイダ名（`aiProvider`）は辞書項目には保存しない。

#### 日時形式
- `createdAt` / `lastReferencedAt` は、UNIXエポックからの経過秒数（UTC・整数）を10進の **文字列** で保存する（`dictionary_repository.rs` の `current_unix_timestamp_text`）。RFC3339 ではない。
- `createdAt` は項目の新規保存時、`lastReferencedAt` は新規保存時・同じ項目の再保存時・保存済み解説を再利用して表示したとき（用語解説で保存済み項目に一致したとき）に、その時刻で設定する。

#### 参照回数
- `referenceCount` は項目の参照回数（0以上の整数）。新規保存時は `1`、同じ項目の再保存時と、保存済み解説を再利用して表示したときに `1` 増やす（上限で頭打ち）。
- 再利用表示時の更新は、解説の表示とは独立した付随処理とする。新しい項目は作らず、更新に失敗しても解説は表示し、失敗は調査用ログに残すだけにする（`dictionary_service.rs` の `explain_selected_term` → `dictionary_repository.rs` の `record_entry_reference`）。
- 一覧の並び順や保存済み解説の選択では、`lastReferencedAt`（無ければ `createdAt`）の文字列を比較して新しい順を判定する（`entry_timestamp_key`）。
- 画面向けの一覧項目（`lastViewedAtText`）にも、この文字列がそのまま渡る。

#### データ移行時の扱い
- データ移行（§15）で辞書を書き出す・取り込む際は、`createdAt` / `lastReferencedAt` を上記のUNIX秒の文字列のまま保持し、形式を変換しない。
- データ移行機能は未実装のため、変換が必要になった場合の扱いはデータ移行の実装時に決める。

### 7.6 辞書種別
| 値 | 意味 |
|---|---|
| `term` | 単語 |
| `phrase` | 短いフレーズ |
| `key_point` | 長文要点説明 |

- 解説を求められる選択文字列は200文字（trim 後・chars 単位）までとする。200文字程度までの長文の要点説明は `phrase` 種別で保存する（判断台帳 D21）。
- 現状の実装は種別を振り分けておらず、AI生成・汎用文の解説は長さにかかわらず `term` で保存される（詳細設計書 §5.3.4）。

### 7.7 再利用ルール
- 初期版では完全一致を基本とする。
- 比較には `normalizedText` を利用する。
- 類似一致は将来拡張とする。

## 8. ユーザー設定データ

## 8.1 設定ファイル
ユーザー設定はJSONで管理する。

ファイル例:

```text
config/settings.json
config/settings.corrupt.json   # 破損時の退避ファイル（初期化した場合だけ作る・1世代のみ）
```

破損時の退避（判断台帳 D57 / セキュリティ詳細設計書 §11.4）:

- `settings.json` が JSON として読めない（`get_user_settings` のエラーコード `JSON_ERROR`）状態で「設定を初期化する」（`reset_user_settings`）を実行したときだけ、既定値で上書きする前に、壊れたファイルを同じフォルダ（アプリ管理ディレクトリの `config/`）へ `settings.corrupt.json` としてバイト列のまま複製する。
- 名前は固定で、残すのは1世代だけ。前回の退避ファイルがあれば新しい内容で置き換える。
- 複製は一時ファイル `settings.corrupt.json.tmp` へ書いてから差し替える。複製に失敗した場合は初期化を中止し、元の `settings.json` をそのまま残してエラー（`IO_ERROR`）を返す。
- 壊れていない状態の通常のリセットでは退避ファイルを作らない。
- 退避ファイルはアプリから読み込まない（調査・手動復旧用）。

- `ui.autoStartOnPcBoot` はOSへの自動起動登録状態の写しであり、通常の設定保存では上書きせず、自動起動の切り替え時だけ更新する。

## 9. ゆうこ通知状態データ

## 9.1 保存ファイル
ゆうこ通知状態はJSONで管理する。

```text

state/yuuko_notification_state.corrupt.json   # 破損時の退避ファイル（作り直した場合だけ作る・1世代のみ）
```

破損時の退避（判断台帳 D57 / セキュリティ詳細設計書 §11.4。ゆうこ通知状態・友情ランク・報酬で共通）:

- 読み込み時に JSON として読めない（構文・型の不一致・不正な UTF-8。先頭の UTF-8 BOM は除いて読む）場合、壊れたファイルを同じフォルダへ `<名前>.corrupt.json` としてバイト列のまま複製してから、既定値で作り直して保存する。設定ファイル（§8.1）と同じ方法で、名前は固定・1世代だけ残し、一時ファイル `<名前>.corrupt.json.tmp` 経由で差し替える。
- 複製に失敗した場合は作り直さず、元ファイルをそのまま残してエラーを返す。次回の読み込みで再試行されるため、通知判定などが止まり続けることはない。
- 型の不一致（例: 新しい版で保存したファイルを古い版で読んだ場合）も破損として扱い作り直す。元のファイルは `<名前>.corrupt.json` に残る。
- 退避には読み込んだバイト列そのものを書き出す（読み直さない。並行した読み込みが先に作り直した既定値で退避ファイルを上書きしないため）。
- 権限などの読み込み自体の IO エラーでは作り直さない（一時的な失敗でデータを消さないため）。
- ログには種類（`yuuko-state` / `friendship` / `rewards`）と破損の分類だけを出し、パスや中身は出さない。
- 退避ファイルはアプリから読み込まない（調査・手動復旧用）。
- 辞書（`dictionary/entries.json`）は利用者のデータを失わないよう自動では初期化しない（読めないときの扱いは別途決める）。
- ゆうこ通知状態の既定値は待機中・通知回数0・紹介済みなし（ゆうこ登場・通知挙動_詳細設計書 §16.3「不正状態は待機中へ戻す」）。

## 11.1 保存ファイル

### 11.2 rewards.json例

```json
{
  "version": 1,
  "unlockedRewardIds": [
    "theme_001"
  ],
  "pendingRewards": [
    {
      "rewardId": "theme_001",
```

### 11.3 報酬マスタ
報酬マスタはアプリに同梱し、Rust のコード内の定数（`src-tauri/src/domain/reward.rs` の `REWARD_MASTER`）として持つ。

現在の内容（当面は UI テーマ2種のみ。表示名は仮で、配色はテーマ設計タスクで決める）:

| rewardId | type | name | unlockRank |
|---|---|---|---|
| theme_001 | theme | テーマ① | 3 |
| theme_002 | theme | テーマ② | 7 |

- ランク r に到達したら `unlockRank <= r` の報酬をすべて解放する（ランクを飛び越えても取りこぼさない）。
- ランク10の報酬枠は空けておく（中身は後で決める）。

### 11.4 Tauri版の注意
- 画像などのリソースを伴う報酬を追加するときは、Tauriで同梱するリソースパスとの整合を取る。
- ユーザーが外部から指定した任意パスをそのまま表示に使わない。
- React側には表示用の安全なパスまたは識別子を渡す。

## 12. ガチャデータ設計

## 12.1 扱い
2026-10-08 決定（判断台帳 D72〜D81。D40 の保留を解除）により、ガチャは小さく作る。
1回引くと未所持のものが1個もらえる。レアリティ・10連・重複・購入は持たない。

## 12.2 保存ファイル
```text
gacha/gacha_state.json
gacha/gacha_state.corrupt.json   # 破損時の退避ファイル（作り直した場合だけ作る・1世代のみ）
```

- 破損時は §9.1 と同じ方法で退避し、既定値（初回と同じ。かけらは初期値 `INITIAL_FRAGMENTS`、所持なし）で作り直す。ログの種類は `gacha`。
- 報酬（§11.1）と違い、獲得済みのものは他のデータから導出し直せないため、作り直すと失われる（退避ファイルからの手動復旧のみ）。

### 12.3 gacha_state.json例

```json
{
  "version": 1,
  "starFragments": 43,
  "ownedItemIds": [
    "card_001",
    "gacha_theme_001"
  ],
  "newItemIds": [
    "gacha_theme_001"
  ],
  "dailyGrant": {
    "date": "2026-10-08",
    "newsReadCount": 3,
    "newsGranted": true,
    "termGrantedCount": 1
  }
}
```

| 項目 | 内容 |
|---|---|
| `starFragments` | 所持中の流れ星のかけら数 |
| `ownedItemIds` | 獲得済みの排出対象ID（重複なし） |
| `newItemIds` | 獲得したがまだ確認していないもの（コレクションで「NEW」表示などに使う。確認したら外す） |
| `dailyGrant` | 日次上限の判定用に、その日の付与状況を1日分だけ持つ。`date` が今日と違えば0から数え直す |
| `dailyGrant.newsReadCount` | その日に未読から既読になった記事の数（同じ記事は二重に数えない） |
| `dailyGrant.newsGranted` | その日のニュース閲覧分のかけらを付与済みか（1日1回まで） |
| `dailyGrant.termGrantedCount` | その日に用語解説・辞書保存で付与した回数（上限 `TERM_DAILY_MAX`） |

- 日付の区切りは友情ランクの日次上限（§10）と同じ基準にする。
- ガチャ結果の履歴は持たない（コレクションで獲得済みを見られれば足りるため）。

### 12.4 ガチャマスタと付与量の定数
ガチャマスタは報酬マスタ（§11.3）と同じ理由で、同梱 JSON（`resources/gacha_master.json`）にせず Rust のコード内の定数として持つ（例: `src-tauri/src/domain/gacha.rs` の `GACHA_MASTER`）。

| 項目 | 内容 |
|---|---|
| `itemId` | 排出対象ID。ランク報酬のID（`theme_001` など）と重ならないようにする |
| `kind` | `card`（ゆうこのひとことカード）/ `theme`（色違いテーマ）/ `deco`（ゆうこの飾り）/ `balloon`（吹き出しデザイン） |
| `name` | 表示名 |
| `text` | ひとことカードの文面（`card` のみ） |

- 当初の内容はひとことカード40枚＋ガチャ用テーマ3種の計43個（D79）。`deco` / `balloon` は素材ができてから行を足すだけで追加できるようにする（D75）。
- ひとことカードの文面は、Claude の下書きを藤井が確認・修正した固定文を組み込む（D78）。AI で生成しない。
- 獲得したテーマを適用すると、ランク報酬のテーマと同じく設定 `ui.themeId` に保存する（D51）。

付与量・消費量は仮の定数とし、使ってみてから調整する（D81）。目安は普通に毎日使って2〜3日に1回引ける程度（D77）。

| 定数（仮） | 値 | 内容 |
|---|---|---|
| `GACHA_COST` | 30 | 1回引くのに使うかけら |
| `NEWS_READ_REQUIRED` | 3 | ニュース閲覧分を付与するのに必要な、その日の既読記事数 |
| `NEWS_DAILY_GRANT` | 10 | ニュース閲覧分の付与量（1日1回まで） |
| `TERM_GRANT` | 1 | 用語解説・辞書保存1回あたりの付与量 |
| `TERM_DAILY_MAX` | 3 | 用語解説・辞書保存で付与する1日の上限回数（合計で1日 +3 まで） |
| `RANK_UP_GRANT` | 30 | 上がったランク1つごとの付与量（複数ランクを一度に上がった場合はランク数ぶん付与。報酬が `unlockRank <= r` をすべて解放する §11.3 と同じ考え方。仮の値・D81） |
| `INITIAL_FRAGMENTS` | 30 | 初期の所持かけら |

- ゆうこの通知への反応ではかけらを付与しない（D74）。

### 12.5 抽選ルール（未所持のみ）
- 抽選は `GACHA_MASTER` のうち `ownedItemIds` に無いものから1個を等確率で選ぶ（D76）。レアリティ・重み付けは持たない（D72）。
- 重複は発生しないため、重複時処理（還元・変換）は持たない。
- 未所持が0個ならコンプリートとし、抽選せず、かけらも消費しない。
- かけら不足のときも抽選せず、かけらを消費しない。
- かけらの消費と獲得の記録は1回の保存でまとめて行い、片方だけ反映された状態を残さない。

### 12.5A 仮の設計判断（判断台帳外・2026-10-08）
次は決定（D72〜D81）から導いた仮の設計判断で、実装・使用後に見直してよい。
- 破損時の退避と既定値での作り直し（§12.2。他の状態ファイルと同じ扱いに合わせた）
- `newItemIds` の使い方（「NEW」表示など）と `newsReadCount` の数え方（未読→既読になった記事数）、日付の区切り（友情ランクと同じ基準）（§12.3）
- `RANK_UP_GRANT` を上がったランク1つごとに付与すること（§12.4）
- 等確率の抽選、不足・コンプリート時に消費しないこと、消費と獲得を1回の保存にまとめること（§12.5）
- 結果履歴を持たないこと（§12.3）
- かけらを付与するきっかけ（2026-10-08・実装時に決めた仮の判断）:
  - ニュース閲覧: 記事の詳細を初めて開いたとき（既読状態が `detail_viewed` へ進んだとき）に既読1件と数える。`detail_viewed` は一方向の最終状態のため、同じ記事は二重に数えない。ゆうこの軽量プレビュー（`previewed` への遷移）はゆうこの通知への反応なので数えない（D74）。プレビュー済みの記事も、詳細を開けば1件と数える。
  - 用語解説・辞書保存: 用語解説を表示できたとき（保存済み辞書の命中を含む）と、辞書へ保存できたときに、それぞれ1回と数え、合計で1日 `TERM_DAILY_MAX` 回まで付与する。
  - ランクアップ: 友情ポイントの加算でランクが上がったとき（ゆうこからメインへの移動による加算を含む）、上がったランク数ぶん付与する。
  - 付与に失敗しても、元の操作（記事を開く・用語解説・辞書保存・ポイント加算）は成功として扱い、ログだけ残す（ガチャは付随機能のため）。

### 12.6 Rust側責務
- 抽選処理（未所持のみ）
- 所持状態・未確認状態の更新
- かけらの付与・消費と日次上限の判定
- 状態の保存と破損時の退避

React側はガチャ結果の表示と演出、コレクションの表示を担当する。

## 14. アーカイブデータ設計

### 14.1 基本方針
1か月経過したニュース群を月単位でZIP化する。

> **決定（2026-06-09 / `docs/archive-retention-policy`）**
> 退避方針は本§14のとおり「**1か月経過 → 月単位ZIP**」で確定する。お気に入り・再展開中・エラー状態・整合性未確認の記事は対象外（§14.3）。
> - **「4〜7日で退避」案は不採用**。要件定義書 §7.2「1か月経過したニュース群を月単位でアーカイブ対象とする」および本書 §9.4 と矛盾し、数日で過去ニュースが履歴画面から消え「過去ニュースを見返せる導線」（要件 §7.2）を損なうため。
> - 月次ZIP作成、記事単位カタログ、安全な単記事復元、元Markdownの退避付き削除は実装済み。日次自動実行は同じ安全検証を再利用する最終増分とする。
> - 状態遷移の目安: `active`（1か月以内）→ `archive_candidate`（1か月経過・未処理）→ `archived`（月次ZIP済み）→ `restored`（ユーザー操作で再展開）。
> - 保管期間・圧縮ルールは将来変更可能とする方針を維持（本書「変更可能なこと」=保管期間/圧縮ルール）。お気に入り記事は期間に関わらず常に除外。

```text
archive/
  2026-03.zip
  2026-02.zip
```

### 14.2 アーカイブ対象
- 1か月以上前のニュース
- お気に入りではないニュース
- アーカイブ済みでないニュース

### 14.3 アーカイブ対象外
- お気に入り記事
- 再展開中の記事
- `archiveState: restored` の記事
- エラー状態の記事
- 保存整合性が確認できない記事

### 14.4 アーカイブインデックス
アーカイブ内検索を軽くするため、月別情報と記事単位の表示用メタデータを持つ。
`archive_index.json` はZIP内Markdownから再構築できる派生カタログであり、本文は保持しない。

```text
archive/archive_index.json
```

例:

```json
{
  "version": 2,
  "archives": [
    {
      "month": "2026-03",
      "file": "2026-03.zip",
      "articleCount": 42,
      "createdAt": "2026-04-01T00:10:00+09:00",
      "sizeBytes": 102400,
      "catalogComplete": true,
      "articles": [
        {
          "articleId": "publickey-20260301-example",
          "entryName": "publickey-20260301-example.md",
          "title": "記事タイトル",
          "sourceName": "Publickey",
          "publishedAtText": "2026-03-01T09:00:00+09:00",
          "fetchedAt": "2026-03-01T09:05:00+09:00",
          "genre": "テクノロジー",
          "summary": "履歴表示用の短い要約",
          "readState": "detail_viewed",
          "recommendationScore": 0.8
        }
      ]
    }
  ]
}
```

- v1（`version`と`articles`がない形式）は後方互換で読み込む。
- 新規作成・月次ZIP再構築時はv2で保存する。
- v1から未移行の月は`catalogComplete: false`として扱い、元Markdown削除の判定には使わない。
- 履歴一覧は通常Markdownと記事カタログを統合し、同一`articleId`では通常Markdownを優先する。
- 取得済みID判定には記事カタログも含め、元Markdown削除後のRSS再取得を防止する。
- ZIP再閲覧ではReactからパスを受け取らず、Rust側で`articleId`から対象を特定する。
- 過去ニュース（要件定義書 §7.7）の月別一覧と対象月の記事一覧は、ZIPを開かず本indexだけから返す（`list_archive_months` / `list_archive_month_articles`）。
  - 月別一覧は`month`・`articleCount`・`catalogComplete`を新しい月から返す。年月・ファイル名が安全な形式でないエントリは返さない。
  - 対象月の記事一覧は、Reactから年月（`YYYY-MM`・月は01〜12）だけを受け取り、index内の一致検索にだけ使う（パスは組み立てない）。index にない月はNotFoundとする。
  - 記事一覧はアーカイブ時点の記事カタログのスナップショットを取得日時の新しい順に返し、お気に入りだけは現在の`article_favorites.json`を反映する。
  - `catalogComplete: false`（v1から未移行）の月は件数のみ返し、記事一覧は空とする。

### 14.5 Tauri版の注意
- ZIP化や展開はRust側で行う。
- React側から任意ファイルパスを指定させない。
- アーカイブファイル名は年月など安全な形式から生成する。
- 単記事復元commandは`articleId`だけを受け取り、英数字・ハイフン・アンダースコア以外を拒否する。
- Rust側で`archive_index.json`から月次ZIPとentry名を解決し、年月とファイル名の対応、entryの完全一致、UTF-8、Front Matterの`articleId`と年月を検証する。
- ZIP全体と展開entryにサイズ上限を設け、暗号化entry、ディレクトリentry、パスを含むentry名、対象entryの欠落・重複を拒否する。
- 復元先Markdownは一時ファイル経由で保存し、既存の利用可能なMarkdownは上書きしない。
- 復元後は`archiveState: restored`、`archived: false`として保存し、同じ記事を再アーカイブ候補にしない。
- 復元時も元の月次ZIPと記事カタログは保持し、履歴表示と取得済みID判定を継続できるようにする。

### 14.6 元Markdownの退避付き削除
- 削除対象は、`archiveState: archived`であり、お気に入り・復元済みではない記事に限定する。
- `catalogComplete: true`の月だけを対象とし、ZIPサイズ、entry件数・名前・サイズ、UTF-8、Front Matter、記事カタログを全件照合する。
- ローカルMarkdownとZIP内Markdownは、アーカイブ状態を表すフィールドだけを正規化して比較する。アーカイブ作成後に本文や状態が変わっている場合は削除しない。
- 削除計画作成後の変更も取り込まないよう、通常領域から移動する直前にMarkdownを再読込する。差分を検出した場合は、その処理内ですでに移動した記事もrollback領域から元へ戻す。
- 対象Markdownは直ちに消去せず、`archive/.markdown-retirement.rollback/`へ同一相対パスで移動する。全件移動後に`archive/.markdown-retirement.committed/`へ切り替えてから削除する。
- commit前に停止した場合は、次回起動時にrollback領域から元の`news/YYYYMM/`へ復元する。commit後の掃除に失敗した場合は記事削除を取り消さず、警告を残して後続の掃除へ持ち越す。
- 元Markdown削除後も月次ZIPと`archive_index.json`は保持し、履歴表示、取得済みID判定、単記事復元を継続できるようにする。
- Tauri commandは任意パス・年月・記事IDを受け取らず、Rust側が管理対象全体から安全な候補だけを選ぶ。

### 14.7 日次アーカイブ保守状態
起動時と低頻度の日付確認時に、月次ZIP作成と元Markdownの退避付き削除を順番に実行する。

```text
state/archive_maintenance_state.json
```

```json
{
  "lastCompletedDate": "2026-06-12"
}
```

- 日付はローカル日付（`YYYY-MM-DD`）で管理する。
- 同じ日付で完全成功済みの場合は、ZIP確認やMarkdown全走査を再実行しない。
- `archive_candidates`と`retire_archived_markdown`の両方が成功し、commit済み退避領域の掃除も完了した場合だけ日付を保存する。
- ZIP作成失敗、退避失敗、cleanup pending、状態保存失敗では日付を更新せず、次回の低頻度チェックで再試行する。
- 処理対象が0件の場合も正常完了として日付を保存する。
- 状態JSONの欠落・破損は未完了扱いとする。アーカイブ処理自体の冪等性と完全性検証を前提に、安全側で再実行する。
- ニュース取得の30分間隔チェックを共有し、アーカイブ専用の常駐スレッドや高頻度ポーリングは追加しない。

- OS資格情報

### 15.3 移行ZIP構成
```text
yuuko_transfer_<transferId>.zip
  manifest.json
  config/
  news/
  dictionary/
  user/
  rewards/
  gacha/
```

### 15.4 manifest.json例

```json
{
  "version": 1,
  "appVersion": "0.1.0",
  "transferId": "tr_abc123",
  "createdAt": "2026-04-28T14:00:00+09:00",
  "expiresAt": "2026-04-28T14:30:00+09:00",
  "included": [
    "config",
    "news",
    "dictionary",
    "user",
    "rewards",
    "gacha"
  ],
  "encrypted": true,
  "encryption": {
    "algorithm": "TBD",
    "keyStoredInCloud": false
  }
}
```

### 15.5 暗号化方針
- Google Driveへアップロードする場合は、ZIP化後にクライアント側で暗号化する。
- Drive上に平文ZIPを置かない。
- 復号鍵はDrive上に保存しない。
- ワンタイムパスコードまたはQRコードで復元情報を受け渡す。
- 暗号化・復号・ZIP作成はRust側または安全な連携層で行う。
- React側は進捗表示、QR表示、ワンタイムパスコード入力を担当する。
- 本節の暗号化は Google Drive 経由の移行が対象。§15.6 のローカルZIP書き出し（Drive に置かない）は暗号化しない（`encrypted: false`）。

### 15.6 ローカルZIP書き出し（実装済み・判断台帳 D41 / D24）
PC変更時の移行用に、ローカルデータを1つのZIPへ書き出す（`export_migration_data`、`src-tauri/src/services/data_export_service.rs`）。辞書の単独書き出しはこれで兼ねる（D24）。取り込みは §15.7。

- 書き出し先はアプリデータ直下の固定フォルダ `exports/`。ファイル名は `yuuko_transfer_<transferId>.zip`、`transferId` は `tr_<ローカル日時 YYYYMMDDhhmmss>`（同じ名前があれば `_2` 以降の連番を付け、既存のZIPは上書きしない）。Reactからパス・ファイル名は受け取らず、戻り値もファイル名と件数だけ。
- 含めるものは許可リストで決める（新しい秘密情報ファイルが既定で入らないようにするため）。

| 区分 | 含めるファイル |
|---|---|
| `config` | `config/settings.json` のみ |
| `news` | `news/<記事ID>.md` と `news/<月フォルダ>/<記事ID>.md`（名前は英数字・`-`・`_` のみ。それより深い階層は入れない） |
| `favorites` | `favorites/article_favorites.json` |
| `dictionary` | `dictionary/entries.json` |
| `user` | `user/friendship.json` |
| `rewards` | `rewards/rewards.json` |
| `gacha` | `gacha/gacha_state.json`（§12） |
| `archive` | `archive/archive_index.json` と `archive/YYYY-MM.zip`（月次ZIPは再圧縮せず無圧縮で格納） |

- 上記以外は入れない。特に `config/news_sources.json` / `config/network_allowlist.json`（ニュース取得の git 外設定）、`.env`・APIキー（環境変数で受け取りファイルに保存していない）、`logs/`・`cache/`、端末ごとの状態 `state/`、破損退避 `*.corrupt.json`、一時ファイル・退避ファイル（`*.tmp` / `*.bak` / `archive/.markdown-retirement.*`）、`exports/` 自身は含まない。
- `gacha/` は `gacha_state.json` だけを入れる。`gacha_state.corrupt.json`（破損退避）・`gacha_state.json.bak` / `.tmp`（保存途中の退避物）は入れない。`manifest.json` の `included` には区分 `gacha` が入る（区分の並びは `config` → `news` → `favorites` → `dictionary` → `user` → `rewards` → `gacha` → `archive`）。
- `gacha` 区分の追加で manifest の `version` は 1 のまま変えない。新しいアプリは `gacha` 区分を含まない従来のZIPもそのまま取り込める（後方互換）。一方、`gacha` 区分を含むZIPは、この変更より前のアプリでは「未知の区分」として取り込みを拒否する（現在のデータには触れずに失敗するので、データは壊れない）。
- シンボリックリンク（Windows のジャンクションを含む）は辿らず、実体のフォルダ配下の通常ファイルだけを入れる。
- `manifest.json` は §15.4 の項目のうち `version`（1）・`appVersion`・`transferId`・`createdAt`・`included`（1件以上入れた区分）・`encrypted`（false）を持ち、加えて `files`（`path` と `sizeBytes` の一覧、`manifest.json` 自身を除く）を持つ。`expiresAt` / `encryption` は Drive 経由の受け渡し用のため持たない。
- 各ファイルはZIPへストリームで書き込み、全体をメモリへ読み込まない。書き出しは同時に1件だけ実行する。
- `<最終名>.tmp` へ書き、再オープンしてエントリ数と `manifest.json` を確認できたものだけを最終名へ変える。途中で失敗したら一時ファイルを消す。前回の中断で残った `yuuko_transfer_*.zip.tmp` は次回の書き出し開始時に消す。
- 書き出し中に、計画したファイルが消えていた場合（同時に動くアーカイブ保守が記事を新しい月次ZIPへ移したなど）は、書き出し全体を失敗とする（一時ファイルを消してエラーを返す）。飛ばすとその記事がどの格納物にも入らないため。再実行すれば新しい状態で書き出せる。
- 古い書き出しZIPの自動削除は行わない。

### 15.7 ローカルZIP取り込み（実装済み・判断台帳 D41）
§15.6 で書き出したZIPを別のPCで取り込む（`list_migration_imports` / `import_migration_data`、`src-tauri/src/services/data_import_service.rs`）。画面（設定画面の導線）は別途実装する。

- 取り込み元はアプリデータ直下の固定フォルダ `imports/`。利用者がZIPをここへ置く。候補にするのは `yuuko_transfer_<英数字・-・_>.zip` という名前の通常ファイルだけ（シンボリックリンク・ジャンクション・フォルダは除く）。候補一覧は名前の降順で最大100件。戻り値はファイル名・大きさ・manifest の `createdAt`（RFC 3339 として読めたものを整形し直した値）だけで、フルパスは返さない。
- `import_migration_data` はファイル名だけを受け取り、名前規則に合い、かつ `imports/` の一覧に同じ名前の通常ファイルがあるときだけ開く（パス・`..`・区切り文字は受け付けない）。
- 受け付けるファイルは §15.6 の許可リストと同じ規則（書き出しと共通の判定関数）で決める。次のどれかに当たるZIPは取り込まない（現在のデータには触れない）。
  - `manifest.json` が無い・読めない・`version` が 1 でない・`encrypted` が true・`included` に未知の区分がある。
  - manifest の `files` とZIPのエントリが過不足なく一致しない（余分なエントリ・足りないエントリ・同じパスの重複）。
  - エントリ名が許可リスト外、または `/` 区切りの相対パスでない（絶対パス・ドライブ文字・`..`・`\`・空の区切り）。フォルダ・シンボリックリンクのエントリ、暗号化エントリ、無圧縮／deflate 以外の圧縮方式。
  - 大きさの上限を超える、またはヘッダ・manifest の `sizeBytes` と実際に展開したバイト数が一致しない。
  - JSON が読み込み時と同じ型として読めない（`config/settings.json` / `favorites/article_favorites.json` / `dictionary/entries.json` / `user/friendship.json` / `rewards/rewards.json` / `gacha/gacha_state.json` / `archive/archive_index.json`。`archive_index.json` は読み込み時と同じ整合チェックも行う）。記事Markdownは UTF-8 であること（Front Matter の破損は読み込み側が1件ずつ飛ばすため、取り込みでは拒否しない）。月次アーカイブZIPは展開せずそのまま置くが、ZIPとして開けること。

| 上限（ZIP爆弾対策） | 値 |
|---|---|
| 取り込みZIPファイルの大きさ | 4 GiB |
| エントリ数（`manifest.json` を含む） | 50,000 |
| 中央ディレクトリの大きさ | 64 MiB |
| 展開後の合計 | 4 GiB |
| `manifest.json` | 16 MiB |
| JSON 1ファイル | 64 MiB |
| 記事Markdown 1ファイル | 4 MiB |
| 月次アーカイブZIP 1ファイル | 1 GiB |

- エントリ数と中央ディレクトリの大きさは、ZIPの末尾レコード（ZIP64 を含む）を読んで中央ディレクトリを読み込む前に確かめる（末尾にコメント以外のデータが付いたZIPは受け付けない）。各ファイルの大きさは宣言値だけでなく実際に読んだバイト数で確かめる。月次アーカイブZIPにもエントリ数・中央ディレクトリの上限を同じく当てる。
- 手順: ① 検証しながらアプリデータ直下の一時フォルダ `.migration-import-staging/` へ展開する（前回の残りは消してから使う）。ここまでで失敗したら一時フォルダを消して終わる。② 記事・辞書・友情ランク・報酬・ガチャの書き込みと同じロックを取り（この順で取る。ガチャのサービスはロック中に他のサービスを呼ばないので最後に取る）、現在のデータを `migration-backups/<YYYYMMDDhhmmss>/` へ移す（自動バックアップ）。③ 展開したファイルを所定の場所へ移す。④ 一時フォルダを消す。
- 置き換える「現在のデータ」は §15.6 の許可リストに一致するファイルに加え、読み込み時に自動で戻される退避物（`*.json.bak` / `*.json.tmp`、`archive/YYYY-MM.zip.rollback` / `.tmp` / `.bak`、`archive/.markdown-retirement.rollback` / `.committed`）。取り込みに含まれない現在のデータも退避フォルダへ移る（全置き換え）。ガチャ状態を置き換えるときは `gacha/gacha_state.json.bak` / `.tmp` も一緒に退避する（古い退避物が次回の読み込みで復元されないようにするため）。`gacha_state.corrupt.json` は自動では戻されないので触らない。
- **仮の設計判断**: ガチャ状態（`gacha/gacha_state.json`）を含まないZIP（ガチャ保存の実装前に書き出したもの、または移行元でガチャを一度も使っていないもの）を取り込むときは、全置き換えの例外として、移行先の現在のガチャ状態とその退避物（`.bak` / `.tmp`）を退避も置き換えもせずにそのまま残す。獲得済みのものは他のデータから導出し直せず（§12.2）、古いZIPを取り込んだだけで失われるのを避けるため。ほかの区分は従来どおり全置き換え。`state/`・ニュース取得設定・`logs/`・`exports/`・`imports/` などは触らない。
- ②③の途中で失敗したら、置いたファイルを消して退避したものを元へ戻し、空になった退避フォルダを消す。退避フォルダには差し替え中だけ印（`.incomplete`）を置き、戻せなかった場合は印と退避フォルダを残す。印が残っている間は次の取り込みを始めない（そのフォルダにしか無いデータがあり得るため、手動で戻す）。
- 退避フォルダは最新の1世代だけ残す（成功後に、それより前の `YYYYMMDDhhmmss` 形式の退避フォルダを消す。それ以外の名前のフォルダは消さない）。取り込んだZIP自体は `imports/` に残す。
- 書き出しと取り込みは同じロックを共有し、同時には実行しない。設定（`settings.json`）の保存には書き込みロックが無いため、差し替え中に設定を保存すると取り込みが失敗（元へ戻す）または上書きされ得る。取り込み中は画面側で他の操作を止める想定とする。
- Rust 側のサービスは保存データをメモリに持たず毎回ファイルから読むが、画面が表示中の値・自動要約キューの記事ID・起動時の報酬同期は取り込み前のデータに基づくため、取り込み後はアプリの再起動を勧める（戻り値 `restartRequired` は常に true）。

## 16. ログ設計

## 16.1 基本方針
ログは必要最小限にする。

### 16.2 保存先と保存方針
```text
logs/app.log
```

- 配布ビルドでは、警告とエラーだけをアプリデータ直下の `logs/app.log` に保存する（D29。`tauri-plugin-log` の Folder 出力）。
- 1ファイルの上限は 1 MiB。超えたら `app_<日時>.log` へ退避し、退避ファイルは新しい順に4つまで残して古いものを自動で削除する（書き込み中の `app.log` と合わせて最大5世代）。
- ファイルへ書くのは自クレート（`app_lib`）のログだけとする。依存ライブラリの警告は URL やパスなど制御できない文字列を含みうるため残さない。
- パニック時は発生箇所（ファイル:行）だけを記録する（内容は外部由来の文字列を含みうるため記録しない）。
- ログ行の時刻と退避ファイル名の日時は UTC（プラグイン既定）。
- 開発ビルドは従来どおり Info 以上を標準出力と OS のログフォルダへ出す（プラグイン既定の出力先・サイズ）。
- ログを初期化できない場合も起動は止めず、ログなしで続行する。
- 実装: `src-tauri/src/infra/app_logging.rs`。

### 16.3 記録してよい情報
- アプリ起動 / 終了
- ニュース取得成功 / 失敗
- AI要約成功 / 失敗
- 用語解説成功 / 失敗
- 友情ポイント加算イベント
- アーカイブ処理成功 / 失敗
- Tauri command失敗概要
- エラー概要

### 16.4 記録してはいけない情報
- APIキー
- 認証情報
- 記事本文全文
- ユーザー選択文字列全文
- メール本文
- メール送信者情報
- Googleアカウント情報
- 復元キー
- ワンタイムパスコード
- URL（クエリを含みうるため）。取得先・記事URLを含むログは debug レベルにとどめ、配布ビルドのファイルには残さない

## 17. データバージョン管理

## 17.1 versionフィールド
JSONやMarkdown Front Matterには、可能な限り `version` またはスキーマ版数を持たせる。

```json
{
  "version": 1
}
```

### 17.2 マイグレーション
将来的に保存形式を変更する場合に備え、以下を検討する。

- 起動時にデータバージョンを確認
- 古い形式の場合は変換
- 変換前にバックアップ
- 変換失敗時は元データを維持
- 変換処理はRust側で行う

### 17.3 TypeScript側の扱い
React側では、マイグレーション済みのDTOを受け取ることを基本とする。  
React側で古い形式のデータ変換を行わない。

## 21. まとめ
本アプリは、基本データをローカルに保存し、ニュースと辞書を可読性の高い形式で管理する。

MVPでは、以下のデータ構造を優先して実装する。

- ニュースMarkdown
- ゆうこ辞書
- ユーザー設定
- 友情ランク
- ゆうこ通知状態
- お気に入り
- 既読状態
- AI要約メタ情報

Tauri版では、React / TypeScriptは表示用DTOを扱い、保存・読込・更新・アーカイブ・移行処理はRust側で担当する。  
ガチャ、Google Drive移行、詳細アーカイブは、将来的な拡張としてデータ構造の余地を残しつつ、MVP段階では過剰に作り込まない。
