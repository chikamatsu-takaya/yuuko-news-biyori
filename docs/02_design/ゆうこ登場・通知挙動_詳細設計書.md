# ゆうこ登場・通知挙動 詳細設計書_Tauri v1

## 1. 文書目的
本書は、AIニュースマスコットアプリ「ゆうこのニュース日和」における、マスコットキャラクター「ゆうこ」の登場、通知、退場、クリック挙動、抑制条件、状態管理をTauri版の実装前提で詳細化するための設計書である。

本アプリでは、ゆうこは単なる画面上の飾りではなく、以下の役割を持つ。

- ニュースをユーザーへ届ける
- ユーザーをメイン画面やニュース閲覧画面へ誘導する
- 用語解説や補足の起点になる
- 友情ランクや報酬通知を伝える
- 作業の邪魔にならない範囲で、親しみや継続利用性を生む

そのため、ゆうこの登場ロジックや通知頻度、抑制条件、クリック時挙動を明確にしておく必要がある。

本書は、以下を目的とする。

- ゆうこの登場条件を明確にする
- 通知が邪魔にならないよう抑制条件を整理する
- 2段階クリック方式の動きを定義する
- 報酬通知時の特殊挙動を定義する
- Rust側とReact側の責務を分離する
- Tauri commandで扱う境界を定義する
- MVPで実装する範囲と後続拡張を分ける

## 2. 前提

### 2.1 基本方針
ゆうこは、通常時は画面上に常時表示されるのではなく、バックグラウンド待機中に必要条件を満たした場合のみ画面端から登場する。

ただし、メイン画面やニュース閲覧画面など、ユーザーが明示的に画面を開いた状態では、画面内の一部として表示される。

### 2.2 位置づけ
本書では、ゆうこの表示状態を以下の2種類に分ける。

| 種別 | 内容 |
|---|---|
| 常駐時ゆうこ | バックグラウンド待機中に画面端から登場するゆうこ |
| 画面内ゆうこ | メイン画面、ニュース閲覧画面、辞書画面などに配置されるゆうこ |

本書の主対象は **常駐時ゆうこ** である。

### 2.3 Tauri版での前提
Tauri版では、以下の責務分離を基本とする。

| 領域 | 担当 |
|---|---|
| React / TypeScript | ゆうこの表示、登場・退場アニメーション、吹き出し、軽量プレビュー、クリック操作 |
| Rust | 登場条件判定、抑制条件判定、通知頻度管理、紹介ニュース選定、ポイント加算、報酬通知状態管理 |
| Tauri command | ReactからRust側状態・処理へアクセスする境界 |
| Markdown / JSON | 通知状態、紹介済み状態、報酬通知状態などのローカル保存 |

### 2.4 MVPでの扱い
MVPでは、すべての抑制条件や高度な状態判定を完全実装する必要はない。  
ただし、将来拡張で破綻しないよう、状態・責務・条件は先に整理しておく。

## 3. ゆうこの基本状態

## 3.1 状態一覧
ゆうこは、常駐時に以下の状態を持つ。

| 状態ID | 状態名 | 内容 |
|---|---|---|
| YS-001 | 非表示 | 画面上にゆうこが表示されていない |
| YS-002 | 待機中 | 条件判定中。表示はしていない |
| YS-003 | 抑制中 | 条件により登場を抑制している |
| YS-004 | 登場準備中 | 登場条件を満たし、表示位置や紹介ニュースを決定中 |
| YS-005 | 登場中 | 画面端からゆうこが出てくるアニメーション中 |
| YS-006 | 吹き出し表示中 | 短い誘い文を表示して待機 |
| YS-007 | 軽量プレビュー表示中 | 初回クリック後、ニュース軽量プレビューを表示 |
| YS-008 | 退場中 | 画面外へ戻るアニメーション中 |
| YS-009 | 画面遷移待ち | メイン画面またはニュース閲覧画面へ遷移する直前 |
| YS-010 | 報酬通知中 | ランクアップや報酬獲得を通知中 |
| YS-011 | 一時停止中 | ユーザー操作により通知停止中 |

### 3.2 基本状態遷移
```text
非表示
  ↓
待機中
  ↓ 条件成立
登場準備中
  ↓
登場中
  ↓
吹き出し表示中
  ↓ 初回クリック
軽量プレビュー表示中
  ↓ 詳しく見る / 再クリック
退場中
  ↓
画面遷移待ち
  ↓
メイン画面 または ニュース閲覧画面
```

抑制条件に該当する場合は、待機中から登場準備中へ進まず、抑制中へ移る。

```text
待機中
  ↓ 抑制条件あり
抑制中
  ↓ 抑制解除
待機中
```

## 4. 登場条件

## 4.1 基本登場条件
ゆうこが画面端から登場するには、以下の条件を満たす必要がある。

| 条件 | MVP | 内容 |
|---|---|---|
| 通知設定ON | 必須 | ユーザーが通知を許可している |
| おすすめニュースあり | 必須 | 紹介可能なニュース候補が存在する |
| 通知時間帯内 | 必須 | 設定された時間帯内である |
| 日次通知上限未到達 | 必須 | 1日の通知回数上限に達していない |
| クールタイム経過 | 必須 | 前回通知から一定時間経過している |
| 抑制条件なし | 必須 | フルスクリーン等に該当しない |
| ユーザー一時停止中でない | 必須 | 一時停止設定が無効 |
| アプリがバックグラウンド待機中 | 必須 | メイン画面などが前面に出ていない |

### 4.2 登場トリガー
ゆうこの登場契機は以下を候補とする。

| トリガー | MVP | 内容 |
|---|---|---|
| 起動時ニュース取得後 | 必須 | 起動時におすすめ候補がある場合 |
| 指定時間帯内ランダム | 重要 | 勤務時間帯内でランダムに登場 |
| 新着ニュース取得後 | 重要 | 日付変更時のニュース取得後 |
| 一定時間無操作 | 後続 | ユーザー操作が一定時間ない場合 |
| ランクアップ報酬通知 | 重要 | 報酬未通知状態がある場合 |
| 手動デモトリガー | MVP用 | 発表や開発確認用 |

### 4.3 MVPでの登場条件
MVPでは、以下を満たせば登場可能とする。

```text
通知ON
AND おすすめニュースあり
AND 通知時間帯内
AND 日次通知上限未到達
AND クールタイム経過
AND 簡易抑制条件なし
```

MVPでは、マイク使用中や特定アプリ検知などの高度な判定は未実装でもよい。

### 4.4 Rust側判定方針
登場条件の判定はRust側で行う。

React側で判定してよいもの:
- 現在表示中のUI状態
- アニメーション中かどうか
- ユーザーが閉じるボタンを押したかどうか

React側で判定してはいけないもの:
- 日次通知上限
- クールタイム
- 紹介済み管理
- 友情ポイント加算
- 報酬通知確定
- ファイル保存を伴う状態更新

## 5. 抑制条件

## 5.1 基本方針
ゆうこは、ユーザーの作業を邪魔しないことを最優先とする。  
以下に該当する場合、登場を抑制する。

## 5.2 抑制条件一覧

| 抑制条件 | MVP | 内容 |
|---|---|---|
| 通知OFF | 必須 | ユーザーが通知を無効にしている |
| 通知時間帯外 | 必須 | 設定された通知時間外 |
| 日次通知上限到達 | 必須 | その日の通知回数が上限に到達 |
| クールタイム中 | 必須 | 前回通知から十分な時間が経っていない |
| 一時停止中 | 必須 | ユーザーが一時停止している |
| フルスクリーン中 | 重要 | フルスクリーンアプリが存在する |
| マイク使用中 | 後続 | 会議中の可能性がある |
| 抑制対象アプリ起動中 | 後続 | ユーザー指定アプリが起動中 |
| PCスリープ復帰直後 | 後続 | すぐに出ないよう猶予を置く |
| 発表・プレゼンモード | 後続 | 発表中は抑制する |
| メイン画面表示中 | 必須 | すでにメイン画面が前面にある |
| ニュース閲覧画面表示中 | 必須 | すでに閲覧中の場合は通知しない |

### 5.3 抑制中の扱い
抑制条件に該当した場合、通知候補は即破棄せず、以下の扱いを検討する。

| 種別 | 扱い |
|---|---|
| ニュース紹介 | 次回判定まで保留 |
| 報酬通知 | 報酬未通知状態を維持 |
| ランクアップ通知 | 抑制解除後に再通知 |
| 手動通知 | ユーザー操作なら表示可能 |

### 5.4 抑制解除後
抑制解除後は、すぐに登場するのではなく短い猶予を置く。

初期案:

```text
抑制解除後 30秒〜180秒 のランダム猶予
```

これにより、会議終了直後やフルスクリーン解除直後に即座に登場する違和感を避ける。

## 6. 通知頻度制御

## 6.1 基本方針
ゆうこは可愛いが、しつこくならないことを重視する。  
通知頻度は、日次上限・時間あたり上限・クールタイムで制御する。

## 6.2 通知回数上限

| 項目 | 初期案 | 備考 |
|---|---:|---|
| 1日最大通知回数 | 3回 | MVP初期値 |
| 1時間最大通知回数 | 1回 | 後続でも可 |
| 最短クールタイム | 60分 | 前回通知からの間隔 |
| 閉じられた後の再通知抑制 | 120分 | ユーザーが閉じた場合 |
| 無視された後の再通知抑制 | 180分 | 放置された場合 |

### 6.3 通知カウント対象
通知回数に含めるもの。

- ニュース紹介通知
- 報酬通知
- ランクアップ通知

通知回数に含めない候補。

- ユーザーが手動で呼び出した場合
- メイン画面内のゆうこ表示
- ニュース閲覧画面内のゆうこ表示

### 6.4 通知優先度
複数の通知候補がある場合、以下の優先順位とする。

1. 報酬未通知 / ランクアップ通知
2. 重要度が高いニュース
3. 驚き要素が高いニュース
4. ユーザー関心に合うニュース
5. 新着ニュース

ただし、報酬通知ばかりにならないよう、報酬通知も回数上限やクールタイムの対象とする。

## 7. 登場位置・退場位置

## 7.1 登場位置候補
ゆうこは画面端から登場する。

| 位置ID | 位置 | MVP | 備考 |
|---|---|---|---|
| POS-001 | 右下 | 推奨 | 邪魔になりにくい |
| POS-002 | 左下 | 候補 | タスクバー位置によって調整 |
| POS-003 | 右端中央 | 候補 | 吹き出しと相性がよい |
| POS-004 | 左端中央 | 候補 | 将来設定候補 |
| POS-005 | 上端 | 非推奨 | 通知やメニューバーと干渉しやすい |

### 7.2 MVPでの基本位置
MVPでは、**右下から登場** を基本とする。

理由:
- 通知領域に近く、補助アプリらしい
- 画面中央の作業領域を邪魔しにくい
- 吹き出しを左上方向へ出しやすい

### 7.3 Tauri版での位置制御
Tauri版では、実装段階で以下のどちらかを選択する。

#### 案A: メインウィンドウ内に常駐レイヤーを持つ
- 実装が簡単
- MVP向け
- アプリウィンドウ表示中の演出に向く
- デスクトップ全体の右下通知には弱い

#### 案B: 常駐ゆうこ用の小型Tauriウィンドウを別に持つ
- デスクトップマスコットらしい動きが可能
- 右下からの登場と相性が良い
- 常駐アプリらしさが出る
- ウィンドウ透過や最前面制御などの考慮が増える

MVPでは、まず案Aまたは簡易的な案Bで検証し、最終方式を詳細実装時に決定する。

### 7.4 タスクバー考慮
Windowsでは、タスクバー位置により右下が使いづらい場合がある。  
MVPでは固定でもよいが、後続で以下を検討する。

- タスクバー位置の検出
- 作業領域サイズの取得
- 画面端から少し内側にずらす
- マルチモニタ対応

### 7.5 退場位置
退場時は、登場した画面端へ戻ることを基本とする。

例:

```text
右下から登場 → 右下へ退場
左下から登場 → 左下へ退場
```

報酬通知時など、演出上必要な場合のみ、一度画面外に歩いてから再登場する。

## 8. 登場アニメーション

## 8.1 基本方針
ゆうこの登場は「ぴょこっと出る」印象を重視する。  
ただし、常駐アプリとして軽量性を優先し、過度な演出は避ける。

## 8.2 MVPアニメーション
MVPでは、以下の簡易アニメーションでよい。

| 項目 | 初期案 |
|---|---|
| 登場時間 | 0.4〜0.8秒 |
| 退場時間 | 0.3〜0.6秒 |
| 吹き出し表示遅延 | 0.2秒 |
| 待機時揺れ | なし、または非常に小さく |
| 表情差分 | なし、または1種類 |
| サウンド | なし |

### 8.3 登場アニメーション案
```text
1. 画面外にゆうこを配置
2. XまたはY方向にスライドして少しだけ画面内へ出る
3. 少しだけオーバーシュート
4. 定位置へ戻る
5. 吹き出し表示
```

### 8.4 退場アニメーション案
```text
1. 吹き出しをフェードアウト
2. ゆうこが少し振り返る、または小さく跳ねる
3. 画面外へスライド
4. 非表示状態へ戻す
```

### 8.5 React実装方針
- CSS animationまたは軽量なReactアニメーションで実装する。
- MVPではCSS transition / keyframesを優先する。
- アニメーション状態はReact側で管理する。
- 通知条件や通知回数はReact側で管理しない。
- 無限アニメーションは避ける。
- 非表示時はアニメーションを停止する。

### 8.6 軽量性注意
- 常時アニメーションは避ける。
- 60fps前提にしすぎない。
- Live2D等の高度演出はMVPでは対象外。
- 画像差分やシンプルなCSSアニメーションで十分とする。

## 9. 吹き出し表示

## 9.1 目的
吹き出しは、ゆうこの発話、ニュース誘導、報酬通知を短く表示するために使う。

## 9.2 表示内容
| 種別 | 例 |
|---|---|
| ニュース紹介 | 「気になるAIニュース、見つけたよ」 |
| 追加誘導 | 「ちょっとだけ見ていかない？」 |
| 報酬通知 | 「ランクアップしたみたい！」 |
| 抑制解除後 | 「今なら少しだけ話してもいいかな？」 |
| エラー時 | 「うまく取れなかったみたい」 |

### 9.3 表示ルール
- 1回の吹き出しは短くする。
- 長文を表示しない。
- 最大2行〜3行程度を想定する。
- 吹き出しには閉じるボタンを付ける。
- 一定時間無操作で自動退場する。
- HTMLとして描画しない。
- AI出力をそのままリンク化しない。

### 9.4 自動退場時間
初期案:

| 状態 | 自動退場時間 |
|---|---:|
| 吹き出し表示中 | 20秒 |
| 軽量プレビュー表示中 | 30秒 |
| 報酬通知中 | 自動退場なし、または60秒 |

報酬通知はユーザー確認が必要なため、OK操作まで残す方式を優先する。

## 10. 2段階クリック方式

## 10.1 基本方針
ゆうこ通知では、いきなりメイン画面を開かない。  
まず軽いプレビューを表示し、ユーザーが興味を持った場合に詳細画面へ遷移する。

### 10.2 基本フロー
```text
ゆうこ登場
  ↓
吹き出し表示
  ↓ 初回クリック
ニュース軽量プレビュー表示
  ↓ 再クリック / 詳しく見る
ゆうこ退場
  ↓
メイン画面 または ニュース閲覧画面へ遷移
```

### 10.3 初回クリック
初回クリック時には、以下を表示する。

- ニュースタイトル
- 短い追加要約
- ゆうこの一言
- 詳しく見るボタン
- 閉じるボタン

### 10.4 再クリック
再クリック、または「詳しく見る」押下時には、以下を行う。

1. 軽量プレビューを閉じる
2. React側で退場アニメーションを開始する
3. Rust側へクリック確定を通知する
4. Rust側で紹介済み管理と友情ポイント加算を行う
5. 遷移先を決定する
6. メイン画面またはニュース閲覧画面を表示する

### 10.5 遷移先
MVPでは以下を候補とする。

| 条件 | 遷移先 |
|---|---|
| 紹介ニュースが1件 | ニュース閲覧画面 |
| 複数ニュースを見せたい | メイン画面 |
| デモ時 | ニュース閲覧画面へ直接 |

初期開発では、ニュース閲覧画面へ直接遷移の方がデモしやすい。

### 10.6 閉じる / 無視
| 操作 | 挙動 |
|---|---|
| 閉じる | ゆうこ退場、クールタイム設定 |
| 無操作タイムアウト | ゆうこ退場、無視扱い |
| Escキー | 閉じると同等 |
| 右クリック | 後続でメニュー表示候補 |

閉じる、無視、詳しく見るの結果はRust側へ通知し、次回通知判定に利用する。

## 11. 報酬通知時の特殊挙動

## 11.1 基本方針
友情ランク上昇や報酬獲得は、ニュース紹介とは異なる特別な通知として扱う。

### 11.2 ランクアップ後の状態
ランクアップ条件を満たした場合、即時で報酬を正式獲得にしない。  
まず以下の状態へ遷移する。

```text
ランクアップ可能
  ↓
報酬未通知
  ↓ ゆうこ通知
報酬通知中
  ↓ OK押下
報酬確認済み
```

### 11.3 ゆうこが非表示の場合
ゆうこが画面上にいない場合。

```text
非表示
  ↓
登場準備中
  ↓
報酬通知として登場
  ↓
ランクアップ通知モーダル
```

### 11.4 ゆうこがすでに表示中の場合
ゆうこがすでに画面上にいる場合。

```text
表示中
  ↓
一度退場
  ↓
短い間隔を置く
  ↓
報酬通知として再登場
  ↓
ランクアップ通知モーダル
```

### 11.5 OK押下
ユーザーがOKを押した時点で、正式に報酬を獲得した扱いにする。

処理:
- pendingRewardIdsから削除
- confirmedRewardIdsへ追加
- 必要ならカスタマイズ設定に反映
- トーストまたはゆうこの一言を表示

この確定処理はRust側で行う。  
React側はOK操作を受け付け、Tauri commandを呼び出す。

### 11.6 MVPでの扱い
MVPでは、以下で十分とする。

- ランクアップ通知モーダル表示
- 新ランク表示
- ゆうこの祝福コメント
- OK押下で確認済み
- 報酬詳細はダミーまたは文言のみ

## 12. ニュース選定ロジックとの連携

## 12.1 基本方針
ゆうこは、当日のおすすめ候補からニュースを選び、ユーザーへ紹介する。

## 12.2 候補選定優先度
候補ニュースは以下を考慮して選ぶ。

1. 未紹介
2. 未読
3. おすすめスコアが高い
4. 重要度が高い
5. 驚き要素が高い
6. ユーザー関心に合う
7. 新しい

### 12.3 紹介済み管理
ゆうこが紹介した記事には、紹介済みフラグを付与する。

```json
{
  "introducedByYuuko": true,
  "introducedAt": "2026-04-28T10:20:00+09:00"
}
```

### 12.4 再紹介
同じ記事を繰り返し紹介しすぎない。

初期案:

| 条件 | 再紹介可否 |
|---|---|
| 同日紹介済み | 原則不可 |
| ユーザーが閉じた | 当日は優先度を下げる |
| ユーザーが無視した | 当日は優先度を下げる |
| 重要度が非常に高い | 後続で再紹介候補 |
| お気に入り済み | 紹介不要 |

### 12.5 Rust側責務
- 紹介候補選定
- 紹介済みフラグ更新
- 閉じられた記事の優先度低下
- 無視された記事の優先度低下
- ニュース閲覧への遷移時のポイント加算判定

---

## 13. 友情ポイント連携

## 13.1 加算対象
ゆうこの常駐通知に関連する友情ポイント加算対象は以下。

| 行動 | ポイント | 備考 |
|---|---:|---|
| ゆうこ経由でメイン画面へ遷移 | 5pt | 既定 |
| ゆうこ経由でニュース閲覧画面へ遷移 | 5ptまたは3pt | 調整候補 |
| ニュース詳細表示 | 3pt | 通常閲覧 |
| 再説明表示 | 4pt | 詳細な閲覧 |
| 用語解説利用 | 1pt | 小ポイント |

### 13.2 MVPでの加算方針
MVPでは、ゆうこ通知経由でニュース閲覧画面に進んだ場合も、`YuukoToMain` 相当として5pt扱いでよい。

### 13.3 日次上限
友情ポイントは日次上限25ptを超えて加算しない。

### 13.4 連打防止
同一記事・同一導線で短時間にポイントが重複加算されないようにする。

例:

```text
同一 articleId + eventType は1日1回まで
```

連打防止とポイント加算はRust側で管理する。

## 16. エラー・例外時の挙動

## 16.1 ニュース候補がない
| 条件 | 挙動 |
|---|---|
| おすすめニュースなし | ゆうこは登場しない |
| 報酬通知あり | 報酬通知として登場可能 |
| 手動呼び出し | 「今は紹介できるニュースがないよ」表示 |

## 16.2 アニメーション失敗
- 表示位置だけ更新し、アニメーションなしで表示してよい。
- アプリ全体を止めない。

## 16.3 状態不整合
- 不正状態になった場合は非表示または待機中へ戻す。
- エラー概要だけログに残す。
- ユーザーに大量の技術エラーを見せない。

## 16.4 遷移失敗
- メイン画面またはニュース閲覧画面への遷移に失敗した場合、ゆうこは退場せず、軽いエラー吹き出しを出す。
- 再試行または閉じる操作を可能にする。

## 16.5 Tauri command失敗
- React側はクラッシュさせず、エラートーストまたは吹き出しで表示する。
- Rust側は原因調査に必要な最小限をログに残す。
- APIキー、本文全文、選択文字列全文はログに残さない。

## 21. まとめ
ゆうこの登場・通知挙動は、本アプリの体験価値を大きく左右する中核機能である。

MVPでは、以下を成立させることを最優先とする。

```text
右下からゆうこが登場
  ↓
短い吹き出しでニュース紹介
  ↓
初回クリックで軽量プレビュー
  ↓
詳しく見るでニュース閲覧画面へ
  ↓
友情ポイント加算
```

Tauri版では、React / TypeScriptがゆうこの表示・アニメーション・クリック操作を担当し、Rust側が通知条件、抑制条件、通知回数、紹介ニュース選定、ポイント加算、報酬通知管理を担当する。  
後続では、抑制条件、報酬通知演出、登場位置設定、マルチモニタ対応、Live2D演出などを段階的に追加する。
