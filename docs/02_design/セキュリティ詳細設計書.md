# セキュリティ詳細設計書 v1

## 1. 文書目的
本書は、AIニュースマスコットアプリ「ゆうこのニュース日和」におけるセキュリティ方針を、Tauri版の実装前に確認できる粒度まで詳細化するための資料である。

本アプリは、ニュース取得、HTML本文抽出、AI要約、用語解説、ローカル保存、将来的なGoogle Driveデータ移行、Google連携など、外部通信やユーザーデータを扱う機能を含む。  
そのため、初期開発段階から以下を明確にする。

- 何を外部送信してよいか
- 何を送信してはいけないか
- どの通信先を許可するか
- HTMLやMarkdownを安全に扱う方法
- APIキーや認証情報の扱い
- Tauri commandとして公開してよい処理と避けるべき処理
- React側へ渡してよい情報と渡してはいけない情報
- ログに残してよい情報と残してはいけない情報
- データ移行時の暗号化方針
- AI駆動開発時に注意すべきセキュリティ境界

本書は、要件定義書、AI利用方針資料、データ設計書、開発環境構築手順書、AGENT.md、Git運用ルールとあわせて利用する。

## 2. セキュリティ基本方針

### 2.1 基本思想
本アプリのセキュリティ方針は、以下を基本とする。

- 必要な情報だけを扱う
- 必要な通信だけを行う
- 外部送信する情報を最小化する
- ローカルデータを不用意に外部へ出さない
- HTMLやMarkdownをそのまま信用しない
- APIキーや認証情報をコードやログに残さない
- React側に秘密情報を渡さない
- Tauri commandを必要最小限にする
- 失敗時は安全側へ倒す
- 初期版では高リスク機能を無理に実装しない

### 2.2 セキュリティ設計の優先順位
1. ユーザーデータと認証情報を守る
2. AI送信データを最小化する
3. 外部通信先を制御する
4. Tauri commandの公開範囲を制御する
5. HTML / Markdown由来の表示リスクを抑える
6. ログや一時ファイルに危険情報を残さない
7. 将来拡張時にも安全な構造にする

### 2.3 MVP段階の方針
MVPでは、以下を必須とする。

- AI送信対象データの制限
- APIキーの直書き禁止
- APIキーをReact側へ渡さない
- HTML生表示禁止
- Markdown表示時の危険要素無効化
- RSS取得先の管理
- Tauri commandの入力検証
- ログ出力の制限
- MockProviderでAIなしでも動作確認可能にする

以下はMVPでは原則対象外とする。

- Google Driveデータ移行の本実装
- Googleメール連携の本実装
- 本格的な管理者向け監査ログ
- 高度な認証基盤
- ローカルデータ全体の暗号化

## 3. 保護対象

### 3.1 守るべき情報
本アプリで保護対象とする情報は以下である。

| 分類 | 例 | 扱い |

| 認証情報 | Google OAuthトークン、Drive連携情報 | 秘密情報 |
| ユーザー設定 | 通知時間帯、興味カテゴリ、テーマ設定 | ローカル保存 |
| 閲覧履歴 | 読んだニュース、既読状態 | ローカル保存 |

| ガチャ情報 | 流れ星のかけら、所持アイテム | ローカル保存 |
| ニュースデータ | タイトル、出典、URL、本文抜粋、AI要約 | ローカル保存 |
| 移行データ | 暗号化ZIP、復元キー | 高注意 |
| ログ | エラー概要、処理結果 | 最小限 |

### 3.2 特に外部送信を避ける情報
以下は、初期版では外部AIへ送信しない。

- Google連携で取得したメール本文
- メール件名
- メール送信者情報
- Googleアカウント情報
- 閲覧履歴全量
- ゆうこ辞書全量
- ユーザー設定全量
- ローカル保存データ全体
- APIキー
- OAuthトークン
- ワンタイムパスコード
- 復元キー
- ログファイル
- 社内機密に該当しうる情報

### 3.3 React側へ渡さない情報
以下はReact / TypeScript側へ渡してはならない。

- APIキー
- OAuthトークン
- Google認証情報
- 復元キー
- ワンタイムパスコードの内部生成元
- AIへ送信した全文
- ログ全文
- OS資格情報
- ローカルファイルの絶対パス全量

React側へ渡す場合は、表示用DTOへ変換し、必要最低限の情報だけにする。

## 4. Tauri構成におけるセキュリティ境界

### 4.1 基本境界
Tauri版では、React / TypeScriptとRustの間に明確な境界を置く。

```text
React / TypeScript
  - 画面表示
  - ユーザー操作
  - 一時的なUI状態
  - Tauri command呼び出し

Rust
  - 外部通信
  - AI API呼び出し
  - APIキー参照
  - ファイル保存
  - 状態確定
  - 入力検証
  - ログ制御
```

### 4.2 React側で行ってよいこと
- 画面表示
- ボタン操作
- 入力フォーム
- 一時的なフィルタ
- 一時的な選択状態
- Tauri command呼び出し
- 表示用エラーメッセージ
- アニメーション
- モーダル表示

### 4.3 React側で行ってはいけないこと
- APIキー管理
- AI API直接呼び出し
- RSS / HTML直接取得
- 任意ファイル読み書き
- ローカル保存データの直接更新
- 通知回数や友情ポイントの確定更新
- 外部通信先の最終判断
- 危険HTMLの表示
- 認証トークンの保持

### 4.4 Rust側で行うこと
- URL検証
- 許可リスト判定
- RSS取得
- HTML取得
- AI送信データの最小化
- Gemini API呼び出し
- MockProvider切替
- Markdown / JSON保存
- 通知状態保存
- 友情ポイント確定
- ログ出力制御
- データ移行時のZIP / 暗号化処理

## 5. Tauri command安全設計

### 5.1 基本方針
Tauri commandはReactからRust側処理を呼び出す公開口である。  
公開口が広がるほど危険度が上がるため、commandは必要最小限とする。

### 5.2 許可するcommandの性質
許可するcommandは、アプリ固有の操作に限定する。

例:

| command | 用途 |
|---|---|
| `get_recommended_articles` | おすすめニュース一覧取得 |
| `get_article_detail` | 記事詳細取得 |
| `generate_article_summary` | 記事要約生成 |
| `update_article_favorite` | お気に入り切替 |
| `explain_selected_term` | 用語解説 |
| `list_dictionary_entries` | 辞書一覧取得 |
| `save_user_settings` | 設定保存 |
| `get_yuuko_notification_state` | ゆうこ通知状態取得 |
| `dismiss_yuuko_notification` | ゆうこ通知を閉じた記録 |
| `draw_gacha_once` | ガチャ実行 |

### 5.3 避けるべきcommand
以下のような汎用的すぎるcommandは禁止または強く非推奨とする。

| 禁止command例 | 理由 |
|---|---|
| `read_any_file(path)` | 任意ファイル読み取りにつながる |
| `write_any_file(path, content)` | 任意ファイル書き込みにつながる |
| `fetch_any_url(url)` | SSRFや危険URL取得につながる |
| `execute_command(command)` | OSコマンド実行につながる |
| `get_env_value(name)` | APIキー漏洩につながる |
| `open_any_path(path)` | ローカルファイル露出につながる |

### 5.4 command入力検証
すべてのcommandはRust側で入力検証を行う。

検証対象:
- articleId
- dictionaryId
- selectedText
- URL
- 設定値
- ファイルID
- rewardId
- gacha count
- provider name

### 5.5 command戻り値制御
commandの戻り値には、以下を含めない。

- APIキー
- 認証トークン
- 絶対パス
- ログ全文
- AI送信全文
- ローカルファイル全文
- メール本文
- Googleアカウント情報

### 5.6 Tauri capability / permission方針
Tauriの権限設定は最小限にする。

- 使わないAPI権限を付与しない
- ファイルシステム系権限は慎重に扱う
- shell系、process系の権限は原則避ける
- 外部URLを開く処理は専用の安全な処理に限定する
- プラグイン追加時はcapability設定をレビューする

## 6. 外部通信設計

### 6.1 外部通信の種類
本アプリで想定する外部通信は以下である。

| 通信種別 | 用途 | MVP対象 | 実装担当 |
|---|---|---|---|
| RSS取得 | ニュース候補取得 | 対象 | Rust |
| 記事HTML取得 | 本文または本文抜粋抽出 | 対象 | Rust |
| Gemini API | 要約・用語解説 | 対象 | Rust |
| OpenAI API | 将来のAI Provider | 対象外 | Rust |
| Google Drive API | データ移行 | 対象外 | Rustまたは専用連携層 |
| Google Mail系API | メール通知補助 | 対象外 | Rustまたは専用連携層 |

React側から直接外部通信しないことを基本とする。

### 6.2 許可リスト方式
外部通信先は、許可リスト方式で管理する。

#### 許可リスト対象
- RSS取得ドメイン
- 記事HTML取得ドメイン
- AI API接続先
- 将来のGoogle API接続先

#### 許可リスト管理例
```json
{
  "version": 1,
  "allowedRssDomains": [
    "example.com",
    "news.example.jp"
  ],
  "allowedArticleDomains": [
    "example.com",
    "news.example.jp"
  ],
  "allowedAiEndpoints": [
    "generativelanguage.googleapis.com"
  ],
  "blockedSchemes": [
    "file",
    "ftp",
    "data",
    "javascript"
  ]
}
```

### 6.3 拒否すべきURL
以下は取得対象から拒否する。

- `file://`
- `javascript:`
- `data:`
- `ftp://`
- `localhost`
- `127.0.0.1`
- `0.0.0.0`
- `::1`
- プライベートIPアドレス
- 社内ネットワークアドレス
- 不明なリダイレクト先
- 許可リスト外ドメイン

### 6.4 リダイレクト時の扱い
記事取得時にリダイレクトが発生する場合、リダイレクト先も許可リストで確認する。

- 許可リスト内: 取得継続
- 許可リスト外: 取得中止
- 危険スキーム: 取得中止

### 6.5 通信失敗時
通信失敗時は、アプリ全体を停止させない。

| 失敗箇所 | 挙動 |
|---|---|
| RSS取得失敗 | 既存ローカルニュースを表示 |
| HTML取得失敗 | タイトル、出典、URL中心で保存 |
| AI API失敗 | Mockまたは要約なし状態で表示 |
| Drive通信失敗 | 移行処理を中止し、ローカルデータは維持 |

## 7. AI送信データ設計

### 7.1 AI送信の基本方針
AIへ送る情報は、要約や解説に必要な最小限のテキストに限定する。  
AI送信の最終制御はRust側で行う。

### 7.2 AIへ送ってよい情報
初期版でAIへ送信してよい情報は以下に限定する。

| 情報 | 用途 |
|---|---|
| ニュースタイトル | 要約・再説明 |
| 出典名 | 文脈補助 |
| 記事本文抜粋 | 要約 |
| 整形済みMarkdownの一部 | 要約 |
| ユーザー選択語句 | 用語解説 |
| 選択語句の前後文脈 | 用語解説補助 |
| 解説レベル | 出力調整 |
| ゆうこの口調設定ID | 文体調整 |

### 7.3 AIへ送ってはいけない情報
以下はAI送信対象外とする。

- メール本文
- メール件名
- メール送信者
- Googleアカウント情報
- APIキー
- OAuthトークン
- ユーザー設定全量
- 閲覧履歴全量
- ゆうこ辞書全量
- ローカルファイル全文
- ログ全文
- Drive移行用データ
- ワンタイムパスコード
- 復元キー

### 7.4 AI入力サイズ制限
AIへの入力は、上限を設ける。

初期案:

| 用途 | 入力上限目安 |
|---|---:|
| ニュース要約 | 2,000〜4,000文字程度 |
| ゆうこの再説明 | 2,000〜4,000文字程度 |
| 用語解説 | 選択語句 + 周辺文脈500〜1,000文字程度 |
| 長文要点説明 | 2,000文字程度 |

上限を超える場合は、先頭・中間・末尾などをルールベースで抽出する。

### 7.5 AI出力の扱い
AI出力は、そのまま危険なHTMLとして扱わない。

- Markdown表示時は危険HTMLを無効化する
- リンク生成を制限する
- AIが出したURLを自動で開かない
- AI出力をファイル名に直接使わない
- 断定しすぎる表現はプロンプト側で抑制する
- React側ではテキスト表示を基本とする

### 7.6 AI Provider切替
MVPでは以下を用意する。

- MockProvider
- GeminiApiProvider

将来候補:

- OpenAiApiProvider
- LocalModelProvider

Provider切替時も、AI送信データ最小化ルールは共通で適用する。

## 8. APIキー・認証情報管理

### 8.1 基本方針
APIキーや認証情報は、コード、Git、ログ、Markdown資料に残さない。  
React側へ渡さず、Rust側でのみ参照する。

### 8.2 Gemini APIキー
開発段階では、Gemini APIキーは環境変数で扱う。

例:

```text
GEMINI_API_KEY
```

### 8.3 保存禁止場所
APIキーやトークンを以下に保存してはいけない。

- ソースコード
- Git管理対象ファイル
- Markdown設計資料
- ログ
- スクリーンショット
- 通常のJSON設定ファイル
- エラー表示
- Google Drive移行ZIP
- React state
- localStorage / sessionStorage

### 8.4 将来的な保存候補
本格運用時は、以下の利用を検討する。

- OSの資格情報ストア
- Windows Credential Manager
- 暗号化設定領域
- 会社が承認した秘密情報管理方式

### 8.5 APIキー未設定時
APIキー未設定時は、以下のいずれかとする。

- MockProviderへ自動切替
- 設定画面で警告表示
- AI機能のみ一時無効化

アプリ全体は停止させない。

### 8.6 設定画面での扱い
設定画面には、APIキーそのものを表示しない。  
表示する場合は、以下のような状態のみとする。

- 未設定
- 設定済み
- 接続確認成功
- 接続確認失敗

## 9. RSS・HTML取得の安全設計

### 9.1 RSS取得
RSS取得では以下を守る。

- 許可リスト内のRSSのみ取得する
- 取得結果をそのまま信用しない
- タイトル、概要、URLはサニタイズする
- 外部URLは取得前に検証する
- 同一URLの重複を避ける
- React側からRSS URLを自由入力させない

### 9.2 HTML取得
HTML取得では以下を守る。

- 許可リスト内URLのみ取得する
- 危険スキームを拒否する
- リダイレクト先を検証する
- スクリプトや埋め込み要素は利用しない
- HTMLをそのまま表示しない
- 本文または本文抜粋だけを抽出対象とする
- 抽出本文はAI送信前に長さ制限する

### 9.3 HTML抽出失敗時
HTML抽出に失敗した場合は、以下の情報のみで記事データを作成可能とする。

- タイトル
- 出典
- URL
- 取得日時
- RSS概要

失敗したHTMLをそのまま保存・表示しない。

## 10. Markdown / React表示の安全設計

### 10.1 基本方針
Markdownは内部保存形式として扱うが、表示時には安全化を行う。  
React側では、原則として安全化済みテキストや構造化データを表示する。

### 10.2 無効化する要素
Markdown表示では、以下を無効化または制限する。

- 埋め込みHTML
- `<script>`
- `<iframe>`
- `<object>`
- `<embed>`
- `javascript:` リンク
- `data:` リンク
- 自動実行される可能性がある埋め込み
- 外部画像の自動読み込み

### 10.3 React表示時の禁止事項
React側では以下を原則禁止する。

- `dangerouslySetInnerHTML`
- AI出力HTMLの直接描画
- 外部HTMLの直接描画
- AI出力URLの自動リンク化
- ユーザー入力をHTMLとして描画
- 外部由来文字列をCSSやstyleへ無検証で反映

### 10.4 リンク表示
リンクは以下のルールで扱う。

- 元記事リンクのみ明示表示する
- AI出力内リンクは自動リンク化しない、または確認を挟む
- 外部リンクを開く場合はユーザー操作を必須にする
- リンク先URLを表示または確認可能にする
- URL検証はRust側で行う

### 10.5 ファイル名への反映禁止
外部由来文字列をファイル名に直接使わない。

禁止例:
- 記事タイトルをそのままファイル名にする
- AI出力をそのままファイル名にする
- ユーザー選択文字列をそのままファイル名にする

代わりに、IDやハッシュ値を使用する。

## 11. ローカル保存データの安全設計

### 11.1 保存場所
ローカルデータは、Tauriのアプリケーションデータ領域配下に保存する。

例:

```text
YuukoAppData/
  config/
  news/
  dictionary/
  user/
  rewards/
  gacha/
  archive/
  logs/
```

### 11.2 保存データの扱い
保存データは原則ローカル完結とする。

- クラウドDBには保存しない
- 専用バックエンドを前提にしない
- 必要時のみGoogle Drive移行を検討する
- AIへローカルデータ全量を送らない
- React側から任意パスで読み書きさせない

### 11.3 ユーザー設定
ユーザー設定はJSON保存を基本とするが、秘密情報は含めない。

設定に含めてよいもの:
- 関心カテゴリ
- 通知設定
- 解説レベル
- テーマID
- Mock/Gemini切替設定

含めてはいけないもの:
- APIキー
- OAuthトークン
- 復元キー
- 個人Googleアカウント情報

### 11.4 ローカルデータ破損時
ローカルデータ破損時は以下を検討する。

- 該当ファイルのみ読み込みスキップ
- 破損ファイルを退避
- 初期設定で再作成
- エラー概要を表示
- アプリ全体は停止させない

### 11.5 ファイルパス制御
Rust側では、保存・読込対象をアプリ管理ディレクトリ配下に限定する。

禁止:
- Reactから渡された絶対パスをそのまま開く
- `../` を含むパスを許可する
- 任意のユーザーファイルを読み込む
- 任意ディレクトリへ保存する

### 11.6 月次ZIPからの単記事復元
ニュースアーカイブの復元では、React側からZIPパスやentry名を受け取らない。

- Tauri commandの入力は検証済み`articleId`に限定する
- `archive_index.json`の年月・ZIPファイル名・記事entry名の対応をRust側で検証する
- ZIPと展開entryにサイズ上限を設け、パストラバーサル、暗号化entry、非ファイルentry、欠落・重複entryを拒否する
- 展開後MarkdownのUTF-8、Front Matter、`articleId`、保存月を検証してから保存する
- 既存の利用可能なMarkdownは上書きせず、失敗時は新しいMarkdownを残さない
- 復元・アーカイブ・記事更新は同じ書込ロックで直列化し、同時実行によるロストアップデートを防ぐ

### 11.7 アーカイブ済みMarkdownの退避付き削除
元Markdownの削除は、月次ZIPを単に開けることだけで成功扱いにしない。

- Tauri commandはパス・年月・記事IDを受け取らず、Rust側で管理対象を選定する
- `archive_index.json`が完全な記事カタログを持つ月だけを対象にする
- ZIPサイズ、全entryの件数・名前・展開サイズ、UTF-8、Front Matter、記事カタログを照合し、余分・欠落・重複・暗号化・非ファイル・危険なパスを拒否する
- ローカルMarkdownとZIP内Markdownの内容がアーカイブ状態以外で一致しない場合は削除しない
- 削除計画後のTOCTOUを抑止するため移動直前にローカルMarkdownを再検証し、変更検出時は先行して移動した記事もrollbackする
- お気に入り、復元済み、状態不整合の記事は削除しない
- 通常領域から固定rollback領域へ移動し、全件成功後にcommit済み領域へ切り替える。途中失敗時は移動済みファイルを元へ戻す
- rollback領域が残った場合は次回起動時に復元し、既存の変更済みMarkdownを上書きしない
- commit後の掃除失敗は警告として扱い、アプリ全体を停止させない。ただし残存領域が解消されるまで次回削除は安全側で停止する
- symlinkや想定外のディレクトリ構造を退避・復旧対象として扱わない
- 日次自動実行の状態が欠落・破損した場合は未完了扱いとし、ZIP/index/Markdownの検証を省略せず再実行する
- 日次完了日はZIP作成・退避付き削除・commit済み領域の掃除が全て成功した場合だけ保存する
- 自動実行でも任意パスを受け取るcommandは追加せず、手動実行と同じRust側検証を再利用する

## 13. Google Driveデータ移行の安全設計

### 13.1 位置づけ
Google Driveデータ移行はMVP対象外とし、将来拡張候補とする。

### 13.2 基本方式
将来的に実装する場合、以下の方式を想定する。

```text
移行元PC
  1. 移行対象データを収集
  2. ZIP化
  3. クライアント側で暗号化
  4. Google Driveへアップロード
  5. 長めのワンタイムパスコード / QRコードを表示

移行先PC
  1. 同じGoogleアカウントで認証
  2. ワンタイムパスコードまたはQRコードを入力
  3. 暗号化ZIPをダウンロード
  4. 復号してローカル展開
  5. Drive上の一時ファイルを削除
```

### 13.3 保存先
開発段階:
```text
Google Drive / YuukoTransfer /
```

本格運用候補:
```text
Google Drive appDataFolder
```

### 13.4 必須ルール
- Drive上に平文ZIPを置かない
- Drive上に復号鍵を置かない
- 復元キーをログに出さない
- 移行ファイルに有効期限を設ける
- 復元完了後にDrive上の一時ファイルを削除する
- 有効期限切れファイルを削除対象とする
- Drive全体への広範なアクセス権限は避ける
- React側へOAuthトークンを持たせない

### 13.5 移行対象
移行対象候補:

- config/
- news/
- dictionary/
- user/
- rewards/
- gacha/

移行対象外:

- logs/
- cache/
- APIキー
- OAuthトークン
- Google認証情報
- メール本文
- メール送信者情報
- OS資格情報

### 13.6 QRコード
QRコードには復元に必要な情報を含める。

候補:
- transferId
- restoreKey
- 有効期限
- バージョン

QRコード中央にゆうこの顔アイコンを配置する場合は、誤り訂正レベルを高め、読み取り精度を損なわないサイズに制限する。

### 13.7 Tauri版での責務
- ZIP作成: Rust側
- 暗号化: Rust側
- Drive連携: Rust側または承認済み連携層
- QR表示: React側
- 入力フォーム: React側
- 復元確定: Rust側

## 16. エラー・フォールバック時の安全方針

### 16.1 基本方針
失敗時は、安全側へ倒す。

### 16.2 代表例
| 失敗 | 安全な挙動 |
|---|---|
| RSS取得失敗 | ローカル保存済みニュースを表示 |
| HTML抽出失敗 | タイトル・出典・URL中心で保存 |
| AI要約失敗 | 要約なしまたはMock表示 |
| 用語解説失敗 | 再選択を促す |
| 辞書保存失敗 | エラー表示、元データ維持 |
| 設定保存失敗 | 変更前設定を維持 |
| Tauri command失敗 | React側でトースト表示、アプリ継続 |
| Driveアップロード失敗 | ローカルデータを削除しない |
| 復元失敗 | 既存ローカルデータを上書きしない |

### 16.3 禁止するフォールバック
以下は禁止する。

- HTML抽出失敗時にHTMLを生表示する
- AI失敗時に秘密情報を含むリクエスト内容を表示する
- Drive移行失敗時にローカルデータを削除する
- APIキー未設定時にエラーでアプリ全体を落とす
- command失敗時に内部エラー詳細をそのままUI表示する

## 21. まとめ
本アプリは、ローカル保存を基本とし、外部通信はニュース取得とAI要約・解説に必要な範囲へ限定する。

MVPでは特に以下を守る。

- APIキーをコードやGitに入れない
- APIキーをReact側へ渡さない
- AI送信データを最小化する
- HTMLを生表示しない
- Markdown表示を安全化する
- Tauri commandを必要最小限にする
- ログに危険情報を残さない
- 外部通信先を管理する
- 失敗時は安全側へ倒す

Tauri版では、React / TypeScriptは表示と操作受付を担当し、Rust側が外部通信、AI連携、保存、入力検証、ログ制御を担当する。  
将来的にGoogle Driveデータ移行やGoogleメール連携を実装する場合も、平文データや認証情報を外部に不用意に置かず、会社のセキュリティ方針確認後に採用判断する。
