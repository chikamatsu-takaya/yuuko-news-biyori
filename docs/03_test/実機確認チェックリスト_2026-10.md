## 0. 準備

### 0.1 アプリを用意する
次のどれか1つ。**A または B を推奨**（2つ目の起動・自動起動など、配布版に近い動きを確かめられる）。

| 方法 | コマンド（リポジトリのフォルダで実行） | 起動するもの |
|---|---|---|
| A. インストーラー | `pnpm tauri build` | `src-tauri/target/release/bundle/` の下にできるインストーラーで入れ、スタートメニューから起動 |
| B. デバッグビルド | `pnpm exec tauri build --debug --no-bundle` | `src-tauri/target/debug/app.exe` をダブルクリック |
| C. 開発起動 | `pnpm tauri dev` | 自動でウィンドウが開く（手早いが、2つ目の起動の確認には向かない） |

- 詳しい前提（Build Tools・Node・Rust・pnpm の導入）は [開発環境構築手順書](../01_setup/開発環境構築手順書.md) §5・§8・§9（最短は §26）、起動・ビルドは §14・§15。
- A は初回の `pnpm tauri build` で Tauri CLI がインストーラー作成用の道具（WiX・NSIS）を自動で取得するため、ネットワーク接続が要る。準備に不安があれば開発者に手伝ってもらう。
- **ローカルAI（同梱 llama-server）** を使う項目（§9〜§11。§10.1 を含む）があるので、ビルド前に同梱物を置いておく。手順は [開発環境構築手順書](../01_setup/開発環境構築手順書.md) §17.5 と [ローカルLLM同梱配布手順](../01_setup/ローカルLLM同梱配布手順.md)（`node scripts/local-llm/place-bundle.mjs <同梱物のフォルダ> --vc-crt <VC++ ランタイムのフォルダ>`）。A（インストーラー）は同梱物が無いとビルドが止まる。
- アプリの設定で **設定 > 解説・AI設定 > AIプロバイダー** を「ローカル」にして「保存する」。

### 0.2 データの場所（app-data）
- `%APPDATA%\jp.star-system.yuuko-news\`

## 4. 通知のタイミング（通知モード）
- **目的**: 設定「通知のタイミング」の4つのモードが選べて、動きに反映されることを確かめる。
- **手順**
  1. 設定 > 通知 を開き、「ニュース通知を受け取る」の下にある「通知のタイミング」を見る。
  2. 4つ（時間帯内ランダム（既定）/ ランダム / 定時 / 通知しない）を順に選び、選択肢の下の説明文が変わることを見る。「ランダム」では通知時間帯を使わない旨の注記が出る。
  3. 「ニュース通知を受け取る」を OFF にすると、「通知のタイミング」が選べなくなる。ON に戻すと元の値のまま。
  4. **通知しない**: 選んで保存 → メイン画面を × でしまい、30分ほど待つ。その後トレイ「ゆうこを呼ぶ」。
  5. **定時**（時間があれば）: 今の時刻を含む側の時間帯（午後なら「午後の通知時間帯」）の開始を今の数分後にし、終了はそれより後のままにして保存 → メイン画面をしまって待つ。
  6. **時間帯内ランダム**（時間があれば）: 既定に戻して保存し、しまったまま1〜2時間ようすを見る。
  7. 選んだモードで保存 → アプリを「常駐を終了する」で終了 → 起動し直して、設定が残っているか見る。
- **期待結果**
  - 4: 自動ではゆうこが出ない（報酬のお知らせも出ない）。「ゆうこを呼ぶ」では出る。
  - 5: 開始時刻ごろ（しまっているときは5分おきの判定なので、最大5分ほど遅れる）に1回出る。
  - 6: 時間帯の開始ちょうどではなく、ばらけた時刻に出る。
  - 7: 選んだモードが残っている。
  - 注: 1日の上限（既定3回）とクールタイム（前回から60分、閉じた後120分、放置した後180分）はどのモードでも効くため、すでに通知が出た日は出ないことがある。

## 10. 自動要約と手動操作の協調
- **目的**: 自動要約の最中でも、手で頼んだ解説・要約が待たされすぎず、二重に作られないことを確かめる。
- **手順**
  1. 新しい記事を取って自動要約が動いている状態にする（§9 の 2）。
  2. 記事画面で要約・再説明の文字を選び（またはページ下の用語候補から）「解説」を続けて2〜3回使う。
  3. 解説を最後に使ってから、次の記事の要約が進み始めるまでの時間を見る。

### 10.1 （任意・開発者と一緒に）起動失敗が続いたときの待ち
llama-server の起動を2回失敗させ、10分は自動要約から起動し直さないことを確かめる。

- **注意**: `llama-server.exe` そのものの名前を変えると「部品が見つからない」扱いになり、**起動失敗としては数えられない**（この確認にはならない）。起動失敗として数えられるのは、プログラムが起動したあとに落ちた場合など。
- **手順**
  1. 自動要約か「解説」で一度 llama-server を起動させる（同じ起動中は部品の照合が1回で済むため）。
  2. `llama-server.exe` が消えるまで待つ（§9）。
  3. タスクマネージャーで動いていたときに確かめた場所（`llama-server.exe` を右クリック →「ファイルの場所を開く」で事前に開いておく）にある `llama-server-impl.dll` の名前を `llama-server-impl.dll.off` に変える（MSI で Program Files に入れた場合は管理者権限が要る。方法B の `src-tauri\target\debug` の下で行うと楽）。
  4. 「解説」を1回、1分以上あけてもう1回使う。Windows のエラーのウィンドウが出たら閉じる。
  5. ログ（0.5）を見る。その後、新しい記事を取って10分ほど自動要約を待つ。
  6. **必ず名前を `llama-server-impl.dll` に戻す。** 戻したらアプリを終了して起動し直す。
- **期待結果**
  - ログに `llama-server failed to start: reason=... exit_code=... consecutive=1`、続いて `consecutive=2` が出る。2回目のあと `paused for 600s` を含む警告が出る。
  - その後の10分間、自動要約は llama-server を起動しに行かない（デバッグ・開発版のログには `llama-server start skipped` が出る）。アプリ全体は落ちない。
  - 6 のあと、解説・自動要約が元どおり動く。
