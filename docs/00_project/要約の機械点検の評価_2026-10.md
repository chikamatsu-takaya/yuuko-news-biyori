# 要約の機械点検と1回の作り直しの評価（国内記事）2026-10

作成日: 2026-10-27 ／ 判断台帳: D166 ／ 関連: [海外ニュース要約の試作評価_2026-10](海外ニュース要約の試作評価_2026-10.md) §8（D165 の機械点検の試作）、詳細設計書 §12.2.1

## 0. 結論（藤井さん向け）

1. **誤検出の率は 0%（問題のない要約 84 件のうち 0 件）、検出の率は「記事情報にない数字・桁違い」で 5/5 件、人工の誤り（桁違い・材料にない数字・簡体字・指示の写し）で 100%** だった（点検を直した後の値。§2）。
2. 点検の最初の版では、小さいモデルが書く「80 万 4,300 人」「2 億 1000 万円」（単位の前後の空白）を読めず、**90 件中 10 件を桁違いと誤検出**した。作り直しで内容が悪くなった例もあった（§3）。読めるように直し、単体テストに入れた。
3. 作り直しの対象にした点検: **数字（材料にない数字・桁違い）・簡体字・指示の写し・日本語でない**。入れなかった点検: **注記・長さ**（理由は §4）。要点・注目ポイント・再説明・一言は作り直さない。
4. 作り直しは 90 件中 6 件（6.7%）で起き、作り直した要約の点検は全件通った。ただし 5 件中 1 件は、数字は直ったが別の作り話が入り、内容は悪くなった（§3.2）。
5. 生成時間の増え方: 作り直し1回は平均 9.2 秒（最大 13.0 秒）。記事1件の要約一式（4段）は平均 42.4 秒（直した点検での実測。30 件中 1 件で作り直し 6.6 秒）。作り直しの起きる率から見込む増え方は平均 **約 1.5%**（作り直しの起きた記事だけなら約 +15〜30%）。点検そのものは1回 中央値 1.1 ミリ秒（デバッグビルド）で無視できる（§5）。

## 1. 方法

### 1.1 評価データ

- **既存の品質評価（`local_llm_quality_eval`）には、リポジトリ内の固定の評価データがなかった**（取得した記事は毎回一時フォルダに置いて評価後に削除する運用）。今回はネット取得をせず、アプリの app-data にも触れない決まりなので、**評価のために架空の国内記事 30 件を書いて固定データにした**: `src-tauri/src/services/summary_service/eval_data/domestic_articles_synthetic.json`。
  - 実在の記事の転載ではない（企業名・地名・人物は架空。`example.com` の URL）。
  - ジャンル: 社会 9・経済 6・テクノロジー 4・地域 4・スポーツ 3・科学 2・エンタメ 2（重いニュース〔火災・地震・台風〕を含む）。抜粋は 107〜242 字。
  - 数字の書き方を混ぜた: 3 桁区切りのカンマ、全角、「万・億・兆」とその続き（1万8000人・33万2,150人・1兆2,300億円・2兆800億円）、％・ポイント・倍・割（2割・1割・6割）、範囲（4〜9月）、時刻（午前9時・午後2時15分・午後9時）、元号（令和8年度）、漢数字（創業百年・三代目・一本千八百円・十一月末）、小数（1.32倍・0.3ミリ秒）。
- 実ニュースより文が整っており、数字の多い記事に寄せている。誤検出の率は実ニュースでは上がりうる（§6）。

### 1.2 生成

- 同梱の Qwen3.5-2B（llama-server）。メインの作業フォルダの同梱物を `YUUKO_LOCAL_LLM_DIR` で読み取り専用で指した。起動と照合は先に済ませた（35.6 秒）。
- **点検の評価（`summary_output_check_eval`）**: 30 件 × 解説レベル 3 つ（やさしく・ふつう・くわしく）= 90 件の要約を、アプリと同じ種（`build_summary_seed`）・プロンプト（`summary_v1`）・出力検証で作り、点検をかけ、アプリと同じ作り直しの関数（`check_and_retry_summary`）を通した。
- **時間の評価（`local_llm_quality_eval` の summary 段）**: 同じ 30 件で、アプリの要約一式（要約 → 作り直し〔あれば〕 → 要点・タグ → 再説明 → 一言）を手動要約の経路で作り、段ごとの時間を測った。点検を直す前（run1）と後（run2）の 2 回。
- 生成した要約・記録は一時フォルダに置き、評価の後に削除した。

### 1.3 判定

- 誤検出: 点検が問題ありとした要約を Claude が材料と読み比べ、問題がなければ誤検出とした。
- 検出の率（自然な誤り）: 90 件すべてを読み、数字の誤り（材料にない値・桁違い）・簡体字・指示の写しを数え、点検が拾った割合を出した。
- 検出の率（人工の誤り）: 全点検に合格した要約に、機械的に誤りを1つ入れて点検した（最初の算用数字を 10 倍／材料にない数に置き換え、日本語の字1つを簡体字〔発→发など〕に置き換え、「記事情報によると、」を前に付ける、固定指示の文を後ろに付ける）。

## 3. 作り直しの効果

### 3.1 最初の版の誤検出（単位の前後の空白）

- 最初の版は「80 万 4,300 人」「2 億 1000 万円」「1 兆 2,300 億円」のように、**単位の後ろに空白を入れて続きの数を書く形**を1つの数として読めず、「4,300」「1000 万」「2,300 億」を別の数と見て桁違いと判定した。90 件中 10 件（d15・d16・d17 の各レベル）が誤検出で、正しい要約まで作り直した。
- 時間の評価 run1 では、作り直し 2 件がどちらもこの誤検出で、d17 では作り直しで「修繕費 410 億円」「市債残高 2 兆 800 億円」が消え、**内容が悪くなった**。D165 の §8.4 と同じく、誤検出は作り直しを無駄にするだけでなく内容を悪くする。
- 直したこと: 続きの数の前後の空白を読み飛ばす（ただし「80 万人、2026 年」のような日付・回数の数は続きにしない）。単体テストに実例を入れた。

### 3.2 正しい指摘での作り直し（点検の評価・6 件のうち記録のある 5 件）

| 記事 | 結果 | 内容 |
|---|---|---|
| d04 やさしく | 直った | 「9 月」が消え、事実は材料どおり |
| d04 くわしく | **点検は通ったが内容は悪化** | 「9 月」は消えたが、「東陵高校から先発のエースが…」と主語を取り違え、「県予選の末に決勝に進んだため…初優勝として発表することになった」という材料にない文が入った |
| d13 くわしく | 直った | 「過去 2002 年度以降で最も大きく」。文は短くなった |
| d15 やさしく | 直った | 「80 万 4,300 人」と正しく書いた（作り直しの記録は誤検出の版のもの。直した点検でも合格） |
| d16 ふつう | 直った | 「4 ヶ月間」が消え、「412 件」も入った |

- 4 / 5 で直り、1 / 5 は数字は直ったが別の作り話が入った。作り直しの採否は点検だけで決めるので、点検の外の悪化（作り話・主語の取り違え）は防げない。
- 作り直しの採否のきまり: 作り直しの理由になる問題の数が減り、最初になかった種類が出ていないときだけ採る（悪化を見分けられる範囲では悪化させない）。作り直しが失敗・検証落ち・Mock への切り替えのときは最初の要約を使う。

## 4. 入れた点検・入れなかった点検

| 点検 | 作り直しの理由にするか | 理由 |
|---|---|---|
| 材料にない数字・桁違い | する | 自然な誤りの大半。誤検出 0（直した後）。要約のプロンプトも「数や日付を別の言い方に変えない」と頼んでいるので、指摘とプロンプトがそろう |
| 簡体字 | する | 国内記事では自然な混入 0 件だったが、日本語の文字コードに無い字だけを見るので誤検出の余地が小さい（材料にある字は除く）。再説明・一言の後処理と同じ一覧 |
| 指示の写し | する | 1 件拾えた。材料にある語（例: IT 記事の「外部データ」）は除くので誤検出の余地が小さい |
| 日本語でない | する | 0 件。英語のまま返したときの安全網 |
| 注記（「記事には」「明記されていない」など） | しない（記録のみ） | 国内記事では「〜は明らかにされていない」のような記事そのものの言い回しと区別しにくい。今回は 0 件で、誤検出の率を測れなかった |
| 長さ | しない | 要約は「1〜2文」で頼み、文字数の上限を決めていない（保存前の検証は 3000 字）。要約の長さ（空白を除く）は 55〜177 字（中央値 106〜119 字）で、点検の対象にするほどの長すぎる出力はなかった |

- **漢数字**: 材料の側は読む（「三代目」→ 3、「千八百円」→ 1800、「二〇二六」→ 2026）が、**要約の側は照合しない**。要約の漢数字には「一部」「一方」「十分」「一人ひとり」のように数でない言い回しが多く、読むと誤検出になるため。今回、要約に漢数字の数字を書いたのは d14（材料も漢数字）だけで、見逃しの実害は確認していない。
- **数字の書き方の違いは同じ数とみなす**: 全角・カンマ・「万・億・兆・千」（1.8 万人 = 1万8000人）・割と％（1割 ⇔ 10%、6割 ⇔ 60%）・午後3時 ⇔ 15時・令和8年 ⇔ 2026年。今回の要約では「約 10％」「約 60%」（材料は割）と「約 1.8 万人」が出て、どれも通った。
- **要点・注目ポイントは作り直さない**: 時間の評価で要点・注目ポイント（30 件）にも同じ点検をかけたが、問題ありは 0 件だった。要点の段は一式で最も長い（平均 14.8 秒）ので、作り直しの費用に見合う不良が見えていない。再説明・一言は既存の後処理（簡体字の文の除去・指示の写しの除去）がある。

## 5. 時間

| 項目 | 値 |
|---|---|
| 最初の要約（90 件） | 平均 8.1 秒・最大 10.8 秒 |
| 作り直し（11 件。誤検出の分を含む） | 平均 9.2 秒・最大 13.0 秒 |
| 点検そのもの | 中央値 1.1 ミリ秒・最大 11 ミリ秒（デバッグビルド） |
| 要約一式（30 件・run1。点検を直す前） | 平均 48.6 秒・最大 70.9 秒（作り直し 2 件） |
| 要約一式（30 件・run2。点検を直した後） | 平均 42.4 秒・最大 49.7 秒（作り直し 1 件: d27 の指示の写し。作り直し 6.6 秒、その記事の一式 45.4 秒） |

- 作り直しの起きる率（直した点検で 6 / 90 = 6.7%）× 作り直し 1 回（約 9.2 秒）で、要約一式（約 42 秒）の平均の増え方は約 0.6 秒（**約 1.5%**）。run2 の実測では 30 件で作り直し 1 回（6.6 秒）＝ 1 件あたり平均 +0.2 秒。作り直しが起きた記事だけなら 1 件あたり 7〜13 秒（約 +15〜30%）。
- run1 と run2 の平均の差（48.6 秒 → 42.4 秒）は作り直しの数（2 → 1）だけでは説明できず、ほとんどは生成のばらつき（出力の長さ）による。
- run2 の d27 では、最初の要約の末尾に「…という事実だけを使用し、数値や日付をそのまま記事情報に忠実に反映した要約を作成しました。」が混ざり、作り直しで消えた（指示の写しの自然な検出が計 2 件になった）。
- 作り直しは最大 1 回なので、最悪でも要約一式に生成 1 回分（最大 13 秒程度）が足されるだけ。

## 6. 残る懸念

- 評価データは架空の記事で、実ニュースより文が整っている。実ニュース（RSS 概要だけの短い抜粋・表・見出しの混じった抜粋）での誤検出の率は測っていない。小さいモデルが書く数字の形（単位の前後の空白など）は今回 1 つ見つかったので、ほかの形でも誤検出が出うる。ログ（`the summary output check found issues (...)`）の件数を見て、増えたら点検を絞る。
- 作り直しの採否は点検だけで決めるので、点検の外の悪化（作り話・主語の取り違え）は防げない（5 件中 1 件）。
- 要約の側の漢数字・数字の係り先・意味の取り違えは見逃す。
- 採点者は Claude 1 人、各要約 1 回の生成。
- Gemini の要約にも点検をかける（問題があれば呼び出しが 1 回増える）。Gemini の出力では評価していない。

## 7. 再現の手順（PowerShell）

```text
$env:CARGO_TARGET_DIR = "<一時の target フォルダ>"
$env:YUUKO_LOCAL_LLM_DIR = "<同梱物のフォルダ（読み取り専用で参照）>"
# 点検の評価（90 件。generate → analyze）
$env:YUUKO_SUMMARY_CHECK_EVAL_OUT = "<一時フォルダ>\summary-check"
cargo test --manifest-path src-tauri/Cargo.toml -j 4 summary_output_check_eval -- --ignored --nocapture
# 時間の評価（要約一式 30 件）
$env:YUUKO_LLM_EVAL_OUT = "<一時フォルダ>\pipeline"
$env:YUUKO_LLM_EVAL_PHASE = "summary"
$env:YUUKO_LLM_EVAL_ARTICLES = "src-tauri\src\services\summary_service\eval_data\domestic_articles_synthetic.json"
cargo test --manifest-path src-tauri/Cargo.toml -j 4 local_llm_quality_eval -- --ignored --nocapture
```

- `<OUT>/summary_checks.jsonl` に要約・点検・作り直しの記録、`<OUT>/analysis.json` に集計と問題ありの一覧、`<pipeline>/summaries.jsonl` に段ごとの時間（`promptId` が `summary_retry_v1` の段が作り直し）が入る。終わったら出力を削除し、`tasklist` で llama-server が残っていないことを確かめる。
