## 1A. Tauri版における技術前提

### 1A.1 採用技術
本システムの初期開発およびMVPでは、以下の構成を基本とする。

| 領域 | 採用技術 | 役割 |
|---|---|---|
| アプリ基盤 | Tauri v2 | デスクトップアプリ基盤、WebView、Rust連携、OS連携 |
| UI | React | 画面表示、ゆうこ表示、吹き出し、モーダル、ポップアップ |
| UI言語 | TypeScript | 型安全な画面実装、Tauri command呼び出し |
| 中核処理 | Rust | ニュース取得、AI連携、保存、辞書、友情ランク、通知状態管理 |
| 保存形式 | Markdown / JSON | ニュース、辞書、設定、状態情報のローカル保存 |
| AI | Gemini API / MockProvider | 要約、再説明、用語解説、ゆうこの一言生成 |
| 開発環境 | VS Code / pnpm / Cargo | チーム開発、AI駆動開発、Tauri起動確認 |

### 1A.2 責務分担
Tauri版では、以下の責務分担を基本とする。

```text
React / TypeScript
  - 画面表示
  - ユーザー操作受付
  - ゆうこの表示・アニメーション
  - モーダル / ポップアップ / トースト表示
  - Tauri command呼び出し

Rust
  - RSS取得
  - HTML取得と本文抜粋抽出
  - AI Provider呼び出し
  - Markdown / JSON保存
  - ゆうこ辞書管理
  - 友情ポイント・ランク判定
  - 通知条件・抑制条件判定
  - Tauri command実装
  - 入力値検証
  - セキュリティ境界管理
```

React側には、APIキー管理、AI API直接呼び出し、RSS取得、HTML取得、任意ファイル読み書き、友情ポイント確定処理、通知回数確定処理を持たせない。

### 1A.3 C++ / Qt / QMLの扱い
過去検討のC++ / Qt / QML構成は、本Tauri版MVPでは使用しない。  
旧資料は退避資料として残してよいが、初期開発で参照する最新版は `_Tauri` 付きの資料とする。

### 1A.4 MVP起動確認基準
MVPでは、以下のコマンドでTauriアプリが起動することを基本的な確認基準とする。

```bash
pnpm tauri dev
```

必要に応じて以下も確認する。

```bash
pnpm dev
cd src-tauri
cargo check
```


## 2. システム概要
本システムは、ユーザーの関心ジャンルに応じてニュースを収集し、AIによる要約と用語補足を付与して閲覧しやすくするデスクトップ向けソフトウェアである。

ソフト内にはマスコットキャラクター **「ゆうこ」** が存在し、ユーザーの画面端から定期的またはランダムに現れてニュースを紹介したり、ユーザーが選択した気になる単語や用語について簡潔に解説したりする。

また、継続利用を促すために、ゆうことの交流によって友情ランクが上がり、ランク上昇ごとにデコレーション要素またはUIテーマを1つずつ解放する仕組みを持たせる。

## 3. 企画背景・コンセプト

### 3.1 背景
- ニュースは量が多く、タイトルだけでは内容を把握しづらい。
- 難しい用語や専門用語が含まれると、読むハードルが上がる。
- 単なるニュース一覧では継続利用につながりにくい。
- 社内活動の題材として「懐かしいもの」を取り入れる方針がある。
- 社内発表向け作品として、実用性と遊び心の両立が求められる。

### 3.2 企画上の立ち位置
本企画は、昔の情報アシスタント型アプリの「寄り添ってくれる」「情報を届けてくれる」体験から着想を得て、現代のAI要約・用語解説・パーソナライズ機能を組み合わせて、社内向けに再構成したソフトとする。

なお、懐かしさの方向性はあくまで企画背景・体験設計上の参考とし、名称・キャラクター・画面デザイン・表現は独自のものとして構成する。

### 3.3 目的
- ユーザーに合ったニュースを分かりやすく届ける。
- AI要約と用語解説により、ニュース理解の入口をつくる。
- マスコットキャラクター「ゆうこ」により、親しみや継続利用性を高める。
- 友情ランクと報酬解放により、継続的に使いたくなる体験を提供する。
- 社内公開を前提に、セキュアかつ運用しやすい構成にする。

## 7. 機能要件


### 7.0 Tauri command共通要件
- React / TypeScript側からRust側機能を呼び出す場合は、Tauri commandを使用すること。
- Tauri commandはアプリ固有の操作単位に限定すること。
- `read_any_file`、`write_any_file`、`fetch_any_url`、`execute_command` のような汎用的で危険なcommandは作成しないこと。
- すべてのcommand引数はRust側で検証すること。
- command戻り値にはAPIキー、OAuthトークン、ログ全文、ローカル絶対パス全量、AI送信全文を含めないこと。
- React側はcommand結果を画面表示へ反映する役割に留め、永続状態の確定更新はRust側で行うこと。


### 7.1 ユーザー設定機能

#### 7.1.1 関心ジャンル設定
- ユーザーは興味のあるニュースジャンルを設定できること。
- ジャンルは複数選択可能であること。
- 初期開発時点では、**IT** および **AI** を初期カテゴリとして提供すること。
- 将来的に、ユーザーがカテゴリやニュースソースを追加し、自分向けのニュース空間を拡張できることが望ましい。
- 設定内容はローカル保存され、次回起動時も保持されること。

#### 7.1.2 通知時間帯設定
- ユーザーは、ゆうこが話しかけに来る時間帯を設定できること。
- 通知の出現タイミングは以下を選択可能とすること。
  - ランダム
  - ユーザー指定時間帯内でランダム
  - 定時
  - 通知しない
- 業務中の邪魔にならないよう、通知頻度の上限を設定できること。
- 初期値として、以下の勤務時間帯を設定すること。
  - 09:00～12:00
  - 13:00～18:00

#### 7.1.3 解説レベル設定
- 用語解説の出力レベルを選択できること。
- 少なくとも以下のレベルを想定すること。
  - 超ざっくり
  - 普通
  - 少し詳しく
- 解説レベル設定は、単語解説および長文選択時の要点説明の両方に反映されること。

#### 7.1.4 テーマ設定
- ユーザーは解放済みのUIテーマを選択できること。
- テーマはプリセット方式を基本とすること。
- テーマ設定内容はローカル保存され、次回起動時も保持されること。

#### 7.1.5 ゆうこ登場抑制設定
- ユーザーは、ゆうこの登場を抑制する対象条件を設定できること。
- 少なくとも以下を設定候補として持つこと。
  - 特定ソフト起動中
  - マイク使用中
  - フルスクリーン表示中
- 特定ソフトについては、ユーザーが抑制対象アプリを指定できること。

#### 7.1.6 自動起動設定
- ユーザーは、本ソフトを **PC起動時に自動起動するかどうか** を設定できること。
- 自動起動が有効な場合、本ソフトは通常ウィンドウを前面表示せず、バックグラウンド待機状態から開始すること。
- 自動起動設定内容はローカル保存され、次回起動時も保持されること。

### 7.2 ニュース取得・管理機能

#### 7.2.1 ニュース取得元
- ニュース候補の取得には、**RSS を主取得元** とすること。
- 必要に応じて、利用条件上問題のない補助的なニュースソースや公開フィードを組み込める構成とすること。
- 初期版では無料利用や低コスト運用を重視し、継続運用時にも利用条件に抵触しにくい取得方法を優先すること。
- 将来的に追加のニュースソースを組み込める構成であることが望ましい。

#### 7.2.2 ニュース取得タイミング
- ニュース取得は、**アプリ起動時に1回**実施すること。
- 長時間起動継続している場合に備え、**日付変更時点（深夜0時）で1回**追加取得できること。
- 過剰な通信やAPI消費を避けるため、MVPでは高頻度な定期ポーリングは行わないこと。
- 手動更新機能は将来的な拡張候補とする。

#### 7.2.3 ニュース取得対象
- ユーザー設定されたジャンルに応じてニュースを取得できること。
- 初期開発時点では、IT および AI に関する記事取得を対象とすること。

#### 7.2.4 重複排除
- 重複ニュースは識別し、不要な重複保存を避けること。
- 初期方針として、以下の条件を重複判定に利用すること。
  - 同一 URL の記事は重複とみなす
  - 同一出典かつ同一タイトルの記事は重複候補とみなす
  - 取得日時が近く、タイトル類似度が高い記事は重複候補とみなす
- 詳細な類似度判定アルゴリズムは後続設計で定義すること。

#### 7.2.5 HTML本文取得
- 記事URL先の HTML を取得し、本文または本文抜粋を抽出できること。
- 本文抽出は、生成AIではなくルールベースまたはテンプレートベースの処理で行うこと。
- 媒体差異に対応するため、汎用抽出処理に加え、必要に応じて媒体別ルールを適用できる構成が望ましい。
- 本文抽出に失敗した場合は、タイトル、出典、URL、取得可能な概要情報のみで保存可能とすること。

#### 7.2.6 ニュース保存形式
- 取得したニュース情報は **1記事につき1ファイル** の Markdown で管理すること。
- HTML から Markdown への変換は、生成AIではなくテンプレートベースの処理で行うこと。
- Markdown は内部処理用の中間データおよび保存形式として扱い、ソフト内のユーザー向け表示はこの Markdown をもとに再構成した内容を表示すること。
- 少なくとも以下の情報を保持すること。
  - 記事ID
  - タイトル
  - 出典
  - URL
  - 取得日時
  - ジャンル
  - AI要約
  - ゆうこの一言
  - タグ
  - 表示状態
  - アーカイブ状態
  - 本文抜粋
  - 解説対象候補語

#### 7.2.7 ニュース一覧表示
- ニュース一覧をソフト内で閲覧できること。
- 一覧上で、タイトル・要約・出典・日時・ジャンルを確認できること。
- 一覧のデフォルト並び順は **おすすめ順** とすること。
- 切替候補として、新着順やジャンル順を将来的に検討可能とすること。
- 気になったニュースは詳細表示へ遷移できること。
- 元記事への導線を表示できること。

#### 7.2.8 既読管理
- 各ニュースに対して既読状態を段階的に保持できること。
- 初期方針として、少なくとも以下の状態を管理できること。
  - 未読
  - 要約閲覧済み
  - 詳細閲覧済み
  - 再説明閲覧済み
  - 元記事遷移済み
- 少なくとも、ニュース一覧上で未読・既読を識別できること。
- 詳細な状態は、おすすめ判定や再提示制御の補助情報として利用できること。

#### 7.2.9 お気に入り機能
- ユーザーはニュース記事をお気に入り登録できること。
- お気に入り登録された記事は、専用フォルダまたは専用管理領域で管理すること。
- お気に入り登録された記事は、通常の月次圧縮アーカイブ対象から除外すること。
- お気に入り記事を一覧表示・再閲覧できること。

#### 7.2.10 過去ニュース保管
- 一定期間経過後のニュース情報を圧縮保管できること。
- 初期方針として、**1か月経過したニュース群を月単位でアーカイブ対象**とすること。
- 圧縮後もユーザーが過去ニュースを見返せる導線を提供すること。
- 過去ニュースを参照したい場合は、ユーザー操作により圧縮アーカイブから取り出し、再閲覧できること。
- お気に入り登録済み記事は圧縮候補から除外すること。

### 7.3 AI要約機能

#### 7.3.0 Tauri版AI Provider方針
- AI要約、再説明文生成、用語解説、ゆうこの一言生成は、Rust側のAI Provider層を通じて実行すること。
- React / TypeScript側からAI APIを直接呼び出さないこと。
- APIキーはReact側へ渡さないこと。
- 初期開発および発表デモでは、Gemini APIに加えてMockProviderを必ず利用可能とすること。
- AI Providerは将来的にGemini API、OpenAI API、ローカルモデル等へ差し替え可能な構造とすること。
- AI送信対象はニュースタイトル、出典、本文抜粋、選択語句、必要最小限の文脈に限定すること。


#### 7.3.1 要約生成
- 要約は、Markdown化後の本文または本文抜粋を入力として生成すること。
- タイトルや概要文のみを要約対象とするのではなく、記事内容をある程度把握できるテキストを入力に含めること。
- 要約は、ユーザーが本文を読む前に概要をつかめる長さであること。
- 初期方針として、1〜3文程度の簡潔な要約を想定する。
- 要約生成の入力は、Markdown化後の本文または本文抜粋を基本とすること。
- 本文整形処理と要約生成処理は分離すること。

#### 7.3.2 興味喚起文生成
- ゆうこが話しかける際に使用する、軽い誘い文句を AI またはテンプレートで生成できること。
- 例: 「こういうニュースがあるんだけど話さない？」
- 誘い文は、フレンドリーだがしつこすぎないトーンであること。

#### 7.3.3 詳細紹介文生成
- ゆうこがメイン画面でニュースを紹介する際、通常要約より少し長めの紹介文を表示できること。
- 紹介文は、ニュースの概要把握を目的とし、元記事の代替ではなく導入として機能すること。
- ソフト内では、記事本文そのものの大量表示を避け、**ゆうこによる再説明文、要点整理、注目ポイント、用語補足** を中心に表示すること。
- 利用者が原文表現を確認したい場合は、出典リンクを通じて元記事へ遷移できること。
- ゆうこの一言コメントに加え、**ゆうこの意見・感想** を表示できること。
- 再説明文は、元記事の表現や構成をそのままなぞるものではなく、事実関係および公開情報をもとに理解補助を目的として再編集した内容とすること。

### 7.4 用語解説機能

#### 7.4.1 解説対象
- 用語解説の対象は、**単語から短いフレーズ** を基本とすること。
- 初期方針として、1語から短いフレーズ程度までを用語解説対象とすること。
- 長文が選択された場合は、通常の用語解説ではなく **要点説明モード** に切り替えること。
- 単語、短いフレーズ、長文要点説明のいずれも、後述するゆうこ辞書への保存対象とすること。

#### 7.4.2 範囲選択連動
- ユーザーがニュース画面上の語句または文章を範囲選択した際、その内容をトリガーとして解説を表示できること。
- 範囲選択後、直ちに長文解説を出すのではなく、小さな解説ボタンまたは補助アクションを表示すること。
- ユーザーがそのボタンを押下した場合に、ゆうこ吹き出しまたはサイドパネルで解説を表示すること。
- 解説ボタンは、解説対象として適切な長さまたは形式の選択である場合に表示できることが望ましい。

#### 7.4.3 解説内容
- 解説は、少なくとも以下の要素を含めて生成すること。
  - 何を指す言葉か
  - ニュース文脈上でどういう意味か
  - 必要に応じた補足または重要性
- 長文選択時の要点説明モードでは、選択範囲の内容を短く整理し、何が重要かを分かりやすく説明すること。
- 解説はユーザーが最初に理解しやすい分量を優先し、必要に応じて詳細を追加表示できること。

#### 7.4.4 表示方式
- 解説は **最初は短く表示し、必要なら「もっと見る」で詳しく表示** する方式とすること。
- 初回表示は、1〜3文程度の短い説明を基本とすること。
- 詳細表示時は、解説レベル設定に応じて補足情報や背景説明を追加できること。
- ユーザー体験として「横から教えてくれる」感覚を持たせること。

#### 7.4.5 解説口調
- 用語解説および要点説明は、**ゆうこの喋り口調のまま説明する** こと。
- ただし、キャラクター性を持たせつつも、内容の理解性や信頼性を損なわないこと。
- 友情ランクや解放済み口調設定に応じて、解説時の表現も変化可能とすることが望ましい。

#### 7.4.6 解説レベル連動
- 解説レベル設定は、用語解説および要点説明の出力量に反映されること。
- 初期方針として、以下のような段階を想定すること。
  - 超ざっくり: 1文中心の簡潔説明
  - 普通: 2〜3文程度の標準説明
  - 少し詳しく: 背景や補足を含むやや詳細な説明

#### 7.4.7 同一語句の再解説
- 同一の単語、フレーズ、長文要点説明が再度要求された場合でも、通常通り表示できること。
- ただし、AI再実行前に保存済みの解説履歴またはゆうこ辞書を参照し、**完全一致** する項目が存在する場合は、その内容を優先再利用できること。
- 上記により、応答速度向上およびトークン使用量削減を図ること。

#### 7.4.8 解説失敗時の挙動
- 解説対象が不適切、長すぎる、または十分な説明が生成できない場合は、無理に解説を生成しないこと。
- その場合は、ユーザーに対して再選択を促す案内、または要点説明への切り替え案内を表示できること。
- 例: 「もう少し短く選ぶと説明しやすいよ」等の補助メッセージを表示可能とすること。

#### 7.4.9 ゆうこ辞書機能
- 一度解説した単語、短いフレーズ、長文要点説明は、再利用可能な辞書データとして保存できること。
- ゆうこ辞書は、同一語句の再解説時に参照されるだけでなく、ユーザーが後から閲覧できること。
- ゆうこ辞書には、少なくとも以下の情報を保持できることが望ましい。
  - 見出し語または対象フレーズ
  - 解説内容または要点説明内容
  - 作成日時または最終参照日時
  - 関連ニュース情報
  - ユーザー付箋メモ
  - お気に入り状態
- ゆうこ辞書は、トークン節約およびユーザーの知識蓄積支援を目的とすること。

#### 7.4.10 ゆうこ辞書のユーザー操作
- ユーザーは、ゆうこ辞書の項目に対して **付箋メモ** を残せること。
- ユーザーは、辞書項目に **★マーク** を付与し、見返しやすくできること。
- ユーザーは、不要になった辞書項目を削除できること。
- 辞書項目の閲覧、メモ追加、お気に入り化、削除は専用画面または辞書画面から行えること。

#### 7.4.11 ゆうこ辞書の再利用ルール
- ゆうこ辞書の再利用判定は、初期版では **完全一致** を基本とすること。
- 類似一致やあいまい検索による再利用は、将来的な拡張候補とすること。
- 完全一致項目が存在する場合は、AIへ再問い合わせする前に辞書内容を優先表示できること。

### 7.4A おすすめ判定ロジック

#### 7.4A.1 基本方針
- ニュースのおすすめ判定は、初期版では **ルールベース** を主軸として行うこと。
- おすすめ判定は、単なる関心ジャンル一致だけでなく、**内容の重要度** と **驚き・意外性** を重視すること。
- ユーザーにとって学びや発見のある記事を提示できるよう、関心に合う記事だけでなく、やや意外性のある記事も候補に含めること。

#### 7.4A.2 判定要素
- おすすめ判定には、少なくとも以下の要素を利用すること。
  - 内容の重要度
  - 驚き・意外性
  - ユーザー関心ジャンル一致
  - 閲覧履歴およびお気に入り由来の傾向メモ一致
  - 鮮度
  - 既読状態

#### 7.4A.3 重要度の判定方法
- 内容の重要度は、少なくとも以下の情報を材料にルールベースで判定すること。
  - 特定キーワード
  - 見出しの強さ
  - 本文内の変化表現
- 重要度は、おすすめ判定における最重要要素の1つとして扱うこと。

#### 7.4A.4 驚き要素の判定方法
- 驚き・意外性は、少なくとも以下の情報を材料にルールベースで判定すること。
  - 「初」「最大」「新」「発表」「公開」などの表現
  - 数値変化
  - 意外な組み合わせ
- 驚き要素は、興味喚起やゆうこの「かまちょ感」を高める補助要素として扱うこと。
- 驚き要素のみで過度に順位が上がらないよう、重要度とのバランスを取ること。

#### 7.4A.5 ユーザー傾向メモ
- お気に入り登録記事および実際に閲覧された記事をもとに、ユーザー傾向を短い要約メモとして保持すること。
- ユーザー傾向メモは、次回ニュース走査時のおすすめ判定補助情報として利用すること。
- ユーザー傾向メモの更新は、**1日1回** を基本とし、アプリ起動時または日付変更時点（深夜0時）に実施できること。
- ユーザー傾向メモは、必要に応じて設定画面等から確認可能であることが望ましい。

#### 7.4A.6 既読・鮮度補正
- 既読記事はおすすめ候補から完全除外するのではなく、順位を下げるための減点要素として扱うこと。
- 新しい記事ほど一定の優先度補正を与えること。
- ただし、鮮度が高いだけの記事が過度に優先されないよう、重要度や関心一致とのバランスを取ること。

#### 7.4A.7 候補件数
- 1日あたりに内部的に保持するおすすめ候補件数は、**10件前後** を目安とすること。
- 候補件数は、興味を引く記事が0件にならないよう、少なすぎず多すぎない件数に調整すること。

#### 7.4A.8 おすすめ判定の基本フロー
- 初期版では、少なくとも以下の流れでおすすめ判定を行うこと。
  1. ニュース候補取得
  2. 重複除外
  3. 既読状態・鮮度による補正
  4. 内容の重要度判定
  5. 驚き要素判定
  6. 関心ジャンル一致判定
  7. ユーザー傾向メモ一致判定
  8. 総合スコア順に並び替え
  9. 上位10件前後を当日候補として保持
- ゆうこは、当日候補の中から順次ニュースを持ってくること。

### 7.5 マスコット「ゆうこ」機能

#### 7.5.1 表示演出
- ゆうこは通常時は待機状態とし、条件に応じて PC 画面端から「ぴょこっと」出現すること。
- 出現位置は画面端固定またはユーザー設定可能とすること。
- 出現時には、短い話しかけ文またはニュース誘導文を表示できること。

#### 7.5.2 話しかけ機能
- ゆうこは取得済みニュースをもとに、ユーザーへ話しかけることができること。
- 話しかけの契機は以下を想定する。
  - ランダム
  - 指定時間帯
  - 新着ニュース取得時
  - ユーザーのアクションが一定時間ない場合
- ユーザーが明示的に設定しない場合は、勤務時間帯内かつ利用可能条件を満たす任意タイミングで登場すること。

#### 7.5.3 振る舞い制御
- ゆうこの出現頻度は調整可能であること。
- 作業の妨げにならないよう、一時停止やミュートが可能であること。
- ゆうこは以下の条件のいずれかに該当する場合、登場しないこと。
  - PCがスリープ状態である場合
  - ユーザー指定の抑制対象ソフトが起動中である場合
  - マイクが使用中である場合
  - フルスクリーン表示中のアプリケーションが存在する場合

#### 7.5.4 クリック時挙動
- ゆうこは2段階クリック方式を採用すること。
- 初回クリック時には、対象ニュースの簡易な追加要約と、さらに詳しい表示へ進むための誘導メッセージを表示すること。
- 再度クリックされた場合、ゆうこは画面端から退場し、メイン画面またはニュース詳細画面へ遷移すること。
- 遷移先画面では、少し長めの要約、要点整理、元記事リンク、ゆうこの一言コメント、注目ポイント、および必要に応じてゆうこの意見・感想を表示すること。

#### 7.5.5 ソフト内ビュー連携
- MVPでは、記事閲覧は原則として本ソフト内ビューで行うこと。
- ソフト内ビューでは、要約を先に表示し、必要に応じて**ゆうこによる再説明文、要点整理、注目ポイント、用語補足** を表示すること。
- 記事本文そのものの大量表示は避け、原文表現を確認したい場合のために元記事リンクを提供すること。
- ゆうこはソフト内ビュー上で待機し、用語解説や補足表示の起点となること。
- 元記事へ移動するためのリンクは補助導線として提供すること。

#### 7.5.6 デコレーション機能
- ゆうこに対して、解放済みのデコレーション要素を適用できること。
- デコレーションは初期版ではプリセット方式を基本とすること。
- デコレーション例として以下を想定する。
  - アクセサリ
  - 表情差分
  - 吹き出しデザイン
  - 小物

### 7.6 継続利用・ゲーム要素

#### 7.6.1 友情ランク
- ゆうことの交流量に応じて友情ランクが上がること。
- 友情ランクは**ポイント制**で管理すること。
- ユーザーの行動に応じて友情ポイントを付与し、一定値に到達した時点でランクアップすること。
- 友情ランクには最大値を設けること。
- 初期開発時点では、最大ランクを **20** とすること。
- ランクアップ必要ポイントは、前半は軽く、後半はやや重くなるバランスとすること。

#### 7.6.2 友情ポイント付与対象
- 友情ポイントは、少なくとも以下の行動で付与すること。
  - 画面端に登場したゆうこをクリックし、メイン画面まで遷移した場合
  - ニュース詳細を開いた場合
  - 詳細なニュース表示または再説明表示を開いた場合
  - 用語解説機能を利用した場合
- 初期想定のポイント量は以下の通りとすること。
  - ゆうこ経由でメイン画面へ遷移: **5pt**
  - ニュース詳細表示: **3pt**
  - 詳細なニュース表示または再説明表示: **4pt**
  - 用語解説利用: **1pt**
- 用語解説利用は小ポイントとし、過度なポイント稼ぎの中心にならないよう調整すること。

#### 7.6.3 日次上限
- 1日あたりに獲得できる友情ポイントには上限を設けること。
- 初期想定の1日上限は **25pt** とすること。
- 日次上限到達後も通常機能の利用は継続可能とし、友情ポイントのみ加算対象外とすること。
- 短時間の繰り返し操作による過剰なランク上昇を防止すること。

#### 7.6.4 ランク報酬解放
- 友情ランクが1段階上がるごとに、**報酬を1つ解放**すること。
- 報酬の解放順は**固定順**とすること。

- 解放済み報酬は、設定画面からいつでも切り替え可能であること。
- 報酬には少なくとも以下の種別を含めること。
  - ゆうこのデコレーション
  - UIテーマ
  - 話し方・口調設定

  - セリフパターン
  - ニックネーム機能

#### 7.6.5 ニックネーム機能

- ニックネーム機能は友情ランク報酬の一種として解放すること。

#### 7.6.6 口調・性格・テーマ等の切替

### 7.6A 状態遷移・状態管理

#### 7.6A.1 アプリ全体の状態
- 本ソフトは、少なくとも以下の基本状態を持つこと。
  - 未起動
  - 起動中（初期化中）
  - バックグラウンド待機中
  - ゆうこ通知中
  - メイン画面表示中
  - 設定画面表示中
  - アーカイブ閲覧中
  - 終了中
- 本ソフトは、通常時は **バックグラウンド待機中** を基本状態とすること。
- 起動時は、必要に応じてニュース取得およびおすすめ候補更新を行った後、バックグラウンド待機中へ遷移すること。
- 長時間起動継続時は、日付変更時点（深夜0時）でニュース取得およびおすすめ候補更新を行った後、再びバックグラウンド待機中へ戻ること。

#### 7.6A.2 記事状態
- 各ニュース記事は、少なくとも以下の処理状態を段階的に持てること。
  - 取得済み
  - 本文抽出済み
  - Markdown化済み
  - 要約生成済み
  - おすすめ候補
  - ゆうこ紹介候補
  - アーカイブ対象
  - アーカイブ済み
  - 再展開済み
- 記事状態は、取得処理、表示制御、アーカイブ運用、およびおすすめ判定に利用できること。

#### 7.6A.3 お気に入り状態
- お気に入りは独立した記事状態ではなく、**フラグ** として管理すること。
- お気に入りフラグが有効な記事は、通常のアーカイブ候補から除外されること。

#### 7.6A.4 用語解説状態
- 用語解説は、少なくとも以下の段階的状態を持てること。
  - 範囲選択中
  - 解説ボタン表示中
  - 辞書参照中
  - AI解説生成中
  - 解説表示中
  - 詳細表示中
  - 要点説明中
  - ゆうこ辞書保存済み
- 完全一致するゆうこ辞書項目が存在する場合は、AI解説生成前に辞書参照を優先すること。

#### 7.6A.5 友情ランクおよび報酬状態
- 友情ランク関連は、少なくとも以下の状態を管理できること。
  - ポイント加算対象
  - 日次上限到達
  - ランクアップ可能
  - 報酬未通知
  - 報酬通知中
  - 報酬獲得待ち
  - 報酬確認済み
- ランクアップ条件を満たした場合、報酬は即時自動反映せず、まず **報酬未通知** 状態へ遷移すること。
- ゆうこが画面上に表示されていない場合は、画面端から登場して報酬獲得を通知すること。
- ゆうこがすでに表示中の場合は、一度画面外へ退場した後、あらためて報酬通知演出として登場できること。
- ユーザーが **OKボタン** を押下した時点で、報酬は正式獲得となり **報酬確認済み** 状態へ遷移すること。

#### 7.6A.6 起動・待機・表示遷移の基本方針
- 本ソフトは、未起動 → 起動中 → バックグラウンド待機中 の順で基本遷移すること。
- バックグラウンド待機中から、条件に応じてゆうこ通知中またはメイン画面表示中へ遷移できること。
- メイン画面は、ユーザーが明示的に開いた場合、またはゆうこの誘導から詳細表示へ進んだ場合にのみ表示することを基本とする。
- 設定画面およびアーカイブ閲覧画面は、メイン画面から遷移し、終了後はメイン画面またはバックグラウンド待機中へ戻れること。



### 7.6B ガチャ要素（採用時）

#### 7.6B.1 基本方針
- 継続利用性および報酬体験の強化を目的として、**ガチャ要素** を導入できること。
- ガチャ要素は、ニュース閲覧やゆうことの交流を主目的とする体験を阻害しない範囲で提供すること。
- 初期版では、ガチャの細かな演出、排出率、収集数の詳細は後続設計で調整可能とし、本書では導入方針と初期仮定を定めること。

#### 7.6B.2 通貨名
- ガチャで使用する通貨の初期名称は、**流れ星のかけら** とすること。
- 表示名称、アイコン、UI上の表記ゆれは後続設計で調整可能とすること。

#### 7.6B.3 入手経路（初期仮定）
- 流れ星のかけらの初期想定入手経路は、少なくとも以下を候補とすること。
  - 友情ランク報酬
  - ニュース閲覧や継続利用に応じた獲得
  - 特定の行動達成時の追加報酬
  - 将来的なイベント的配布
- 実際の付与量、頻度、条件は、ゲーム要素が強くなりすぎないよう後続設計で調整すること。

#### 7.6B.4 排出対象（初期仮定）
- ガチャの排出対象は、少なくとも以下を候補とすること。
  - UIテーマ
  - ゆうこのデコレーション要素
  - 吹き出しデザイン
  - 表情差分
  - 話し方 / 口調の追加要素
  - 性格表現やセリフ系の追加要素
  - 将来的な特別演出用要素
- 排出対象は、実用機能を阻害しない範囲で、継続利用や収集の楽しさに寄与するものとすること。

#### 7.6B.5 重複時の扱い（初期仮定）
- 既に所持済みの排出対象が重複した場合の扱いは、少なくとも以下を候補とすること。
  - 流れ星のかけらへの一部還元
  - 別の補助素材への変換
  - 重複獲得として記録のみ行う
- 初期方針としては、**ユーザー体験を損ないにくい還元方式** を優先候補とし、詳細は後続設計で確定すること。

#### 7.6B.6 レアリティ（初期仮定）
- ガチャ要素を導入する場合、**レアリティ概念を持たせるかどうか** を選択可能な設計が望ましい。
- 初期仮定としては、レアリティ導入を候補としつつ、初期版では過度に複雑化しないよう調整すること。
- レアリティを導入する場合でも、UI上の分かりやすさと軽量性を損なわないこと。

#### 7.6B.7 ガチャ実行と結果表示
- ガチャ要素を導入する場合、専用の **ガチャ画面** または同等の実行導線を持つこと。
- ガチャ実行後は、結果表示をユーザーが認識しやすい形で提示できること。
- 結果表示では、少なくとも以下を扱えることが望ましい。
  - 排出対象名
  - 新規獲得か重複か
  - 必要に応じたレアリティ表示
  - ゆうこの反応またはコメント
- ガチャ結果は、必要に応じてカスタマイズ画面や所持一覧画面へ遷移できること。

#### 7.6B.8 所持情報管理
- ガチャ要素を導入する場合、少なくとも以下の所持情報を管理できること。
  - 所持中の流れ星のかけら数

  - 未確認の新規獲得物
  - 直近の獲得履歴（必要に応じて）
- これらの情報は、カスタマイズ画面、ガチャ画面、または報酬確認画面等から閲覧可能であることが望ましい。

#### 7.6B.9 UX上の方針
- ガチャ要素は、ニュース閲覧や用語理解を継続した結果として楽しめる副次的要素とすること。

### 7.8 データ移行機能（将来拡張）

#### 7.8.1 基本方針
- PC変更や別PC利用に備え、将来的にローカルデータ移行機能を提供できる構成とすること。
- MVPでは本実装対象外とし、ローカル保存構造と移行対象データの整理を優先すること。
- 移行対象データは、ニュースMarkdown、ゆうこ辞書、閲覧履歴、お気に入り、友情ランク、報酬情報、ガチャ所持情報、UIテーマ設定、通知設定等を候補とすること。
- AI APIキー、OAuthトークン、Google認証情報、メール本文、メール送信者情報、ログ、一時キャッシュは移行対象外とすること。

#### 7.8.2 ローカルZIP書き出し方式
- 最も単純な移行方式として、移行対象データをZIP化し、ユーザーが別PCへ移す方式を候補とすること。
- ZIP作成、対象データ収集、復元処理はRust側で行うこと。
- React側は進捗表示、確認画面、エラー表示を担当すること。
- 会社セキュリティ上、USBメモリ等の利用が禁止される可能性があるため、代替方式も検討すること。

#### 7.8.3 Google Drive一時保存方式
- 将来的な拡張として、暗号化した移行ZIPをGoogle Driveへ一時保存する方式を候補とすること。
- 開発段階では通常Driveフォルダ、本格運用ではappDataFolder利用を候補とすること。
- Drive上には平文ZIPや復号鍵を保存しないこと。
- 復元には長めのワンタイムパスコードまたはQRコードを利用できること。
- 復元完了後または有効期限経過後、一時ファイルを削除できること。
- Google Drive API利用可否、OAuthスコープ、個人Drive利用可否は会社セキュリティ方針確認後に決定すること。

#### 7.8.4 QRコード
- QRコードは、ランダムなQR風画像ではなく、復元用データから生成した正規QRコードとすること。
- QRコード中央にゆうこの顔アイコン等を配置する場合は、誤り訂正レベルと読み取り精度を確認すること。
- 復元用データ生成、復元キー生成、検証はRust側で行い、React側はQR表示を担当すること。


## 8. 非機能要件

### 8.1 セキュリティ要件
社内公開を前提とするため、以下の対策を考慮すること。現段階では安全寄りの初期方針として定義し、詳細は後続設計およびチームレビューで精査する。


#### 8.1.0 Tauri版セキュリティ境界
- Tauri版では、React / TypeScriptを表示層、Rustを外部通信・保存・AI連携・検証層として分離すること。
- React側にAPIキー、OAuthトークン、Google認証情報、復元キー、ワンタイムパスコード内部生成元を保持させないこと。
- Tauri commandは必要最小限の公開に留め、任意ファイル読み書きや任意URL取得を可能にする汎用commandを作成しないこと。
- Tauri capability / permissionは最小限とし、プラグイン追加時は権限とライセンスをレビューすること。
- 外部通信、AI送信、Markdown / JSON保存、ログ出力はRust側で制御すること。


#### 8.1.1 外部通信の制御
- ニュース取得先および AI 利用先は明示的に管理された接続先のみ許可すること。
- RSS取得先、記事HTML取得先、AI利用先は **許可リスト方式** で管理すること。
- 不要な外部通信は行わないこと。
- 通信先一覧を管理可能であること。
- 外部URL取得時は、ローカルアドレス、社内アドレス、file系スキーム等の危険な取得先を拒否すること。
- 将来的に取得先を追加する場合も、レビュー可能な設定経由で管理できることが望ましい。

#### 8.1.2 HTML取得および表示データの安全化
- 取得したHTMLはそのまま生表示しないこと。
- HTMLからは本文または本文抜粋、タイトル、公開日時等の必要情報のみを抽出し、内部処理に利用すること。
- スクリプト、危険な埋め込み要素、不正なリンク等を除去した上で整形すること。
- Markdown表示では埋め込みHTMLを原則無効化し、危険なURLスキームやスクリプト実行を防止すること。

#### 8.1.3 AI送信データの最小化
- AIへ送信するデータは、要約や解説に必要な最小限の情報に限定すること。
- 初期方針として、記事抽出テキスト、本文抜粋、タイトル、ユーザーが選択した用語または短文のみを送信対象とすること。
- ユーザー環境情報、他ファイル内容、履歴全量等は送信対象に含めないこと。
- AI利用先へ送るデータ内容は将来的に設定・監査できることが望ましい。

#### 8.1.4 データ保護
- ユーザー設定、閲覧履歴、友情ランク情報などのローカル保存データは安全に管理すること。
- 機密情報を含む設計にしないこと。
- API キーや認証情報はコードへ直書きしないこと。
- APIキーや秘密情報は、環境変数、OSの安全な保管機構、暗号化設定領域等に格納することを検討すること。
- 機微情報は OS の安全な保管手段や暗号化保存を検討すること。

#### 8.1.5 入力値対策
- ニュース本文、AI入力、ユーザー選択テキストなど外部由来の文字列はサニタイズ処理を行うこと。
- Markdown 表示時のスクリプト実行や危険なリンク展開を防止すること。
- HTML取得結果をMarkdownへ変換する際も、安全な整形処理を行うこと。
- 外部由来データをファイル名、表示文言、内部テンプレートへ反映する際は、制御文字や危険文字列への対策を行うこと。

#### 8.1.6 ログ管理
- エラーや動作ログは必要最小限に留めること。
- 個人情報や機微情報がログに過剰出力されないこと。
- 記事本文全量、ユーザーの選択文字列全文、APIキー、認証情報等は原則ログへ出力しないこと。
- 初期方針として、取得成否、要約成否、エラー概要、友情ポイント加算イベント等の運用上必要な情報のみ記録すること。

#### 8.1.7 更新性
- 脆弱性対応のため、依存ライブラリやモデル接続部を更新しやすい構成にすること。
- 取得先ドメイン一覧、HTML抽出ルール、AI送信設定、Markdown表示設定等を後から更新しやすい構成が望ましい。

### 8.2 性能・軽量性要件
- ニュース一覧表示は日常利用でストレスのない速度で行えること。
- 用語解説表示は、可能な限り短時間で返すこと。
- ゆうこ辞書に完全一致する項目が存在する場合は、AI再問い合わせを行わずに高速表示できることが望ましい。
- アーカイブ処理は通常操作を阻害しないタイミングで行うこと。
- ゆうこの出現・退場・画面遷移演出は、日常利用で不快感を与えない応答速度で行えること。
- 起動時ニュース取得は、業務開始時の体験を大きく阻害しない範囲で完了すること。
- 本ソフトは、バックグラウンドで常駐していても業務利用に支障を与えにくい軽量な動作を目指すこと。
- 起動、ニュース一覧表示、ゆうこの表示、用語解説表示などの主要操作は、ユーザーに待ち時間のストレスを与えにくい速度で行えること。
- キャラクター演出や画面遷移は、見た目の楽しさだけでなく、操作の快適さを損なわないこと。
- UXを重視し、日常的に使っても煩わしさを感じにくい応答性と操作性を備えること。
- メモリ使用量、CPU負荷、通信頻度は、常駐アプリとして過剰にならないよう配慮すること。
- 本ソフトは、通常時はバックグラウンドで常駐することを前提とすること。
- ユーザーが明示的にメイン画面を開いた場合、またはゆうこの誘導から詳細表示へ進んだ場合を除き、メイン画面は常時表示しないこと。
- バックグラウンド常駐時には、不要な画面描画やウィンドウ保持を避け、軽量な待機状態を保つこと。
- 常駐時は、ゆうこの登場や通知に必要な最小限の機能のみを動作させること。

## 9. データ管理要件


### 9.0 Tauri版ローカル保存方針
- ローカルデータは、Tauriのアプリデータディレクトリ配下へ保存することを基本とする。
- 開発中は検証用ディレクトリを利用してもよいが、本番想定ではOS標準のアプリ管理領域へ寄せること。

- Markdown / JSONの保存、読込、更新、アーカイブ、移行対象収集はRust側repository / serviceで行うこと。

### 11.0 Tauri版運用・開発要件

- Rust側は必要に応じて `cargo check` で確認できること。
- VS Codeの推奨拡張は `.vscode/extensions.json` で共有できること。
- `node_modules/`、`src-tauri/target/`、`.env`、認証情報、実ユーザーデータはGit管理対象外とすること。
- `Cargo.lock` はアプリ開発であるため、基本的にGit管理対象とすること。
- AGENT.mdに従い、AI駆動開発時もReact / Rustの責務分離を維持すること。

- RSS取得対象媒体および補助ニュースソースの変更や追加が可能なこと。
- AI要約ロジックやプロンプトの差し替えが可能なこと。
- アーカイブ保管期間や圧縮ルールを変更可能なこと。
- デコレーションやテーマの追加配布または更新が可能なこと。
- HTML本文抽出テンプレートの更新が可能なこと。
- ゆうこ辞書項目の管理ルールや保存形式を更新可能なこと。
- ガチャ排出対象、通貨入手経路、重複時処理ルール等を後から更新可能なこと。
- 将来的に社内限定ニュースや社内お知らせを混在表示できる拡張性が望ましい。

## 12. 制約・前提条件

### 12.1 前提
- 利用環境は PC を想定する。
- 社内公開であるため、利用者は一定のITリテラシーを有することを前提とする。
- ニュース本文の扱いについては、利用するニュースソースの規約を確認した上で、必要に応じてタイトル・要約・リンク中心の構成とする。
- ソフト内表示は、記事本文そのものの大量表示ではなく、ゆうこによる再説明文、要点整理、注目ポイント、用語補足を中心とする。
- 原文表現の確認は、出典リンクから元記事へ遷移する方式を基本とする。
- 懐かしさの表現は企画背景に留め、第三者の権利を侵害しない独自表現とする。
- MVPでは記事閲覧体験の統一性を重視し、ソフト内ビューを主軸とする。
- HTMLからMarkdownへの整形は、生成AIではなくテンプレートベースの処理を基本とする。
- ゆうこ辞書の再利用判定は、初期版では完全一致を基本とする。

### 12.2 制約
- 著作権や利用規約に反する形でニュース本文を無制限に保存・再配布しないこと。
- ソフト内表示は、原文の大量転載や原文表現の実質的代替とならないよう配慮すること。
- 社内利用であっても、外部送信データの扱いには十分注意すること。
- キャラクター、名称、画面デザインは独自表現とし、既存作品の模倣にならないこと。
- 外部ブラウザ上の高度な追従補助は、MVPでは必須としないこと。
- 記事本文は媒体により全文取得できない場合があるため、本文または本文抜粋を扱う前提とすること。
- ゆうこ辞書の類似一致再利用や高度な検索機能は、MVPでは必須としないこと。

## 15. v3.1_Tauri時点のまとめ
本システムは、ニュース取得・AI要約・用語解説・キャラクター通知・継続利用要素を組み合わせた、実用性と遊び心を両立する AI ニュースコンパニオンである。

特に、マスコットキャラクター「ゆうこ」が単なる装飾ではなく、
- ニュースを勧める
- 難しい言葉を噛み砕く
- 継続利用の動機になる
- 業務の邪魔にならないよう状況に応じて振る舞いを抑制する
- 一度説明した言葉や要点を「ゆうこ辞書」として蓄積する
という複数の役割を担うことが本システムの核となる。

また、友情ランク上昇時にデコレーション要素またはUIテーマを1つずつ解放する仕組みにより、ニュース閲覧を継続しやすい軽量なゲーム体験へつなげる。

v2.9では、これまで整理したニュース取得、ソフト内表示、用語解説、ゆうこ辞書、友情ランク、軽量常駐、セキュリティ初期方針、およびおすすめ判定ロジックに加え、**アプリ全体の基本状態、記事状態、お気に入りフラグ管理、細かな既読状態、用語解説状態、報酬通知から正式獲得までの状態遷移、深夜0時更新、およびPC起動時自動起動設定** を明確化した。次フェーズでは、技術選定、HTML抽出方式の詳細設計、性能目標値の具体化、ガチャ要素の詳細仕様調整、および基本設計への落とし込みへ進むものとする。

## 16. Tauri版としての最終整理

### 16.1 MVPで優先する中心体験
Tauri版MVPでは、以下の体験を最優先で成立させる。

```text
Tauriアプリ起動
  ↓
RSSニュース取得
  ↓
Rust側でMarkdown / JSON保存
  ↓
React画面におすすめニュース表示
  ↓
ゆうこがニュースを紹介
  ↓
ニュース閲覧画面でAI要約・再説明を表示
  ↓
選択語句をゆうこが解説
  ↓
ゆうこ辞書へ保存
  ↓
友情ポイント・ランク進捗に反映
```

### 16.2 MVPでは後回しにするもの
以下は魅力的な要素ではあるが、MVPでは本格実装を後回しにする。

- Google Driveデータ移行
- Googleメール連携
- 本格的なガチャ排出率管理
- 大量のテーマ・デコレーション
- Live2D等の高度演出
- 高度な通知抑制
- 月次アーカイブの完全自動運用
- 類似語句による辞書再利用

### 16.3 Tauri版で守るべき実装原則
- React / TypeScriptは画面と操作に集中する。
- Rustは通信、保存、AI連携、状態確定、検証を担当する。
- Tauri commandはアプリ固有の安全な操作だけを公開する。
- APIキーや認証情報をReact側に渡さない。
- AI送信データは最小限にする。
- HTMLを生表示しない。
- Markdown表示時の危険HTMLを無効化する。
- MockProviderでAPIなしでもデモ可能にする。
- 常駐アプリとして軽量性を重視する。
